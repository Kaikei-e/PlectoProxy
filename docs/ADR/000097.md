# ACME(自動 HTTPS)を序列外から deferred 先頭へ昇格し、証明書ローテーション検知の二層 content hash を床として同時に固定する

## Status
accepted

## Date
2026-08-01

## Affected Components
- roadmap / governance — deferred 序列の改訂(5 回目)。[[000074]] 以来の序列 4 スライス(mTLS [[000078]] / PROXY v2 [[000057]] / 圧縮 [[000075]] / h3 drain [[000059]])は全て着地済みであり、本 ADR は空になった序列の次の先頭を確定する
- control(`plecto-control`)— `content_hash_at` の対象拡張と reload フィンガープリントの導入(実装は本 ADR と同一ブランチの RED/GREEN コミット)
- fast path(`plecto-server`)— v1 実装 ADR への引き継ぎ制約のみ(本 ADR ではコード変更なし)

## Context

対競合の記述は [[000067]] の規律に従い、個別プロダクト名を挙げず実装の型で語る。

### 外部事実(取得日 2026-07-31 / 2026-08-01、一次ソースで裏取り済み)

- **ACME はテーブルステークス化が完了した。** 証明書自動化に最も保守的だった主要 Web サーバ実装までもが 2025-08 に native ACME モジュール(Rust 実装)を出荷し、続くリリースで TLS-ALPN-01 対応も追加した。自動 HTTPS を長年内蔵してきた先行プロキシ実装群では、それが採用理由の第一位であることが複数ソースで一貫している。[[000043]] 時点(2026-07-02)の「ネイティブ ACME はテーブルステークス化した」という認識は、その後さらに確定した。
- **証明書短命化は制度として不可逆になった。** CA/B Forum SC-081v3(2025-04 可決)は最大有効期間を 200 日(2026-03-15)→ 100 日(2027-03-15)→ **47 日(2029-03-15)**へ段階短縮する。Let's Encrypt は 45 日プロファイル(2026-05-13 発行開始)・160 時間 `shortlived` プロファイル(2026-01-15 GA)を出荷済み。外部クライアント併用運用の摩擦は年々増える一方である。
- **更新オーケストレーションは標準化された。** ARI(ACME Renewal Information)は RFC 9773(Standards Track、2025-06)として発効し、Let's Encrypt は `replaces` 付き ARI 更新を**全レート制限から除外**する。OCSP は Let's Encrypt が 2025-08-06 に完全廃止した(stapling は実装対象から消えた)。
- **Rust 実装の部品は成立している。** `instant-acme` 0.8.5(2026-02-24、aws-lc-rs 既定・ARI/profile 対応済み・HttpClient 差し替え可能)は、通常依存の全てが既に Plecto の依存木に存在する(hyper 1 / rustls 0.23 / aws-lc-rs / serde / thiserror 2)。対して `rustls-acme` は別系統の async リアクタ・第二 HTTP クライアント・chrono を必須依存で持ち込み、`tokio-rustls-acme` は ring を非オプションで持ち込む(いずれも [[000051]] の単一 provider・`deny.toml` 規律と衝突)。
- **反面教師も特定済み。** ACME を内蔵する先行実装の一つには、challenge 用 fast path が接続 deadline を解除していた脆弱性(CVE-2026-22045、2026-01-15 公表)がある: `acme-tls/1` を広告して沈黙するだけの未認証クライアントで fd を無期限に固定できた。同実装の HTTP-01 側にも同型の先例(CVE-2023-47124)。**challenge 経路に通常のタイムアウト・接続上限のバイパスを作った**ことが共通原因である。また別の先行実装は証明書未取得時に自己生成証明書で handshake を完了させる(fail-open)。

### 内部事実

- [[000043]] は ACME を「序列外の完全後回し」とし、再検討条件 (c) を「証明書の外部クライアント運用がセルフホスト採用の**実測ボトルネック**になったとき」と置いた。その代替策は「外部 ACME クライアント + SIGHUP reload([[000039]])」だった。
- その後 [[000067]] / [[000074]] / [[000076]] が近期顧客を**セルフホスター・データ主権志向チーム**と名指しした。ACME はこの層に最も効く欠落機能である(自動 HTTPS を第一看板とする先行実装群の採用動機がその証左)。[[000074]] が圧縮を昇格させた論法——顧客名指しにより [[000043]] 自身の「代替可能な機能より代替のない穴が先」基準を再適用する——が ACME にそのまま適用できる状態になった。
- **2026-08-01 のコード実査で、[[000043]] の代替策そのものを壊す実装上の罠を特定した。** reload gate(`control_reload.rs`)は manifest の semantic content hash で冪等判定するが、hash にバイト列が乗るファイル参照は `[listen.client_auth].ca_path` のみ。`[[tls]]` の cert/key、`[upstream.tls]` の ca / client_cert / client_key、`[filter.config_files]`([[000095]])、`[resumption].stek_file`([[000062]])は **in-place 更新 + SIGHUP が `Unchanged` として no-op になる**。つまり外部 ACME クライアントの標準的な deploy-hook(ファイル差し替え → SIGHUP)は、manifest を書き換えない限り新証明書を読まない。[[000014]] が sharp edge としてコード内に明記していた既知事項だが、「外部クライアントで運用が成立する」という [[000043]] の前提とは両立していなかった。
- 秘密材料をそのまま公開 config version に digest する単純な拡張には oracle 問題がある: config version はログに出る公開値であり、`H(manifest ‖ H(secret))` を公開すると、manifest(git 管理で可読)とログを持つ観測者が**低エントロピー secret(`[filter.config_files]` の API キー等)をオフライン総当たりで検証できる**。CA・証明書(公開材料)にはこの問題がない。

## Decision

1. **deferred 序列を改訂する(5 回目): 序列の先頭に ACME(自動 HTTPS)を置く。** [[000074]] までの序列 4 スライスは全て着地済みであり、ACME は現存する deferred 群(mTLS スライスの CRL/OCSP・client identity 伝播 [[000078]]、wasi-otel guest 契約 [[000040]] ほか)より先とする。実装は着手時の個別 ADR で確定する([[000029]] の運用どおり。序列は優先順位であり実装内容の先取りではない)。
2. **昇格の根拠を誠実に記録する: [[000043]] 再検討条件 (c) の文言(実測ボトルネック)は未充足である。** 採用実測データは存在しない。本昇格は (c) の発火ではなく、[[000074]] と同型の**顧客名指しによる基準再適用**(セルフホスターにとって ACME にはプロダクト内の代替がない)+ 外部水準の確定(テーブルステークス化・短命化制度)+ **代替策の実装欠陥**(下記 3 の罠により「外部クライアント + SIGHUP」が宣言どおり機能していなかった)の三点による。[[000043]] には dated 追記を行う。
3. **床の即時修正を確定する(本 ADR と同一スライスで着地): reload gate を二層 content hash 化する。** 不変則は「**`build_active` が読むファイルの in-place ローテーションは、必ず reload gate を通過させる**」。
   - **公開材料**(`[[tls]]` cert、`[upstream.tls]` ca / client_cert)は既存の `[listen.client_auth].ca_path` と同様、**公開 config version に digest** する(ドメイン分離ラベル付き)。
   - **秘密材料**(`[[tls]]` key、`[upstream.tls]` client_key、`[resumption].stek_file`、`[filter.config_files]` の各ファイル)は**ログ・エラー・公開アクセサに一切出ない reload 専用フィンガープリント**として別枠で digest し、gate は「公開 version とフィンガープリントの両方が一致」した場合のみ `Unchanged` を返す。公開 version に混ぜないのは上記 oracle の遮断のため。`config_version()` の公開意味論([[000008]] の監査同一性・レプリカ間比較可能性)は不変。
   - gate 時点でファイルが読めない場合は従来どおり warn の上で full rebuild へフォールスルーし、build 側が fail-closed で正確なエラーを返す。
4. **v1 実装 ADR への引き継ぎ制約を記録する**(本 ADR では実装しない):
   - **challenge 方式**: TLS-ALPN-01(RFC 8737)を主経路とし、既存 rustls `ResolvesServerCert`([[000014]])内で解決する(`acme-tls/1` ALPN + pending SNI → challenge 証明書を返す。新規 listener 不要)。HTTP-01 は **manifest が plaintext listener を明示宣言した場合のみ**の副経路(CDN / L4 前段で `acme-tls/1` が届かない構成向け。:80 の暗黙 open はしない)。**declined(理由付き)**: DNS-01 とプロバイダプラグイン面(先行実装群の実証——一方は 150+ の DNS プロバイダを in-tree に抱えるに至り、他方は意図的にプロバイダ面を本体外の per-provider ライブラリ群へ切り出した。どちらの道も単独メンテナ体制と供給網規律 §3.3 が抱えるには重い)、wildcard(DNS-01 帰結)、on-demand / dynamic-SNI 発行(発行が攻撃者起動可能になる)、multi-CA フェイルオーバ、OCSP stapling(Let's Encrypt 廃止済み・short-lived は失効情報を構造的に持たない)。
   - **fail-closed 不変則**: 自己署名フォールバックは**恒久的に持たない**(先行実装の fail-open を反面教師とする)。CA が発行していない証明書を提示する経路は存在しない。未発行 SNI は handshake 拒否(既存 SniResolver の no-match 挙動と同型)。boot は非ブロッキング — 有効な cached cert を持つ host は即 serve、初回発行待ちの host は handshake 拒否 + readiness へ反映 + error ログ。リトライは指数 backoff(上限 1 日・最長 30 日という先行実装の実績値を借用、authz 失敗 5 回/時/identifier の CA 制限を尊重)、staging directory スイッチを一級で持つ。
   - **challenge 経路は通常の handshake タイムアウト・接続上限・admission control([[000092]])を完全に継承する**(CVE-2026-22045 の教訓: バイパス経路を作らない)。challenge 接続は challenge 証明書で終端し、upstream へ決してルーティングしない。
   - **ライブラリ**: `instant-acme`(`default-features = false`, `features = ["aws-lc-rs", "time", "x509-parser"]`)+ 自前 `HttpClient`(既存 hyper-util legacy client + webpki-roots。OS trust store 不使用 = [[000042]] 維持、単一 crypto provider = [[000051]] 維持)。**outbound は設定された directory host に pin する**(RFC 8555 は CA が返す URL を追跡するプロトコルであり、悪意ある directory による client-side SSRF を許さない)。CA 鍵 pin はしない(Let's Encrypt は 2026-05 に中間証明書の世代交代と発行一時停止を経ており、鍵 pin は有害)。directory URL は manifest 専用(実行時変更経路なし)。
   - **状態**: node-local([[000053]])。`<state_dir>/acme/<directory-host>/` 配下に account key / cert / meta を 0700/0600・atomic rename で置き、CA host でキー付け(staging↔production の account 混線防止)。取得済み証明書の反映は**既存の atomic reload swap 経路のみ**を使う(第二の証明書導入機構を作らない)。ACME 状態・challenge トークンはフィルタの capability 面に一切露出しない(P4)。
   - **更新**: ARI-first(RFC 9773。`Retry-After` 周期で poll、`suggestedWindow` 内の一様乱択、**`replaces` 必須** — レート制限除外の条件であり、マルチレプリカ時の正しさ要件)。ARI 不在時のフォールバックは残存寿命 1/3 + jitter。**絶対日数定数は書かない**(SC-081v3 の段階短縮で 18 ヶ月以内に誤りになる)。profile は manifest の opt-in 文字列(`shortlived` は「ノード 1 週間停止 → 有効証明書ゼロ → fail-closed で serve 不能」の相互作用を文書化した上での明示選択)。
   - **静的 cert 優先**: manifest 宣言の静的証明書が同一 SNI では常に勝つ。同一 host に静的 cert と ACME の両宣言は validate エラー(fail-closed。ACME が operator pin を silent に影で置き換える経路を作らない)。
   - **v1 は単一ノード限定。** L4 LB 配下の N レプリカでは CA の検証接続が任意のレプリカに着地し、node-local 状態の TLS-ALPN-01 は構造的に成立しない(ACME 内蔵の先行実装が multi-instance 構成を公式に非対応と宣言する理由と同一)。共有ストレージ + リーダー選出は作らない — それは [[000008]] の opt-in 分散ゲートの向こう側であり、compose reference([[000088]])構成では前段 LB 側または外部クライアントで証明書を扱う運用パターンをガイドに記載する。

検討した代替案と却下理由:

- **序列据え置き(ACME を序列外のまま、運用ガイド強化のみ)** — [[000067]] の顧客名指しと序列根拠のずれを放置することになり、[[000074]] が圧縮昇格で確立した自基準の再適用に対して不整合。さらに Decision 3 の罠により「外部クライアントで成立」という現行の公式見解自体が実装上偽だった。却下。
- **[[000043]] (c) の発火を主張する** — 実測ボトルネックの一次データは存在しない。P10 / §3.4(反証可能性)に反する主張はしない。却下(昇格根拠は Decision 2 の三点で立つ)。
- **`rustls-acme` / `tokio-rustls-acme` の採用** — 前者は別系統 async リアクタ・第二 rustls 統合・第二 HTTP クライアント・chrono を必須依存で持ち込み、後者は ring を非オプション依存に持つ(二重 crypto provider)。いずれも [[000051]] と `deny.toml` の供給網規律(§3.3)に反する。full-lifecycle 実装は魅力だが、challenge responder と scheduler は Plecto が既に持つ `ResolvesServerCert` / SIGHUP swap の上に書くべき薄い層である。却下。
- **秘密材料も公開 config version に digest する一層方式** — 実装は最少だが、manifest + ログ観測者に対する低エントロピー secret のオフライン総当たり oracle を作る。「config_files は高エントロピー値を推奨」という文書化で受容する案も検討したが、[[000054]] の審査票水準(空欄なく答える)に対して能動的に弁明が必要な設計を新規に持ち込む理由がない。却下。
- **公開材料のみ digest(秘密材料は非対応のまま)** — 外部 ACME クライアントの deploy-hook の罠は塞がるが `[filter.config_files]`([[000095]] の secret 間接参照)と STEK の in-place ローテーション罠が残り、不変則が「一部のファイルは gate を通る」という運用者の注意力依存に退化する。却下。
- **自己署名フォールバック / 発行待ち 503** — 503 を返すには handshake 完了 = 未検証証明書の提示が必要であり、裏口の fail-open。P4 により却下(plaintext listener が宣言されている場合の :80 での 503 は可)。

本決定は [[000029]](役割駆動)の配置基準を変えない — ACME は横断的データプレーン関心事(採用基準 (i))として native 適格であり、[[000037]] / [[000043]] の「user-policy は拡張プレーン」とも交差しない。

## Consequences

### Pros
- deferred 序列が [[000067]] / [[000076]] の顧客名指し(セルフホスター)と再び整合し、[[000084]] の operator TTFV(≤5 分)導線に「証明書の手動用意」という最大の摩擦を残さない道筋が立つ。
- 二層 hash の着地により、**ACME 実装前であっても**「外部 ACME クライアント + SIGHUP」が宣言どおり機能する(即効の床)。`[filter.config_files]` / STEK / upstream mTLS 素材のローテーション罠も同時に閉じる。
- 昇格根拠と (c) 未発火の区別が記録され、「実測データが無いのに条件発火を主張した」という将来の監査上の疑義を構造的に排除する。
- v1 実装 ADR が引き継ぎ制約から書き始められる([[000074]] → [[000075]] と同じレール)。

### Cons / Tradeoffs
- ACME 実装は fast path に**未認証の新規パース面**(ALPN 分岐・challenge 証明書経路)と**データプレーン発の新規 egress**(CA への outbound)を追加する。引き継ぎ制約(タイムアウト継承・directory pin・upstream 非ルーティング)を実装 ADR の必須制約とする。
- 単一ノード限定の宣言は、compose reference([[000088]])のマルチレプリカ標準形と ACME の同時利用を v1 では塞ぐ(前段 LB 終端または外部クライアント運用をガイドで案内)。
- reload gate の判定材料が「公開 version + 非公開フィンガープリント」の 2 値になり、`Unchanged` の説明可能性が公開値だけでは完結しなくなる(ログには「fingerprint mismatch による rebuild」の事実のみ残し、値は残さない)。
- 序列改訂は 5 回目である。[[000074]] が置いた運用(改訂には顧客名指し級の前提変化を要求)に対し、本件は「顧客名指し(既存)+ 外部水準確定 + 代替策の実装欠陥発見」であり基準を満たすと判断したが、以後も同水準を要求する。
- **再検討条件**: (a) CDN / L7 前段構成のセルフホスト需要が支配的になった場合、HTTP-01 の位置づけ(副 → 主)と trusted-proxy XFF append([[000018]] 系の deferred)を同一文脈で再評価する; (b) マルチレプリカ ACME の実需が一次データで積み上がった場合、共有ストレージ + 調整を [[000008]] の opt-in 分散ゲートの議題として個別 ADR で扱う(native には入れない); (c) wildcard 実需が DNS-01 declined の再考材料になった場合、プロバイダをプロキシ本体に抱えない外部化の形のみを検討対象とする; (d) 2029 の 47 日世代で既定 profile と更新頻度の前提を再点検する。
