# on-response-body(buffer-then-decide)を plecto:filter@0.4.0 で導入し、world 格子受理と厳格 fail-closed 検査既定を確定する

## Status
accepted — **実装済み**(2026-08-09、2 スライス)。前半で契約バージョンのレール(0.3.0 を `wit/v0.3.0/` へ凍結、`plecto:filter@0.4.0`、`request-body-decision` の同形化、`BoundFilter::V04` と 0.1/0.2/0.3 のロード時アダプタ)、後半で `on-response-body` を端から端まで(格子受理の export 探針 `BodyHooks { request, response }`、ヘッダ保持のバッファリング、検査不能クラスの fail-closed、over-cap tri-state、as-received MIME 判定、guest 出力長と content-length の再検証、方向合算の単一バイト予算)。[[000104]] の `path-with-query` 改名も前半に同乗した。実装で確定した事項と、確定できなかった 1 件は Consequences の 2026-08-09 追記を見よ。

## Date
2026-08-01

## Context

対競合の記述は [[000067]] の規律に従い、個別プロダクト名を挙げず拡張モデルの型で語る。

### 契約整合性の穴(2026-08-01 のレビューで言語化)

設計原則 §3.1 は「認証・WAF ルール・**PII マスキング**・カスタムロジック → 拡張プレーン」と定め、[[000037]](native WAF declined)・[[000043]](AI/LLM gateway native declined)は「フィルタで書ける」ことを declined の受け皿にした。しかし現契約(0.3.0)に upstream response body を**読む**フックは存在しない — `on-response` の `resp.body` は常に空で、`replace` は合成のみ([[000073]])。response 側の情報漏えい検査・PII マスキング・LLM ガードレールはいずれも response body を読めなければ書けず、**「native では作らない、フィルタで書ける」の後段が現契約では成立していない**。native declined 判断群の受け皿を実体化することが本 ADR の目的である。

### 外部前例(取得日 2026-08-01、一次ソースで裏取り済み。実装の型で記す)

- **module-ABI 型拡張仕様(公開 ABI v0.2.1 系)**: response body はチャンク + `end_of_stream` で通知され、PAUSE 返却でホストが蓄積する「buffer-then-decide」が全体バッファの慣用形。callbacks は「export されていれば呼ぶ」の **export 存在検出**であり、world という概念を持たない。`content-length` 再計算の規定が無く、代表的ホスト実装の作例は body 変更時に content-length を**削除**して回避している。第 2 世代 OSS WAF エンジンの WASM 移植は「エンジンへは逐次供給、判定確定まで PAUSE で全体バッファ」のハイブリッドで、**ヘッダが先行送出済みのため phase 4 では拒否できず、漏えい検知時は本文を NUL バイトで塗りつぶす**のが最善手になっている(実装コメントに明記)。
- **外部プロセッサ・コールアウト型(gRPC)**: body 送出モードは NONE / STREAMED / BUFFERED / BUFFERED_PARTIAL / 全二重の 5 値。**BUFFERED の over-cap はエラー(500 / 応答途中なら切断。413 は request 側専用語彙)**、BUFFERED_PARTIAL は**無言の切り詰め通過**。失敗時の既定は fail-closed(504/500 の local reply)で、fail-open は明示 opt-in。**body 変更を許すモードでは host が content-length を原則削除**し、guest が設定する場合は実長と不一致なら mutation 拒否 — 不一致許容は request smuggling 級の脆弱性になると公式に警告される。**実行時のモード交渉(guest がモードを上書きする形)は、buffer 状態の非同期化による downstream ハング・多段チェーンでの body 切り詰めの実バグが 2026 年時点で未解決**。
- **script 型拡張の教訓**: 全体バッファ API を持つ script 拡張で、**拡張が接続バッファ上限超の body を返した場合に use-after-free でクラッシュする CVE(CVE-2025-62504、2025 年公表、CVSS 6.5)**。guest が返した body の長さをホストが再検証しないことが原因。
- **WAF 実務の水準**: response 検査は **content-type 許可リスト + 上限付き全体バッファ**が業界の共通形。既定上限は 512 KiB(第 2 世代 OSS WAF エンジンの既定。仕様上の over-cap 既定は Reject/500)〜 1 MiB(接続バッファ既定)、マネージド WAF は先頭 64 KiB 固定など、**複数 MiB の response 検査上限を出荷する実装は確認できない**。出荷推奨設定が process-partial(部分検査で通す)へ倒れるのは「幾分安全でないが、正当なページを壊さない」(推奨設定コメント原文)という**ヘッダ先行送出の構造制約への妥協**であり、原則ではない。SSE(`text/event-stream`)は content-type 許可リストからの**不在**により除外されるのが慣用で、バッファすると streaming UX を壊す実害が複数実装で記録されている。
- **wasi:http@0.3.0(2026-06-11 発効)**: `service` / `middleware` world の response body は `stream<u8>` + `future<trailers>` であり、「読まない」ことがゼロコストのため **hook の有無という概念自体が消える**。`response` の headers は immutable で、変更は新 response の構築(= `replace` 相当)。[[000020]] の収斂が成立した時点で、本 ADR の export 探針機構は丸ごと不要になる(再検討条件に記す)。
  **（2026-08-09 訂正、[[000104]]）**「wasi:http@0.3.0(2026-06-11 発効)」は誤りである。2026-06-11 に発効したのは **WASI コアの v0.3.0** であり、**wasi:http 0.3.0 は 2026-08-09 時点で未発効**。一次ソース（同日再取得）では、`WebAssembly/wasi-http` の最新タグ／リリースは 0.2 系の `v0.2.8`（2025-10-07）、`main` の `wit/` は `package wasi:http@0.2.8;`、0.3 系は `wit-0.3.0-draft/` にあってパッケージ宣言は `wasi:http@0.3.0-rc-2025-09-16`（0.3 系の最新タグも同 rc）。draft の中身自体は rc タグ以後も動いており（2025-10-23 の handlers / worlds 再構成を含む）、本項が引く `service` / `middleware` / `handler` の形はその再構成後のものである。本項の型に関する記述（`stream<u8>` + `future<trailers>`、hook の有無の消滅、headers の immutability）は draft の実体として正しい。訂正の射程は**発効日と、それに基づく収斂の時間軸**に限られる。[[000020]] の収斂ゲートは「WASI コアが出た」ではなく「wasi-http が 0.3.0 を出した」で判定する。

## Decision

### 1. `plecto:filter@0.4.0` を契約正文として追加する

移行は [[000071]] / [[000073]] のレールを踏襲する: 0.3.0 を `wit/v0.3.0/` に凍結、host は `BoundFilter::V04` を追加して decoded imports の `@0.4.` で判定、0.1 / 0.2 / 0.3 guest はロード時アダプタで従来どおり動く([[000064]] の互換ポリシー)。0.4.0 の変更点:

```wit
// The typed outcome of a response-side BODY filter (buffer-then-decide).
// Mirrors response-decision (ADR 000073), not request-body-decision: on the
// response plane nothing is short-circuited — an already-received response is
// forwarded, edited, or replaced (P12).
variant response-body-decision {
    // forward the buffered body unchanged — the host never lowers the bytes
    // back across the boundary (the ADR 000038 body tax is paid once, not twice)
    %continue,
    // forward this body instead; header edits that MUST accompany a body
    // transform (content-type etc.) ride along. content-length is HOST-computed;
    // a guest-supplied content-length is rejected fail-closed (smuggling guard).
    modified(response-body-edit),
    // discard the upstream response (including the buffered body) and send this
    // synthesised one. Same fail-closed header validation as ADR 000071.
    replace(http-response),
}

record response-body-edit {
    body: list<u8>,
    set-headers: list<header>,
    remove-headers: list<string>,
}

// resp.body is always empty (status + headers only) — the buffered body arrives
// as its own parameter, exactly as on-response receives an empty-bodied response.
export on-response-body: func(req: http-request, resp: http-response, body: list<u8>)
    -> response-body-decision;
```

- **`%continue` は素の arm(payload なし)とする。** response 検査の支配的ユースケース(WAF / DLP / PII / ガードレール)は「読むが書き換えない」であり、`continue(list<u8>)` 形は共通系で全量 lift + 全量 lower の二重コピー税を課す。[[000038]] が計測した body 税を response 側に再輸入しない。
- **`request-body-decision` も 0.4.0 で同形に揃える**: `%continue` / `modified(request-body-edit)` / `short-circuit(http-response)`(0.3.0 の `continue(list<u8>)` 形は凍結 world に残り、アダプタが吸収する)。4 つの decision が全て「continue / modified / 終端」で読める(P12)。
- **`req` / `resp` を明示パラメータで渡す**([[000073]] の as-forwarded スナップショットと同じレール)。フィルタはステートレス(P6)であり、status / content-type を知るために host-kv へ退避させる形は採らない。
- **content-length はホストが所有する。** guest の `set-headers` / `replace` に content-length が含まれる場合は fail-closed で拒否(外部プロセッサ型の「不一致 = smuggling 面」という公式警告をそのまま不変則にする)。ETag は既存圧縮スライス([[000075]])と同じ弱化規則、`Vary` 相当の再計算もホスト側。

### 2. 公開 world は floor / ceiling の 2 つ、間はホストが格子(lattice)受理する

公開 world は **`filter`(floor: init / on-request / on-response)** と **`filter-body`(ceiling: + on-request-body + on-response-body)** の 2 つのみ。組合せ毎の world(4 面)は作らない。規範的受理規則を WIT コメントと conformance に固定する:

> コンポーネントは `filter` の全 export + **body hook の任意の部分集合**を export していれば受理される。ホストはロード時に各 optional export を名前で探針(`get_export_index` — 現行の `reads_body()` 検出の一般化)し、`BodyHooks { request: bool, response: bool }` として記録する。`filter` / `filter-body` は格子の両端であり、guest がバインディングを生成するための的であって、合法形状の列挙ではない。WIT が optional export を表現できるようになるまで、world 部分型判定はホスト側で実装する。

- buffer 判定は per-direction: route 上のいずれかのフィルタが `on-request-body` を export していれば request 側をバッファ(既存 [[000038]])、`on-response-body` を export していれば response 側をバッファ。**どちらも export しないフィルタしか居ない route は両方向とも zero-copy のまま**(P3: 不在は型であり続ける)。
- **「on-response-body のみ export」の conformance fixture を同梱する**(公開 world 名がどちらも指さない部分集合)。これが「格子が契約であって world 一覧が契約ではない」ことの機械検証になる。

### 3. 検査意味論: ヘッダ保持 + 厳格 fail-closed(response-body filter を持つ route のみ)

**ホストは response headers を body 判定が返るまで送出しない。** これが本設計の要石である — 先行拡張機構群の「部分検査で通す」「NUL 塗りつぶし」は、ヘッダ先行送出により phase 4 で拒否できない構造制約への妥協であり、経路全体を所有する Plecto が妥協ごと輸入する理由はない(柱 3)。

確定事実(契約・意味論):

- **リクエスト正規化**: 該当 route では upstream リクエストから `Accept-Encoding` / `Range` / `If-Range` を strip する。圧縮応答・206 を平常系から排除し、下の fail-closed を「稀な異常時の拒否」に保つ(帯域増はこの route の検査コストとして文書化)。
- **検査不能クラスは既定 502(fail-closed)+ 理由付き監査**: streaming content-type(`text/event-stream` 等)、`content-encoding != identity`(strip 後も残る場合)、`206` / `content-range`、content-length 無しの無限ストリーム。per-route の明示 opt-out(passthrough)を許すが、既定は拒否。silent スキップは作らない — `plecto_response_body_inspection_skipped_total{reason=...}` と access log に理由を残す。
- **over-cap は tri-state、既定 reject**: `reject`(502。response 側に 413 の語彙は使わない)/ `process-partial`(先頭 cap バイトのみ検査して通す。明示 opt-in)/ `passthrough`(明示 opt-in の fail-open 逃し弁)。
- **cap 既定 1 MiB・per-route 設定可・上限 16 MiB(request 側 [[000025]] を超えない)**。業界の response 検査上限は 64 KiB〜1 MiB に収まっており、複数 MiB 既定は前例のない外れ値になる。MIME 許可リスト(既定: text/plain, text/html, text/xml, application/json)を buffer 発動条件とし、**許可リスト判定は upstream から届いた as-received content-type で行う**(チェーン前段フィルタの header 編集で後段の検査を回避する chain-order bypass を封じる)。
- **guest 出力の長さ再検証**: `modified` / `replace` の body が cap を超える場合は fail-closed 502。guest が返す長さを無検証で信じた実装のクラッシュ CVE(CVE-2025-62504)をそのまま不変則に写す。
- **チェーン規則**: buffer は route で一度、変換結果を後段へスレッド(request 側と同型)。`on-response` が `replace` を返した場合、`on-response-body` は走らない(upstream body が存在しない)。`on-response-body` の `replace` はバッファ済み body を破棄する。trailers は v1 スコープ外(素通し)。

projected(実装スライスで確定):

- fast path 配線(response バッファリングの実装、readiness/metrics 統合)。
- **in-flight バイト予算の両方向統合**: 現行の request 側 `MAX_INFLIGHT_BODY_BUFFERS`(本数上限)と response 側を、方向合算の**単一バイト予算**に置き換える(cap × 本数 × 2 方向の掛け算を、選んだ 1 つの数に潰す)。

### 検討した代替案と却下理由

- **組合せ毎の 4 world(filter / filter-body / filter-response-body / filter-body-full)** — 一度は本 ADR の草案で採った形だが、同日の前例調査で撤回した(P10)。WIT は optional export を持たず(Component Model 1.0 ロードマップにあるのは optional **import**)、hook が増えるたび公開面と conformance 行列が 4→8(trailers)→16(streaming)と倍増する。ホストはどのみち export 探針を持つ(world は実行時オブジェクトではない)ため、world 列挙は表現力を何も足さない。却下。
- **単一 world + 強制 no-op export** — [[000038]] の発見(「全フィルタが body export を持つ → 全 route が buffer 税」)を契約側から再導入し、性能の根拠が契約の形から実装の中身へ転落する(P3 違反)。却下。
- **`capabilities() -> flags` の実行時交渉** — (i) component の型という真実源と二重化し、不一致は fail-closed 解決するしかないので宣言は冗長か誤りにしかならない。(ii) untrusted guest に「全 route の response を全量バッファさせる」ホスト資源レバーを渡す — [[000026]](bucket 仕様は host 所有)・[[000066]](config は operator 所有)が禁じた「guest が自分の制約を自己申告で緩める形」そのもの。(iii) 最も近い実在形(外部プロセッサ型のモード上書き)は buffer 非同期化による downstream ハング・多段切り詰めの実バグを 2026 年時点で抱えている。却下。
- **response 側も `continue(list<u8>)` で request 側と字面対称にする** — 支配的ユースケース(純検査)に二重コピー税を課す。字面の対称より意味の対称(P12): 「変えないなら運ばない」。却下。
- **streaming(`stream<u8>`)を待って response body を一度に解く** — wasip3 は Rust Tier 3、`plecto:filter-streaming` は fast path 未配線であり、待つ間 [[000037]] / [[000043]] の受け皿不在が続く。buffer-then-decide の v1 は WAF 実務の確立形であり、`list<u8>` → `stream<u8>` の差し替え座席は契約に予約済み([[000005]])。却下(streaming は別スライスのまま)。
- **検査不能クラスの silent スキップ(業界出荷既定への追従)** — 「幾分安全でない」と自認する妥協を、fail-closed を第一看板とする製品が新規に既定採用する理由がない。ヘッダ保持により Plecto はこの妥協を強制されていない。却下(per-route opt-out + 監査で運用自由度は残す)。

## Consequences

### Pros
- [[000037]](WAF)・[[000043]](AI/LLM gateway)の「フィルタで書ける」が response 側でも真になり、declined 判断群の受け皿が契約上成立する。reference filter 棚(Program F)に response 検査系(DLP / ガードレール)を追加できる。
- world 数を増やさずに hook を増やせる形が固定され、trailers / streaming の将来増分が公開面を爆発させない。
- 「ヘッダ保持 + 既定 fail-closed」は先行拡張機構群が構造的に持てない性質であり、柱 3(宣言された意味論)の実測可能な差別化になる。
- `%continue` の bare arm 化により、純検査フィルタの body 税が lift 一回分で済む([[000038]] の計測手法で回帰基線に載せられる)。

### Cons / Tradeoffs
- response バッファリングは該当 route のレイテンシ(TTFB)とメモリを確定的に増やす。cap 1 MiB × in-flight の予算はバイト予算統合(projected)まで二重掛け算のリスクが残る。
- `Accept-Encoding` strip は該当 route の upstream 帯域を増やす(検査のコストとして文書化)。ホスト側 decompression は将来増分(その時点で strip 既定を再評価)。
- 0.4.0 追加により host のアダプタ/バインディング系は 5 契約並走になる(0.1 / 0.2 / 0.3 / 0.4 + streaming 実験)。[[000064]] の互換ポリシー(2 リリース系列)を 0.1 / 0.2 に適用して整理する判断は別 ADR。
- 格子受理は「world 名 = 受理形状」という単純な説明を失う(規範はコメント + conformance fixture に移る)。
- **再検討条件**: (a) [[000020]] の wasi:http 収斂が成立した時点で、export 探針機構は `stream<u8>` の遅延読みに置換され本 ADR の受理規則は退役する(計画された取り壊し); (b) process-partial の実需(大容量 JSON API での部分検査要望など)が積み上がったら既定の再評価ではなく **per-route 設定の文書化強化**で応じる(既定は動かさない); (c) trailers を読む/書く実需が出たら格子への 3 bit 目として個別 ADR; (d) ホスト側 decompression(検査前伸長)の需要が strip の帯域コストを上回ったら別スライスで導入。

**(2026-08-09 追記)実装で確定した事項と、確定できなかった 1 件。**

実装スライスが本 ADR の規定を超えて決めたこと(いずれも fail-closed 側):
- **「content-length 無しの無限ストリーム」は独立クラスにせず over-cap へ写像した。** 事前に無限と判定する術が無いため、cap 到達時点で over-cap として扱い `reason="over-cap"` を記録する。既定は同じ 502 で、opt-in モードも自然に効く。決定 3 が 4 クラス目として列挙していた形は、機構上これ以外に取れなかった。
- **`process-partial` + `modified` は 502 で拒否する**(本 ADR 未規定)。前半だけ変換された body と未変換の後半を継ぎ合わせた表現は誰も意図していないため、送るより拒否が妥当と判断した。
- **バッファ経路では trailers が落ちる。** 本 ADR は「trailers は v1 スコープ外(素通し)」としたが、body を materialize してホストが re-frame する以上 trailer frame は保持できない(content-length との併存も不正)。検査しない経路では素通し、検査した body では脱落、という非対称が残る。
- **MIME 許可リスト外は skip として計上しない。** 許可リストは *buffer 発動条件* なので、リスト外は「検査不能」ではなく「宣言された検査スコープ外」と解釈した。画像 1 枚ごとにカウンタが回るのを避けるため。

**確定できなかった 1 件(要判断・未解決)**: **`Content-Type` を持たない応答は検査スコープ外として素通しする。** 許可リストが buffer 発動条件である以上の帰結だが、**upstream が `Content-Type` を落とせば response body 検査を回避できる**という穴が残る。本 ADR は chain-order bypass(as-received 判定)しか塞いでいない。厳格化(content-type 不在を検査不能クラスに含めて既定 502)は、204 / 304 や content-type を出さない API を既定で壊すため、実装スライスの一存では採らなかった。**DLP / PII 用途で upstream 自体を信頼しない脅威モデルを採るなら、この穴は塞ぐ必要がある**——次の再検討条件 (e) とする。
