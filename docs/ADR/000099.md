# 運用者向け出力（アクセスログ・トレース相関・upstream ヘルス・契約版）を契約として固定する

## Status

accepted — **実装済み**（2026-08-09）。決定 1〜6 すべてが入った: サブスクライバの `flatten_event(true)`、`docs/operations.md` のフィールド契約の節、`access_log::record` の無条件 `trace_id` / `span_id`、`plecto_upstream_instances` のスクレイプ時レンダリング、`--version` の契約版とロード時の 1 行、二系列バージョニングの `README.md` / `docs/operations.md` への移設。実装時に 2 点を ADR の文字より広く採った: (a) exposition のラベル値をエスケープする——upstream 名は manifest 由来の自由文字列で、これが exposition 初の動的ラベル値であり、引用符 1 つでスクレイプ全体が壊れる; (b) `.ja.md` の対応節も同時に更新する——パリティを検査する CI が無く、放置すると陳腐化する。

## Date

2026-08-08

## Affected Components

- fast path（`plecto-server`）— `access_log::record` の署名に trace context を通し、`trace_id` / `span_id` を無条件に出す。`metrics.rs` に `plecto_upstream_instances` ゲージを追加（スクレイプ時に `UpstreamGroup` を走査、持続カウンタなし）
- `plecto` バイナリ — `tracing_subscriber::fmt().json()` に `.flatten_event(true)` を設定。`--version` にロード可能な契約版を追加。フィルタロード時にバインドした契約版と isolation を 1 行ずつ出力
- docs — `docs/operations.md` にアクセスログのフィールド契約（型付き一覧）とアップグレード規則の節を新設。二系列バージョニングの記述を `CHANGELOG.md` から `README.md` / `docs/operations.md` へ移設

## Context

Plecto の運用者向け出力は、製品として外に出ている面の一部である。manifest スキーマ、CLI（[[000046]]）、`plecto:filter` WIT 契約（[[000071]] / [[000073]]）、ライブラリクレートは、いずれも「どう変わるか」の表明を持っている。**アクセスログだけがそれを持たない。** 本 ADR はこの非対称の是正と、それに連なる運用者向け出力の穴埋めを一括で扱う。

### 現況（コードから確認した確定事実）

- `crates/server/src/access_log.rs:21-39` の `record()` は `plecto::access` ターゲットに `tracing::info!` を 1 本出す（`[observability] access_log` の opt-in で、既定は無効）。フィールドは client / scheme / method / authority / path / status / duration_ms。意図的に秘密を持たず、path はクエリ文字列を落とす（`:18-20` にセキュリティ特性として明記）。設計としては正しい。
- `crates/plecto/src/main.rs:54-56` のサブスクライバは `tracing_subscriber::fmt().json().with_target(true)`。`flatten_event` を設定していないため、上記の HTTP フィールドは行の直下ではなく `"fields"` オブジェクトの中にネストされる。`tracing-subscriber` 0.3.23 の `src/fmt/format/json.rs:265-273` は、`flatten_event` が true のときイベントのフィールドを `timestamp` / `level` / `target` と同じ serializer マップへ直接書き込む（名前衝突のガードは無く、同名フィールドがあれば JSON のキーが重複する。現行のアクセスログのフィールド集合は衝突しない）。**ネストは JSON レイヤの既定の副産物であって、設計判断として選ばれたものではない。**
- `docs/operations.md` にアクセスログの節が存在しない（現在の見出しは Graceful shutdown / plecto healthz / readiness_grace_ms / Watching a drain / CI pre-flight / Reload vs restart のみ）。スキーマ文書もバージョンもフォーマット選択肢も無い。
- `crates/server/src/proxy.rs:74-79` は inbound `traceparent` をパースして `RequestTrace` を構築し、`:103` が `access_log::record(...)` を呼び、`:107-110` がサンプリングされたトランザクションの OTLP span を push する。**`trace` は同一関数のスコープに生きているのに、アクセスログには入らない。**
- `crates/server/src/metrics.rs:1-7` は依存ゼロを明示的な設計方針とし、`AtomicU64` の集合と固定バケットのヒストグラムを Prometheus text exposition v0.0.4 に手書きでレンダリングする。`:180-183` にある `plecto_requests_total{status_class="..."}` が、ヒストグラムの `le` を除けば露出全体で唯一のラベルであり、route ラベルも upstream ラベルも filter-ID ラベルも無い。
- **upstream の健康状態を示すメトリクスが存在しない。** ペシミスティック開始のアクティブヘルスチェックが fail-closed な 503 を駆動している（[[000017]]）にもかかわらず、露出しているのは 5xx クラスの集計と outlier ejection の累計カウンタだけで、どの upstream の何インスタンスが今落ちているかは分からない。
- `crates/server/src/listener.rs:127` の `ServerMetrics` は `Arc::new(ServerMetrics::new())` で 1 度だけ生成され、ArcSwap されるコンフィグの**外**でプロセス寿命を持つ。reload で作り直されない（[[000039]]）。
- `crates/plecto/src/main.rs:62-69` の `--version` は `plecto {version} (profile: {profile})` を出し、契約バージョンに触れない。`main.rs:154` の起動ログは listen アドレスと config version のみで、どのフィルタがどの契約版にバインドしたかを言う行が無い。一方 `crates/host/src/runtime.rs:287-330` のホストは、各フィルタがどの契約版にバインドしたかを正確に知っている（`FilterPreBinding::V01/V02/V03` → `BoundFilter::V01/V02/V03`）。**情報はホスト内にあり、運用者に出ていないだけである。**
- `CHANGELOG.md` の "Versioning policy (pre-1.0)" は、フィルタ契約が `plecto:filter@<version>` として独立にバージョンされ、ホストはサポートする全契約版をロードし続けると明記している。

### 一次データ（開発者調査 — Alt 本番運用フィードバック、2026-08-08）

1. **ログ転送層が plecto の行を汎用 Rust tracing 出力と自動判定し、型付きスロットが空のまま集計が沈黙した。** 運用者の転送層は plecto 用の明示マッピングを持たず自動判定に落ちた。plecto の行の形（`fields` がある / `timestamp` がある / `msg` が無い）が汎用 Rust tracing 出力の判定に完全一致し、method / status / response_size といった型付きスロットが埋まらないまま、集約側の正規化が発火しなかった。結果として集計は約 4 週間 0 行を返し、その間の調査 2 件がステータスコードとレイテンシの欠如で阻害された。
2. **トレースとログを結合できなかった。** 全リクエストを見る唯一のホップでありながら、「この遅いリクエストのトレースを出せ」に答えられなかった。ログ行とトレースを結ぶ ID が行に無いためである。
3. **アップグレード規則が読まれない場所にしか無く、セキュリティパッチが見送られた。** 運用者は 0.6.0 に固定され 0.6.1〜0.6.4 を見送った。うち 1 本は wasmtime のセキュリティパッチだった。理由は「プロキシのバンプにフィルタの再ビルドが要る」という誤解である。それを否定する方針は存在するが `CHANGELOG.md` にしかない——**壊れたときに読むファイルであって、上げるべきか判断するときに読むファイルではない。**

### 位置づけ

[[000029]] の native 採用基準 (i) は、横断的データプレーン関心事として **observability** を明示的に挙げている。本 ADR の全項目はこの基準の内側にあり、native fast path 側の責務として扱う。[[000009]] が定めた「メトリクスはホスト集約 / トレース文脈はホストが管理」という方式そのものは変えない。本 ADR が変えるのは、**ホストが既に持っている情報を運用者にどう出すか**であり、[[000009]] の Stage A 出力に運用契約としての表明を与える追補である。[[000046]] に対しては `--version` の出力内容を拡張する追補にあたる（同 ADR 決定 5 と 6——version は plain 出力・serving プロセスとは分ける——の線引きは維持する）。

一次データ 1 と 2 は、`CLAUDE.md` のコア原則「運用の単純さ」が製品の内側だけで満たされても、出力が運用者のパイプラインで意味を持たなければ達成にならないことを示している。一次データ 3 は同じことを配布面で示している。

## Decision

1. **JSON サブスクライバに `.flatten_event(true)` を設定し、HTTP フィールドを行の top-level に出す。** ネストは JSON レイヤの既定の副産物であって設計判断ではない。平坦化した行では method / status / duration_ms 等が `timestamp` / `level` / `target` と同じ深さに並び、一般的なログ取り込み層が型付きスロットへ写せる形になる（一次データ 1 の直接の是正）。
2. **アクセスログのフィールド一覧を型付きで `docs/operations.md` に公開し、フィールド集合を manifest スキーマ相当の契約として扱う。** 各フィールドの名前・型・意味・秘密を持たないこと（path はクエリ文字列を落とす）を明記する。フィールドの追加・改名は pre-1.0 のバージョニング方針の下で `CHANGELOG.md` の Changed に載せる。アクセスログを「安定性の表明がある運用者向け出力」の側へ移す。
3. **`access_log::record` に `trace_id` と `span_id` を追加し、サンプリング時のみでなく無条件に出す。** ID は下流でサンプリングされた何かとログ行を結合可能にし、サンプリングされなかった root でもトランザクションを一意に識別する。`RequestTrace` は既に同一関数のスコープにあり、追加の伝播経路を要さない（一次データ 2 の直接の是正）。
4. **`plecto_upstream_instances{upstream="…",state="healthy|unhealthy|ejected"}` ゲージを追加する。** probe が決める health ビットと outlier ejection は実装上**独立した二軸**であり（[[000032]]。probe-healthy かつ ejected があり得る）、`state` はこれを `ejected` > `unhealthy` > `healthy` の優先順で 1 値に畳む——各インスタンスがちょうど 1 系列に数えられ、系列の合計がインスタンス数に一致する。スクレイプ時に `UpstreamGroup` を走査してレンダリングし、**持続カウンタを持たない**。reload をまたいで持ち越す状態が無いため、reload 後は常に新鮮な値になる（`ServerMetrics` がプロセス寿命を持つ問題を、この系列については構造的に回避する）。カーディナリティは manifest に宣言された upstream 数と 3 状態の積で有界。ペシミスティック開始のアクティブヘルスチェック（[[000017]]）が駆動する fail-closed な 503 に、外から見える説明を与える。
5. **`--version` にロード可能な契約版を出す。加えて、ロード時にフィルタごとに 1 行、バインドした契約版と isolation を出す。** ホストは `FilterPreBinding` → `BoundFilter` の対応で既にこの情報を持っている。`--version` は「このバイナリが受け付ける契約版の集合」を、起動ログは「今この構成で各フィルタが実際に何にバインドしたか」を答える。両者は別の問いであり、両方要る。
6. **二系列バージョニングの記述を `CHANGELOG.md` から `README.md` と `docs/operations.md` へ移し、アップグレード規則として述べる。** すなわち、イメージ系列とフィルタ ABI 系列は独立であり、プロキシのバンプにフィルタの再ビルドは決して必要ない。置き場所が読者を決める——アップグレード可否を判断する運用者が読む面に置く（一次データ 3 の直接の是正）。

### 検討した代替案と却下理由

- **`[observability] access_log_format = "json" | "combined" | "json-flat"` のフォーマット選択肢を足す。** 運用者が既にパースできる形を要求できるようになる利点はある。しかし `combined` 等の要求は現時点で観測されていない。設定面とレンダラを投機的に増やすことになり、「不要な抽象化を入れない」に反する。フォーマット要求が要件として立ったときに再検討条件で受ける。却下。
- **`plecto::access` ターゲット専用のフォーマッタレイヤを付け、他の診断ログの形を変えない。** 既存のログパイプラインを壊さない利点があるが、「plecto のログは 2 つの形を持つ」という説明を恒久的に背負うことになる。pre-1.0 においてネスト形に安定性の表明をしていない以上、全体を平坦化して語彙を 1 つに保つ方が、運用者にも我々にも説明コストが低い。却下。
- **`plecto_requests_total` / `plecto_request_duration_seconds` に route ラベルを足す。** 運用者が最も欲しい内訳ではある。しかし `ServerMetrics` は reload をまたいでプロセス寿命を持つため、route ラベルのカーディナリティは「現行 manifest の route 数」ではなく「プロセス起動以降に存在した全 route 名の履歴」で有界になる。加えて route には今日名前が無く、`[route] name` の設計（必須か任意か、未設定時の扱い）を先に決める必要がある。今回は入れず、再検討条件に置く。却下。
- **行ごとに `schema_version` フィールドを出す。** コンシューマがスキーマで分岐できるようになるが、定数を全リクエストのすべての行で払うことになる。決定 2 のドキュメントと `CHANGELOG.md` の規律で同じ契約性が得られ、コストはゼロである。却下。

本決定は新しい設計原則を導入しない。[[000029]] 採用基準 (i) の内側で、[[000009]] が既にホストへ集めた情報に運用契約としての表明を与える。要点は「出力の形は実装レイヤの既定に委ねず、運用者向けの面として明示的に選ぶ」という一点である。

## Consequences

### Pros

- アクセスログが、安定性の表明を持つ運用者向け出力（manifest スキーマ / CLI / WIT 契約 / ライブラリクレート）と同じ扱いになり、製品の外向き面から非対称が消える。
- 平坦化された行が一般的なログ取り込み層の型付きスロットに写り、集計が沈黙する構図（一次データ 1）が解消する。
- `trace_id` / `span_id` により、全リクエストを見る唯一のホップがトレースとログの結合点になる。サンプリングされなかったトランザクションもログ行だけで一意に識別できる。
- `plecto_upstream_instances` により、fail-closed な 503（[[000017]]）に外から見える説明が付く。スクレイプ時レンダリングなので reload をまたいで陳腐化せず、カーディナリティは manifest で有界。
- 契約版の露出により、「このバイナリは何を受け付けるか」と「今この構成で何にバインドしたか」が別々に答えられる。
- アップグレード規則が判断時に読まれる面（`README.md` / `docs/operations.md`）に載り、セキュリティパッチの見送り（一次データ 3）と同じ構図が再発しにくくなる。

### Cons / Tradeoffs

- **平坦化はアクセスログ以外の全ログ行の形も変える。** pre-1.0 においてネスト形に安定性の表明はしていないが、既存の取り込み設定を持つ運用者には移行が発生する。移行を要する変更として `CHANGELOG.md` の Changed に載せ、`docs/operations.md` の新設節で新旧の形を明示する必要がある。
- **`timestamp` / `level` / `target` と同名のフィールドを将来足すと、JSON のキーが重複する。** `tracing-subscriber` 0.3.23 の実装は名前衝突をガードしないため、フィールド追加時の確認事項として恒久的に残る。現行のフィールド集合は衝突しない。
- 決定 2 でフィールド集合を契約にすると、以後の追加・改名が `CHANGELOG.md` の Changed に載る変更になる。軽い追加ができなくなる代わりに、運用者側の取り込み設定が壊れない。この取引を選ぶ。
- `plecto_upstream_instances` は持続カウンタを持たないため、スクレイプ間隔より短い健康状態の揺れは観測できない。状態の遷移そのものを数えたい要求が出たら別系列になる。
- `state` は独立二軸（probe health / outlier ejection、[[000032]]）を優先順で 1 値に畳むため、「probe-healthy だが ejected」のような組み合わせは系列から復元できない。軸ごとの内訳が要るなら別ラベルか別系列になる。
- 決定 5 の per-filter ロード行は、フィルタ数に比例して起動ログの行数を増やす。多数のフィルタを積む構成では起動時の出力が増える。
- **再検討条件**:
  - (a) **route ラベルと `[route] name` の設計** — 複数の運用者から per-route の内訳要求が出たとき。`ServerMetrics` のプロセス寿命とカーディナリティ、および route 名の必須／任意と未設定時の扱いを同じスライスで決める。
  - (b) **代替フォーマットの要求** — 平坦化 JSON では受けられない取り込み層の要求が具体的に立ったとき、`access_log_format` の設定面を再検討する。
  - (c) **`plecto_filter_*` の filter-ID ラベル** — 現在は host-aggregated（[[000009]]）であり、フィルタ単位の内訳は露出していない。フィルタ単位の内訳要求が出たとき、(a) と同じカーディナリティ論点の上で検討する。
