# 静的レスポンスヘッダを native `[route.headers]` に置き、宣言と rewrite ロジックの境界を native 採用基準に足す

## Status

accepted — **実装済み**（2026-08-09）。実装は「各出口でヘッダを押す」形ではなく、**route 確定後の区間を単一の出口に畳んだ**——post-route の処理を一つの `async` ブロックにまとめ、その唯一の出口で宣言を押してから compression を掛ける。これにより現在の 13 本の return パス（429、リクエスト chain の `short-circuit`、body hook の 400 / 408 / 413 / 503、circuit-open 503、no-healthy 503 の 2 経路、per-try / overall の 504、502、Upgrade 経路の各応答と 101、`respond_through_chain` の 3 出口）が構造的に網羅され、**将来追加される return も自動的に対象になる**。route 未確定の 2 経路（パス正規化拒否の 400、no-route の 404）は決定 3 のとおり対象外。

**（2026-08-09 追記）**決定 1 の fail-closed 検証に、ADR が名指ししていなかった 1 項目を実装時に加えた: **hop-by-hop ヘッダと `content-length` の宣言を拒否する**。manifest で宣言された framing ヘッダはレスポンス desync のプリミティブになり（CWE-444）、接続管理はトランスポートの責務である。同じ理由から、空の `[route.headers]` ブロックも拒否する（`upgrade.protocols` / `compression.algorithms` が非空を要求するのと同じ規律）。

## Date

2026-08-08

## Affected Components

- control plane（`plecto-control`）— `crates/control/src/manifest/route.rs` の `Route` に `headers`（`[route.headers]` = `set` / `remove`）を追加する。値はリテラルのみで、名前・値の妥当性検査は起動 / reload を fail-closed で止める
- fast path（`plecto-server`）— `crates/server/src/proxy.rs` のレスポンス側に、chain の後・compression の前という適用点を 1 つ設ける。そのルートに帰属する全応答（`Forward` / 合成 `Respond` / 転送側の 5xx）に掛かる
- extension plane（`plecto-host` / `plecto:filter`）— 契約変更なし。定数ヘッダを置くためだけのフィルタが不要になり、その分の `on-response` 境界越えが消える
- docs/ADR — [[000029]] が固定した native 採用基準に、(i)(ii) と並ぶ第三の但し書き（**manifest 上でリテラルとして尽きる宣言は rewrite ロジックではない**）を足す

## Context

[[000029]] は native fast-path の採用基準を **(i) per-request の filter decision では表現できない横断的データプレーン関心事**、**(ii) グローバルカウンタ** の二つに固定し、user-policy 形状の機能（auth / WAF / OPA / 複雑 authz / **rewrite ロジック**）は拡張面に留めて **native 化を明示的に declined** とした。この二分基準は「後続スライスが native へ滲み出す」のを止めるために置かれた load-bearing なルールであり、本 ADR はそれを緩めるのではなく、**基準そのものに但し書きを足す**。

**現状の穴。** `crates/control/src/manifest/route.rs` の `Route` は matcher / `filters` / `upstream` / `backends` / `strip_prefix` / `rate_limit` / `upgrade` / `compression` を持つが、**ヘッダを出力する側のフィールドを一つも持たない**（`[route.match] headers` はマッチ次元であって出力ではない。`crates/control/src/manifest/` に対する `set_headers` / `add_header` / `response_headers` の grep は空）。つまり運用者がレスポンスに定数ヘッダを 1 本足す方法は、現状フィルタを書く以外に無い。

**境界はすでに二度またがれている。** 同じ `route.rs` の doc コメントは、`strip_prefix` を「**host-native** な path rewrite」であり「`plecto:filter` の契約変更なしに」提供されるもの、と明記している——rewrite の形をしたものが既に一つ native にある。さらに `[route.compression]`（[[000074]] / [[000075]]）は native であり、**レスポンスボディそのものを変換する**。定数ヘッダ 1 本の付与は、ボディ変換より明確に侵襲が小さい。二分基準の文言（rewrite ロジックは拡張面）と、実際に native に置かれているものの間には、既にずれがある。

**一次データ（開発者調査、Alt 本番運用フィードバック、2026-08-08）。** ある運用者の**唯一の**フィルタが、定数 4 本のレスポンスヘッダを設定するためだけに存在していた。コード自体は 54 行である。恒久的なコストは Rust の側ではなく、**リポジトリと CI が背負う**もの——Rust ツールチェイン、同期を保つ必要がある vendored WIT のコピー、署名鍵、OCI レイアウト、そしてツールチェインが動くたびに変わる manifest 内の `sha256:` digest。二次的な効果として、それが唯一のフィルタだったため、その運用者の**フィルタ API に対する体験的評価の全体**が「本来フィルタであるべきでなかった一例」に色付けられた。

**契約側から見ても割に合わない。** `wit/world.wit` の `on-response` は `response-decision` を返す。定数ヘッダを設定するフィルタは、`init` の時点で完全に決まっている集合を、**リクエストごとに確保してコンポーネント境界を越えて持ち上げる**。この構造は入力に何も依存しておらず、per-request decision の形をしていない。

**適用点の下地は既にある。** `proxy.rs` の `respond_through_chain` はレスポンス側の規律として、route の chain を逆順に流し、compression を最後に掛ける（チェーン後段＝フィルタは常に identity を見る、[[000074]]。合成された `Respond` を意図的に compress しないのは [[000075]] 決定 1）。出口は三つ——フィルタ無しルート（`stream_response_direct` → `compression::apply`）、`Forward(edited)`（`stream_response` → `compression::apply`）、`Respond`（`http_response`、compression 無し）。`Respond` は**フィルタの `replace`（[[000073]]）と chain の fail-closed 5xx の両方**を指す。さらにこの関数の外にも合成応答があり、route 未確定の 404、429、400、および転送側から返る 502 / 503 / 504 が該当する。

本決定は [[000029]] の Fork（native / WASM 配置）に対する **amend** であり、コア原則の順序（機能網羅性は後位）と、deny-by-default / fail-closed / 運用の単純さの各テネットに従属する。

## Decision

1. **`[route.headers]` を native に入れる。** 形は `set = {…}` と `remove = […]` の二つ。**値はリテラルのみ**——条件分岐なし、リクエスト値の補間なし、正規表現なし。条件が一つでも要るものは per-request decision であり、拡張面の仕事である。

2. **適用点はレスポンス chain の後、compression の前。** 掛かる対象は**そのルートに帰属する全応答**——`Forward`、フィルタの `replace`、chain の fail-closed 5xx、429、502 / 503 / 504。運用者の宣言は**フロア**であり、フィルタにも障害時にも落とせない（`rate_limit` を「運用者の native な床」と呼ぶ [[000033]] と同じ語法）。

3. **route が決まる前の応答は適用外。** `proxy.rs` の no-route 404 と、その手前の path 正規化 400 は route が決まる前の応答なので、route に帰属する宣言を掛ける先が無い。**既知の穴として文書化**し、埋めない。

4. **[[000029]] の native 採用基準に第三の但し書きを足す: manifest 上でリテラルとして尽きる宣言は rewrite ロジックではない。** rewrite ロジックとは**入力に依存して出力が変わる計算**であり、それは per-request decision として拡張面に残る（[[000029]] の declined は不変）。この但し書きにより、基準は「宣言か計算か」で切れるようになり、機能網羅への滑りが止まる——条件式を一つでも足した瞬間に、それは計算であり native の適格を失う。

検討した代替案と却下理由:

- **リファレンス棚に host-config 駆動の `headers` フィルタを追加する（[[000068]] / [[000080]]）** — 署名鍵とゲストのビルドは運用者の手から消えるが、`[[filter]]` エントリ・OCI 参照・digest ピン・host-config ブロックは manifest に残り、リクエストごとの境界越えも残る。加えて棚への 1 本追加は、新 crate・ビルドスクリプト・CI の import floor アサーション・OCI 発行・署名・互換マトリクスの行を要する——**native 実装より安くない**。却下。
- **chain の前に適用してフィルタが上書きできる形にする** — 同名ヘッダを扱うフィルタと衝突しない利点があるが、運用者の宣言がフロアでなくなる。合成 `Respond` と chain の fail-closed 5xx にヘッダが乗らないため、**障害時にちょうどセキュリティヘッダが消える**。fail-closed の方向と逆。却下。
- **compression と完全に同じ規律にする（chain の後、合成 `Respond` には掛けない）** — レスポンス後段の規則が一つで済むが、上と同じ穴が残る。compression が合成応答を避けるのは、**host が framing を所有する小さな合成 body を圧縮する価値が無い**からであり（[[000075]] 決定 1）、その理由は定数ヘッダの付与に当てはまらない。規則の統一のために、理由の異なる制約を借りる必要が無い。却下。
- **値に条件や変数補間を入れる** — 表現力は上がるが、[[000029]] が止めようとした機能網羅への滑りそのもの。「宣言か計算か」の境界が消え、基準が再び曖昧になる。却下。
- **棚にフィルタを入れて native は 2 人目の運用者を待つ** — 証拠駆動の運用としては筋が通るが、**実装が 2 度になる**。同じ結論に 2 つの実装を出荷する理由が無い。却下。

## Consequences

### Pros

- 定数ヘッダのためだけに存在するフィルタが消え、そのとき運用者が背負っていた恒久コスト（Rust ツールチェイン・vendored WIT の同期・署名鍵・OCI レイアウト・ビルドのたびに変わる `sha256:` digest）が manifest の数行に置き換わる。
- 運用者の宣言が**フロア**として全応答に掛かるので、chain が fail-closed 5xx を返した瞬間や `replace` の合成応答でも、宣言したヘッダが消えない。障害時に消えないことがヘッダの価値そのものである種類の宣言（[[000073]] の `replace` 経路を含む）に効く。
- per-request の境界越えが 1 本減る。`init` の時点で決まっている集合を毎リクエスト持ち上げる構造が無くなり、ホット経路が軽くなる（コア原則「init と per-request を分離」）。
- [[000029]] の二分基準が「宣言か計算か」という**判定可能な形**を得る。`strip_prefix` が host-native な rewrite として既に置かれていること、`[route.compression]` がボディを変換していることと、基準の文言が整合する。
- フィルタ API の評価が「本来フィルタであるべきでなかった例」から切り離される。拡張面が引き受けるべきものだけを引き受ける形になる。

### Cons / Tradeoffs

- **route 未確定の 404 / 400 にヘッダが乗らない。** route が決まる前の応答であり、掛ける先が無い。listener 単位の宣言が必要になるまで、穴として残す。
- **運用者の宣言がフィルタの同名ヘッダを上書きする。** 予測可能であり、運用者が勝つのは deny-by-default の権限方向と一致するが、フィルタ作者にとっては驚きになりうる。
- ヘッダ名と値の妥当性検査を **fail-closed** で持つ必要がある。不正な名前 / 値で起動や reload を通してはならず、検査の分だけ control plane に責務が増える。
- 400 / 429 / 502 / 503 / 504 のうち、route が確定しているものにだけ掛かるという条件が、運用者から見て一様でない。どの合成応答が route に帰属するかを、実装スライスがドキュメントで明示する負債を負う。
- **再検討条件**: (a) 条件付きヘッダの要求が複数の運用者から出たとき——そのときの答えは**棚のフィルタ**であって native の条件式ではない（第三の但し書きを守る）; (b) listener 単位の宣言（404 を含む全応答に掛ける形）が要求されたとき; (c) リクエスト側のヘッダ宣言——今回は入れないが、同じ「宣言か計算か」の境界で別途判断する。
