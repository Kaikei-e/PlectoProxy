# serving で実行されない `[chain]` を manifest から fail-closed で拒否する

## Status

accepted — **実装済み**（2026-08-09）。`[chain] filters` の非空を無条件に拒否する検証、実行経路（`resolved_chain` と便宜 API 4 メソッド）の除去、`manifest/mod.rs` の doc コメント訂正、既存フィクスチャ 5 ファイルの per-route 移行、`CHANGELOG.md` の Changed / Removed までが入った。空の `[chain] filters = []` は決定 1 の「非空なら」に従い引き続き通る（テストで固定）。

## Date

2026-08-08

## Affected Components

- control plane（`plecto-control`）— manifest 検証（`crates/control/src/lib.rs:578-582`）が `[chain] filters` の要素 ID を loaded set に照合する形から、**非空であること自体を拒否する**形に変わる
- manifest — `[chain] filters` は宣言できなくなる。`crates/control/src/manifest/mod.rs:89-90` の doc コメントが約束している「route が自前の filters を持たないときのフォールバック」という記述を、実装どおり（フォールバックは存在しない）に訂正する
- CHANGELOG — pre-1.0 の破壊的 manifest 変更として Changed に載せ、移行先（各 `[[route]]` の `filters`）を明記する

## Context

manifest は `[chain] filters = [...]` を宣言できる。`crates/control/src/manifest/chain.rs:1-12` はこれを「The single ordered chain for v0.1（named chains / route matching are deferred to the fast-path server）」と定義しており、[[000007]] が単一宣言的 manifest を立てた時点での唯一のチェーン表現だった。[[000013]] が fast path と `[[route]]` を導入したとき、このフィールドは additive 互換のため据え置かれた。

問題は、**据え置かれたフィールドが「検証はされるが serving では決して実行されない」状態で残っていること**である。

- 検証は生きている。`crates/control/src/lib.rs:578-582` は `[chain]` の全フィルタ ID を宣言済み filter の集合に照合し、存在しない ID には `UnknownChainFilter` を返す。**運用者から見れば、このフィールドは検査されている＝生きている、と読める。**
- 解決も生きている。`crates/control/src/lib.rs:698-703` はそれを `ActiveConfig.resolved_chain` に解決する。
- しかし消費者が serving 経路に無い。`resolved_chain` を読むのは `crates/control/src/snapshot.rs:45,51` の `ConfigSnapshot::on_request` / `on_response`（同 `:153,160` の `Control::on_request` / `on_response` はここへ委譲する薄いラッパ）だけで、これはライブラリ利用者向けの便宜メソッドである。fast path は per-route の `dispatch_*`（`snapshot.rs:90,100,116`）しか呼ばない——`crates/server/src` に対する `.on_request(` / `.on_response(` の grep は空である。
- route 側にフォールバックも無い。`crates/control/src/route.rs:113-117` の `CompiledRoute::compile` は `r.filters` **のみ**から `resolved_chain` を組む。グローバル `[chain]` を prefix にも default にも使わない。
- そして「`[[route]]` があるときだけ無視される」のではない。`crates/server/src/proxy.rs:167-168` はルート未マッチを即 404 にするので、**ルートを 1 本も持たない manifest は 404 しか返さない**。つまり `[chain]` は serving バイナリにおいて**常に不活性**である。

さらに、doc コメント自身がこの誤読を後押ししている。`crates/control/src/manifest/mod.rs:89-90` は `chain` を「a route that names no filters of its own に使われる」と書いているが、上記のとおりコードはそう動いていない。**コードが守れない約束がドキュメントに残っている**（rfc-first-hrt の Transparent 違反）。

manifest の全 struct は `#[serde(deny_unknown_fields)]` であり、フィールド名のタイポは [[000046]] の `plecto validate` で確実に死ぬ。だがこの穴は構造上その検査に掛からない——`[chain]` は既知のフィールドで、値の参照検証まで通ってしまうからである。

一次データがこの形を裏書きする。開発者調査（Alt 本番運用フィードバック、2026-08-08）では、ある運用者が `filters = ["security-headers"]` を 15 ルート全部に繰り返して書いていた。`[chain]` はまさに、初見の運用者がその重複を DRY 化しようとして手を伸ばす形である。そのときに得られる報酬は、緑の `plecto validate`、清潔な起動、そして**本番全ルートでセキュリティヘッダ 0 件**である。既存の防御は散文 1 節（`docs/writing-a-filter.md:294`）だけで、実地では機能しなかった。

これは「設定ミスが静かに起きない」ことを売りにする製品における、静かな設定ミスの穴である。`CLAUDE.md` のコア原則のうち **fail-closed**（宣言したセキュリティ判断が黙って素通りしてはならない）と**運用の単純さ**（[[000008]] の静的宣言的 manifest は「書いたとおりに動く」ことで価値を持つ）に正面から反する。

## Decision

1. **`[chain] filters` が非空なら、無条件に validate エラーとして fail-closed に拒否する。** `[[route]]` の有無で分岐しない。serving バイナリでは常に不活性だからであり、条件付きにすると運用者が「いつ生きて、いつ死ぬのか」という例外を覚えることになる。拒否は静的検証（[[000046]] の `plecto validate`）と起動・reload（[[000039]]）の双方で効く。
2. **エラーメッセージは移行先を名指しする。** 「このフィールドは proxy に実行されない」「フィルタを各 `[[route]]` の `filters` に移せ」という二点を含む形にする。診断は「間違いを指摘する」だけでなく「次の一手を渡す」ものにする。
3. **`crates/control/src/manifest/mod.rs:89-90` の doc コメントを実態に合わせる。** route へのフォールバックは存在しない。**コードが守れない約束をドキュメントに残さない**（HRT の Transparent）。この訂正は拒否の実装と同一変更に含める。
4. **pre-1.0 の破壊的 manifest 変更として、移行注記付きで CHANGELOG の Changed に載せる。** サイレントな挙動変更ではなく、明示された非互換として扱う。

### 検討した代替案と却下理由

- **`[chain]` を全ルートの chain の prefix として尊重する** — 運用者の期待どおりに動き、一次データが示した「全ルートで同じフィルタを繰り返す」重複もそのまま解消される。魅力的な案である。ただしこれは manifest に新しい語彙を三つ増やす: chain 合成の順序（prefix か suffix か）、同じフィルタが prefix と route の双方に宣言されたときの扱い、per-route の opt-out。default chain が要件として立ったときに**独立した決定として設計するべき**もので、既存の不活性フィールドを黙って生かす形で滑り込ませるものではない。却下（再検討条件として残す）。
- **`[[route]]` が宣言されているときだけ拒否する** — 穴は小さくなるが消えない。ルート無しの manifest に `[chain]` を書いて起動すると、全リクエストが 404 になる一方で `plecto validate` は緑のままになる（`crates/server/src/proxy.rs:167-168`）。最も混乱する組み合わせが検査を素通りする。却下。
- **`Manifest.chain` フィールドごと削除する** — 最も単純で、`deny_unknown_fields` が自動で unknown field エラーを出すので専用のエラー型すら不要になる。ただしそのエラーは「そんなフィールドは無い」としか言えず、**移行先を名指しできない**。運用者は「どこへ移すのか」を自分で探すことになる。フィールドを残して専用診断を出す案（決定 1+2）の方が、同じ fail-closed 性を保ちながら移行コストが低い。却下。
- **散文の警告を強める** — 既に `docs/writing-a-filter.md:294` にあり、実地では機能しなかった（開発者調査）。**fail-closed な製品において、検証されるが不活性なフィールドの答えはドキュメントではない。** 却下。

本決定は [[000007]] の「単一の宣言的 manifest」と [[000013]] の「route 毎 inline chain への進化」を amend する。新しい設計原則は導入せず、`CLAUDE.md` の fail-closed を manifest 表面へ適用し直すものである。要点は、**manifest のフィールドは「検証される」か「実行される」かのどちらかであってはならず、両方であるか、拒否されるかのいずれかであるべき**という不変条件を立てたこと。

## Consequences

### Pros

- 「緑の validate ＋ 清潔な起動 ＋ セキュリティフィルタ 0 件」という組み合わせが構造的に成立しなくなる。fail-closed の主張が manifest 表面でも成り立つ。
- 診断が移行先を名指しするので、拒否に当たった運用者は次の一手（各 route の `filters` へ移す）を検索なしで得られる。
- 検証されるだけで実行されないフィールドが manifest から消え、[[000046]] の静的検証と serving 実体の乖離が一つ減る。`plecto validate` の緑がより強い保証になる。
- doc コメントの訂正で、`Manifest.chain` に関する「コードが守れない約束」が解消される（HRT の Transparent）。
- 拒否が無条件なので、運用者が覚える例外規則がゼロで済む。

### Cons / Tradeoffs

- **既存 manifest に `[chain]` を書いている構成はリロードが止まる。** fail-closed の意図どおりの挙動だが、アップグレード時に実作業（フィルタ ID を各 route の `filters` へ転記）が発生する。15 ルートの構成では 15 箇所への転記になり、重複そのものは解消されない。
- **チェーン便宜 API も同時に削除する。** `ActiveConfig` は `pub(crate)`（`crates/control/src/lib.rs:118`）なので公開構築できず、`Control::on_request` / `on_response` に到達する経路は manifest の `[chain]` **ただ一つ**である。したがって `[chain]` を拒否したうえでこれらを残すと、**到達不能な公開 API** が恒久的に残る——不活性なフィールドを消して不活性な API を残すのでは、本 ADR の目的が半分しか達成されない。削除するのは**実行経路だけ**である: `ActiveConfig::resolved_chain`・`ConfigSnapshot::on_request` / `on_response`・`Control::on_request` / `on_response`。`Manifest::chain` と `Chain` 型は**残す**——決定 2 が要求する「移行先を名指しする診断」は、フィールドを消すと `deny_unknown_fields` の "unknown field `chain`" しか出せず満たせない（同 Decision の却下済み代替案のとおり）。受理して拒否する経路を残し、実行経路を消す、が本 ADR の形である。`plecto-control` は crates.io に公開されているため公開 API の除去にあたり、pre-1.0 の minor bump として `CHANGELOG.md` の Removed に載せる（`cargo-semver-checks` はこの除去を検出する）。到達不能になる `ControlError::UnknownChainFilter` も同時に除去し、`[chain]` 拒否専用のエラーで置き換える。
  **（2026-08-09 追記）**本項は当初「便宜 API は残るが manifest から組み立てられなくなる」と書いていた。実装着手時に `ActiveConfig` が `pub(crate)` であることを確認し、その形では利用者が存在しえない（`ActiveConfig` を直接組む外部利用者は構築手段を持たない）と判明したため、削除に改めた。
- **既存テストの移行が必要になる。** `crates/control/tests/control.rs` / `reload.rs` / `oci_layout.rs` と `crates/control/src/manifest/filter_entry.rs` / `content_hash.rs` のフィクスチャが `[chain]` でマニフェストを組んでおり、いずれも per-route の `[[route]] filters` へ移す。テストが検証しているのはロード・reload・content hash・provenance であってチェーン形状ではないので、移行は機械的である。
- 一次データが示した重複（同じフィルタを全ルートに繰り返す）に対して、本決定は**何も解決しない**。穴を塞ぐだけで、運用者が `[chain]` に手を伸ばした動機は残る。
- **再検討条件**:
  - (a) **default chain**（全ルートに適用される prefix）が複数の運用者から要件として立ったとき — 却下した第一案を、合成順序・重複宣言時の扱い・per-route opt-out を含む独立した決定として設計し直す。
  - (b) **named chains**（[[000013]] が TOML キー衝突を理由に見送り、route の inline `filters` に落とした共有チェーン）が要件として立ったとき — このとき `[chain]` の名前空間をどう使うかを併せて決める。
