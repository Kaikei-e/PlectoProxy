# per-try timeout の per-route override を入れ、overall timeout の per-route 決定に実装を追従させる

## Status

accepted — **実装済み**（2026-08-09）。`[route.timeouts]`（`request_timeout_ms` / `overall_timeout_ms` をいずれも `Option`）、`CompiledRoute` への上書き値のコンパイル、`proxy_core` の post-route 区間での読み替え、`docs/operations.md` の解決順の節までが入った。「未設定」と「明示的に `0`」は `Option<Duration>` で区別され、`None` = upstream 既定を採る、`Some(ZERO)` = 明示的に無効、として E2E で固定されている（upstream 既定 60ms に対し、継承ルートは 504、`request_timeout_ms = 0` のルートは 200）。

## Date

2026-08-08

## Affected Components

- manifest — `[route.timeouts]`（`request_timeout_ms` / `overall_timeout_ms`）を新設。省略時は `[[upstream]]` の同名フィールドがそのまま効く（既存 manifest は無変更で動く）
- control plane（`plecto-control`）— `Route` に timeouts を追加し（今日は `crates/control/src/manifest/route.rs` にどちらのノブも無い）、compile 時に route の**上書き値**を compiled route に持たせる
- server runtime（`plecto-server`）— `proxy_core` の per-try / overall deadline の取得元を、upstream group から route の実効値へ切り替える。fault 値（per-try `upstream-timeout` / overall `request-timeout`）と fail-closed 504 は [[000031]] のまま不変

## Context

本 ADR は**新規要望ではない**。既に採択済みの決定に実装を追従させ、既に書かれていた再検討条件が一次データで発火した、その二つを同時に閉じるものである。

**(1) 採択済み決定と実装の乖離。** [[000031]] の Decision は overall timeout を **per-route** と明記し、検討した代替案の中で「overall を per-upstream に置く」を**明示的に却下**している。却下理由もそこに書かれている——operator が縛りたいのは *この route のリクエストの総時間*（client SLA 由来）であって upstream resource ではない、overall は per-route が自然であり、per-upstream の resource 保護は circuit breaker（[[000028]]）が担う、と。ところが**同じ ADR の frontmatter**（`affected_components`）は「manifest — `[[upstream]]` に `overall_timeout_ms`（既定 0 = overall 無し）を追加」と書いており、実装もそうなっている（`crates/control/src/manifest/upstream.rs` の `Upstream` フィールド）。Status はノブの置き場所に触れず「per-route override は deferred」とだけ述べるが、Decision の文脈でそれが指すのは **per-try** の override である（overall は最初から per-route と書かれている）。つまり **ひとつの ADR の中で Decision と frontmatter / 実装が食い違っている**。

**(2) 再検討条件の発火。** [[000031]] の再検討条件 (c) は literally 「per-try の **per-route override**」である。さらに遡ると [[000019]] は却下した代替案の中で「グローバル固定タイムアウト — 単純だが backend ごとに SLA が違う。per-upstream を採り、**per-route override は後続（必要になったら）**」と書いていた。本 ADR はその「必要になったら」に対する一次データを受ける。

**一次データ（開発者調査、Alt 本番運用フィードバック、2026-08-08）。** レイテンシ特性が本質的に異なるルートが同一 upstream を共有している。リモート画像を fetch・リサイズ・再エンコードするルートは、同一 upstream 上の素の REST 呼び出しより**長い**ヘッダ到達予算を正当に必要とし（そのハンドラ自身が既に 10 秒のデッドラインを持つ）、一方で素の REST 呼び出しは 30 秒の既定よりずっと速く失敗したい。今日この分割を表現する唯一の方法は、**タイムアウトを変えるためだけに同一アドレスの 2 つ目の `[[upstream]]` を宣言する**ことである。そうすると health プローバも複製されて同一コンテナへのプローブトラフィックが倍になり、1 つのバックエンドに対して circuit breaker（[[000028]]）が 2 状態に分裂する。

**今日の配置の確定事実。** `crates/control/src/manifest/upstream.rs` の `Upstream` が `request_timeout_ms`（既定 30000、`0` で無効）・`max_retries`（既定 1）・`overall_timeout_ms`（既定 0）・`circuit_breaker`・`outlier_detection` を全て保持する。`crates/control/src/manifest/route.rs` の `Route` にはこれらのどれも無い。`request_timeout_ms` がレスポンス**ヘッダ**到達までしか縛らない（ヘッダが着けばボディはデッドラインなしでストリームする）という [[000019]] の判断は streaming ルートを救っており、一次データでもストリーミング 8 ルートにタイムアウトを 1 つも設定せずに動いたと報告されている。この判断は本 ADR でも変えない。

**分離基準。** [[000034]] は backend を純粋な `{upstream, weight}` の対に保ち、per-route の方針は route に置くと定めた。`filters` / `strip_prefix` / `rate_limit` / `compression` が全て per-route なのはこの基準による。**タイムアウトはこの基準から取り残された唯一の方針である**。対して [[000028]]（circuit breaker）と [[000032]]（outlier detection）はバックエンドの性質を扱うので upstream 側で正しい。

関係する Tenet: **fail-closed**（超過は素通りさせず 504、不変）、**運用の単純さ**（設定を曲げるための upstream 複製をやめる）、**single-node first**。

## Decision

**(1) `[route.timeouts]` を新設し、upstream の同名フィールドを既定値として上書きする。** route に `request_timeout_ms`（per-try）と `overall_timeout_ms` を置く。どちらも省略可で、省略時は転送先 upstream の同名フィールドがそのまま効く。既存 manifest は変更なしで動く（非破壊・additive）。規則はひとつ——**upstream が既定を宣言し、route が上書きする**。

**(2) `max_retries` / `circuit_breaker` / `outlier_detection` は per-upstream のまま維持する。** [[000034]] の分離基準で、これらは backend の性質（このバックエンドにどれだけ負荷をかけてよいか、このバックエンドは壊れているか）に属する。

**(3) [[000031]] の Decision（overall は per-route）と実装の差分を本 ADR が閉じる。** ただし `[[upstream]].overall_timeout_ms` は**削除しない**——既定値の宣言場所として残す。こうすると per-try と overall が同じ規則ひとつ（upstream が既定、route が上書き）で説明でき、operator が覚える軸が増えない。

**(4) [[000031]] の runtime 規則「per-try と overall のうち厳しい方が勝つ」は維持する。** 解決後の実効値に対して同じ min 規則を適用するだけで、`overall ≥ per-try` の invariant 強制を新たに持ち込まない。

**検討した代替案と却下理由:**

- **per-try だけを override する（[[000031]] の再検討条件 (c) に厳密に留まる）** — 最小差分だが、閉じるのは乖離の半分だけ。overall が per-upstream にあるのは [[000031]] の Decision が**明示的に却下した配置そのもの**であり、放置すれば同じ ADR の中で決定と実装が食い違ったまま残る。却下。
- **`max_retries` も per-route にする** — retry 回数は「このバックエンドにどれだけ負荷をかけてよいか」であり、[[000034]] の分離基準では upstream 側に属する。加えて per-route の overall timeout が入れば、retry 列は route 側のデッドラインで既に縛られる（[[000031]] の再検討条件 (e) が指している方向）。却下。
- **`overall_timeout_ms` を `[[upstream]]` から削除して route へ移す** — [[000031]] の Decision には最も忠実だが、既存 manifest を壊す。既定値の宣言場所として upstream に残し route が上書きする形なら、**非破壊で同じ意味論に到達できる**。却下。
- **同一アドレスに 2 つ目の `[[upstream]]` を宣言する運用回避策を文書化する** — 設定変更ゼロで済むが、health プローバが複製されて同一バックエンドへのプローブが倍になり、1 つのバックエンドに対して circuit breaker が 2 状態に分裂する。設定で表現できない事実を運用の器用さで埋めさせる形になる。却下。

本決定は [[000031]] と [[000019]] を **amend** する（supersede しない）。二段 timeout の意味論・fault 値・fail-closed 504・`0 = 無効` のオプトアウトはいずれも継承し、変えるのは**ノブの置き場所**だけである。設計原則（安全 × 運用の単純さ）と矛盾しない。

## Consequences

### Pros

- レイテンシ特性の異なる route が同一 upstream を共有したまま、それぞれ正当な予算を宣言できる。タイムアウトを変えるためだけの upstream 複製が不要になり、health プローブの重複と circuit breaker 状態の分裂が解消する。
- [[000031]] の Decision（overall は per-route）に実装が追いつき、ADR 本文と設定形状の食い違いが消える。
- 既存 manifest は無変更で動く（additive）。upstream だけで足りる運用は今日のまま。
- タイムアウトが [[000034]] の分離基準に揃う——per-route の方針（`filters` / `strip_prefix` / `rate_limit` / `compression`）と同じ側に並び、backend は純粋な `{upstream, weight}` の対のまま。
- per-try と overall が同じ規則ひとつ（upstream が既定、route が上書き）で説明でき、operator が覚える軸は増えない。
- ヘッダ到達までしか縛らないという [[000019]] の判断を維持するので、streaming route は今日と同じくタイムアウト設定なしで動き続ける。

### Cons / Tradeoffs

- **同じノブが 2 か所に書けるようになる**（upstream が既定、route が上書き）。実効値が何になったかを運用者が読める形（`validate` 出力など）は**今回入れない**——設定を読んで頭の中で解決する負担が残る。
- **[[000031]] の Decision と frontmatter / 実装の乖離は、ADR 本文の内部整合を CI が検出できないことを示した。** ADR グラフ検査は辺（`amends` / `supersedes` / wikilink）の整合を見るが、Decision 本文と実装の一致は見ない。同種の乖離は今後も静かに入り得る。
- ノブの総数は増えないが、解決順序（route → upstream 既定）という新しい概念がひとつ増える。
- **（2026-08-09 追記）実効値の解決は compile 時ではなく転送時になる。** 本 ADR の `affected_components` は当初「compile 時に upstream 既定と route 上書きを解決した実効値を `CompiledRoute` に載せる」と書いていたが、これは [[000034]] の weighted traffic split と両立しない——ひとつの route が既定値の異なる複数の upstream にまたがりうるため、どの既定が効くかは重み付き選択の**後**にしか決まらない。したがって compile 時に持つのは route の**上書き値**（`Option<Duration>` 2 本）であり、`override.unwrap_or(group の既定)` を転送時に評価する。Decision 本文（「upstream が既定を宣言し、route が上書きする」）はそのまま満たされ、変わるのは解決の**時点**だけである。
- **manifest の content hash が全構成で動く。** `Route` に `Option` フィールドを足すと直列化形が変わるため、アップグレード後の初回起動で reload が 1 回余分に走る（[[000100]] の `headers` フィールドでも同じことが起きている）。それ以外の影響は無い。
- **[[000031]] には本 ADR が閉じない乖離がもう一つ残る。** 同 ADR の Decision は `overall >= per-try` の invariant を「manifest 検証で強制し、違反は reload を拒否する」と定めるが、Status は「強制せず runtime で厳しい方が勝つ（min）」と述べ、実装は後者に従っている。本 ADR の決定 4 は実装側（min）を維持する立場を取るので運用上の齟齬は生まないが、**Decision 本文が要求する fail-closed な検証は依然として存在しない**。per-route 上書きが入ると同じ invariant を route と upstream の組み合わせで評価することになるため、実装スライスでどちらに寄せるかを明示的に決める必要がある。
- **再検討条件**：(a) **connect timeout の独立化**（[[000031]] の再検討条件 (a)、未回収のまま）；(b) ヘッダ到達**後**の **idle / stream timeout**（同 (b)。[[000019]] が残したボディ途中の hang の穴は今も開いている）；(c) **デッドライン残量を retry 判断へ渡す連携**（同 (e)。残予算が per-try を下回るなら最後の試行を打ち切る）。
