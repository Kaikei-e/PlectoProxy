# trusted proxy 配下でのクライアント同一性復元を X-Forwarded-For 限定・trusted CIDR 必須で入れる

## Status

accepted — **実装済み**（2026-08-09）。`[listen.trusted_proxy] trusted` の manifest 面（CIDR パースと containment は [[000057]] の実装と共有）、`set_forwarded` での復元と解決済みクライアントの返却、その値をアクセスログ・per-client レートリミット・source-IP ハッシュの三点へ通す配線、`docs/hardening.md`（PROXY v2 が第一選択である旨）までが入った。走査要素数の上限は 32 で、超過時は解決済みアドレスへ倒す。

## Date

2026-08-08

## Affected Components

- server runtime（`plecto-server`）— `set_forwarded`（`crates/server/src/headers.rs`）に trusted-proxy 判定を挿す。trusted CIDR 内の peer のときだけ inbound `X-Forwarded-For` からクライアント IP を復元し、それ以外は現行の無条件上書きを維持する
- control/manifest — `[listen.trusted_proxy]` に `trusted = [...]` を新設。宣言があるときのみ復元経路が有効になる（deny-by-default）

## Context

[[000022]] は Cons の **再検討条件 (a)** に、次の一文をそのまま残していた:

> **trusted-proxy（追記）モード** — 信頼ホップ構成で受信 `X-Real-IP` / `CF-Connecting-IP` 等を尊重するか、family ごと設定可能化する（[[000018]] の再検討条件 (a) と統合）

本 ADR はこの再検討条件の発火である。

コード側にも同じ繰り延べが記録されている。`crates/server/src/headers.rs` の `set_forwarded` の doc コメントは、trusted-proxy の *append* モード（Plecto が別の LB の背後にある場合）を後のスライスに deferred とし、overwrite が安全な既定であると明記している。実装はその宣言どおりで、`set_forwarded` はクライアント供給の転送 / client-IP ヘッダを全て drop し、接続 peer から `X-Forwarded-For` と `X-Real-IP` を、ワイヤの scheme から `X-Forwarded-Proto` を**無条件に**設定し直す。

前段が L4 の場合、この穴は [[000057]] が（TCP listener の範囲で）閉じている。PROXY protocol v2 の受信により、クライアント同一性は **HTTP の下**で復元される。これにより per-client-IP レートリミット、source-IP ハッシュ、`X-Forwarded-*` の再発行、アクセスログの意味論が、N レプリカ構成でも宣言どおりに保たれる。

残っているのは **L7 前段**である。[[000056]] は trusted-hops モデル（`X-Forwarded-For` を N ホップ分信頼して剥く）を却下しており、その理由は「HTTP ヘッダ層での復元は、ホップ数の設定ミスがそのまま偽装可能性になり、[[000018]] の『inbound XFF は無条件に剥がす』という単純さを壊す」というものだった。この却下理由はホップ**数**という判定軸に対して正しい。本 ADR はこの却下を覆すのではなく、**射程を限定する** — ホップ数ではなく trusted **CIDR** で判定する形なら、設定ミスは偽装可能性ではなく復元の失敗（安全側）に倒れる。CIDR 判定は「誰が接続してきたか」で決まるからである。

クライアント IP に依存する機能は既に二つ着地している: [[000033]] の per-client-IP レートリミットと、[[000035]] の source-IP ハッシュ。どちらも「クライアントが誰か」が peer に潰れると意味論が崩れる。

一次データ（開発者調査、Alt 本番運用フィードバック、2026-08-08）: ある運用者は、TLS を終端して平文 HTTP を転送する別のプロキシの背後で Plecto を動かしている。その脚では PROXY v2 が使えないため、クライアント同一性が失われる。per-client レートリミットも source-IP ハッシュも前段プロキシのアドレスをキーにして動き、アクセスログもそれをクライアントとして記録する。

## Decision

1. **`[listen.trusted_proxy] trusted = [...]` を宣言したときのみ有効。** 宣言が無ければ現行どおり無条件上書きで、復元経路は存在しない（deny-by-default）。[[000057]] の `[listen.proxy_protocol]` と同じ「宣言なしに信用しない」形を踏襲し、**キー名も同じ `trusted` に揃える**——`[listen]` ブロック全体で「誰を信頼するか」の語彙を一語に保つ。CIDR 表記のみ受理し、裸 IP は validation error（[[000057]] と同じ規則）。本 ADR とドキュメントでの例示には private CIDR（例: `10.0.0.0/8`）または文書用アドレスブロックを用いる。

2. **判定軸は `set_forwarded` が受け取る解決済みアドレスである。** そのアドレスが trusted CIDR に**属するときに限り** inbound `X-Forwarded-For` を読み、右から trusted な要素を落として、最初の非 trusted な要素をクライアント IP とする。属さなければ現行どおり全て剥がして再発行する。「解決済み」とは、[[000057]] の PROXY v2 受信が有効ならその復元後のアドレス、無効ならワイヤ上の接続 peer、という意味である（Cons の 2026-08-09 確定を参照。この一つの規則が PROXY v2 の有無で自動的に正しい側へ倒れる）。

3. **対象は `X-Forwarded-For` の 1 family のみ。** 他の client-IP variant（[[000022]] が剥がし family へ加えたもの）は復元源にしない。これらを trusted 構成で尊重するかは [[000022]] の再検討条件 (a) の**残余**として開いたままにする（本 ADR が (a) を満たすのは `X-Forwarded-For` の 1 family についてのみ）。

4. **復元後も現行どおり Plecto が `X-Forwarded-For` / `X-Real-IP` / `X-Forwarded-Proto` を発行し直す。** [[000018]] の edge モデルは変えない — 復元は「誰がクライアントか」の決定にのみ使い、下流に渡すヘッダは常に Plecto の権威ある値である。前段が付けたヘッダをそのまま通過させることはしない。

5. **フォールバックは常に peer。** `X-Forwarded-For` が空・不正・全要素が trusted、のいずれの場合も peer にフォールバックする。復元できないときは偽装できない側に倒す。

6. **ドキュメントでは PROXY v2 を第一選択として明記する。** 本モードは PROXY v2 を喋れない L7 前段のための第二の答えと位置づける。HTTP の下で同一性を復元できるなら常にそちらが強い。

検討した代替案と却下理由:

- **trusted-hops モデル（N ホップ分信頼して剥く）** — [[000056]] の却下理由がそのまま当たる。ホップ数の設定ミスが偽装可能性に直結する。CIDR 判定は「誰が接続してきたか」で決まるので、設定ミスは復元の失敗に倒れる。却下。
- **PROXY v2 のみを答えとし、HTTP ヘッダ層での復元は declined のまま維持する** — L4 前段には正しく、[[000018]] の単純さも守られる。ただし PROXY v2 を喋れない L7 前段に答えが無い状態が残り、その構成では per-client レートリミットと source-IP ハッシュが前段のアドレスに対して動き続ける。一次データが示すのはまさにこの構成であり、維持は選ばなかった。
- **client-IP variant を family ごとに設定可能にする** — [[000022]] が既に「列挙の tail は際限がなく、広く使われる主要ヘッダに絞るのが現実的」として却下している。今回もその判断を維持する。復元源を 1 family に絞ることで、trusted 経路で読む untrusted 入力の面も 1 つに留まる。
- **inbound `X-Forwarded-Proto` も尊重する** — 前段が TLS を終端している構成では実用的だが、scheme をワイヤの真実として扱う現行の性質（[[000018]]）を崩す。今回は入れず再検討条件に残す。

本決定は [[000018]] の edge 既定と [[000022]] の family 拡張を、trusted CIDR 宣言下の 1 family に限って amend する。設計原則（安全 × ポータビリティ × セルフホスト性 × 運用の単純さ）との整合: 既定は変わらず安全側、有効化は明示宣言のみ、復元不能時は fail-closed 相当（peer へ後退）、復元源は 1 family に限定。

## Consequences

### Pros

- PROXY v2 を喋れない L7 前段の背後でも、per-client-IP レートリミット（[[000033]]）と source-IP ハッシュ（[[000035]]）とアクセスログが実クライアントに揃う。一次データが示した構成に答えが出る。
- 判定軸が peer アドレスなので、設定ミスの倒れる先が「復元の失敗」であり、偽装可能性ではない。[[000056]] が trusted-hops を却下した理由に抵触しない形になっている。
- 宣言が無い既定の挙動は 1 バイトも変わらない。現行デプロイに対する挙動変化はゼロ。
- 下流に渡すヘッダは復元の有無にかかわらず Plecto の発行値であり、[[000018]] の edge モデル（フィルタも upstream も Plecto の確定値だけを見る）は不変。フィルタ契約（`plecto:filter`）も不変。

### Cons / Tradeoffs

- **trusted CIDR を広く取りすぎると偽装可能になる。** CIDR の範囲は運用者の責任であり、狭く取りすぎた場合は復元が起きない（安全側）だけで済む。非対称なので、運用ガイドは「疑わしければ狭く」と書く。
- 前段が TLS を終端している構成では、`X-Forwarded-Proto` が依然としてワイヤの scheme を反映する。前段までが `https`・Plecto の脚が平文 HTTP なら、下流には `http` が渡る。
- 復元の有無で per-client レートリミットと source-IP ハッシュのキーが変わるため、モードを切り替えると既存のバケットとハッシュ割り当てが不連続になる。切り替えは無停止だが、意味論としては別のキー空間へ移る。
- trusted 経路では inbound `X-Forwarded-For` という untrusted 入力のパース面が一つ増える（現行は読まずに捨てているだけ）。要素数・長さの上界とデータプレーン panic 禁止は実装スライスの必須制約とする。
- `[listen.proxy_protocol]`（[[000057]]）と併用したとき、`set_forwarded` が受け取る peer は既に PROXY v2 で復元済みのアドレスである（[[000057]] は `set_forwarded` を復元 peer の消費点として明記している）。
  **（2026-08-09 確定）**判定軸は**復元後のアドレス**とする。ワイヤ上の L4 peer には戻さない。この選択は両方の構成で正しく畳める: (a) L4 前段が PROXY v2 を喋る構成では復元後の peer が実クライアントになり、それは trusted CIDR に属さないので XFF 復元は起きない——同一性は既に HTTP の下で復元済みなので、これが正しい挙動である（inbound XFF は従来どおり剥がされる）。(b) PROXY v2 を喋れない L7 前段の構成では peer が前段のアドレスのままなので trusted CIDR に属し、XFF 復元が働く。つまり「復元済みアドレスで判定する」という一つの規則が、PROXY v2 の有無で自動的に正しい側へ倒れる。実装は `set_forwarded` の引数を単一の「解決済みクライアント候補」として扱い、その上流で誰が解決したかを問わない。
- **再検討条件**: (a) inbound `X-Forwarded-Proto` の尊重; (b) 他の client-IP variant を trusted 構成で復元源にするか（[[000022]] の再検討条件 (a) の残余）および列挙の tail（同 (b) を継続）; (c) RFC 7239 `Forwarded` の発行・受理（[[000018]] から継続）。
