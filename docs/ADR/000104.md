# plecto:filter@0.4.0 に path-with-query 改名を含め、wasi:http 収斂の時間軸を一次ソースで訂正する

## Status
accepted — **実装済み**（2026-08-09）。決定 1（`http-request.path` → `path-with-query`）は [[000098]] の契約レール・スライスに同乗して着地。決定 3（[[000098]] の発効日訂正）と決定 5（レスポンス経路の doc コメントを能力先行へ書き換え、`replace` の合成レスポンス・レシピを `docs/writing-a-filter.md` に追加）も着地。決定 2（アクセスログ側の `path` は改名しない）は現状維持として成立している。決定 4（decision variant の収斂を未解決として記録すること）は本 ADR の本文がそれ自体を果たしている。

## Date
2026-08-08

## Affected Components
- wit / host / fast path / docs — 上記 frontmatter のとおり。本 ADR は「確定事実」（一次ソースで裏取りした外部状態、現行契約の形、改名の判断）と「projected」（収斂の時間軸、decision variant の写像）を本文で区別する（[[000098]] と同じ規律）
- docs/ADR — [[000098]] Context の外部前例節、および [[000020]] の収斂ゲートへの dated 訂正

## Context

### 外部事実の訂正（取得日 2026-08-08、一次ソースで再確認。2026-08-09 に再取得しても結果は不変）

[[000098]] の Context は外部前例の節で「`wasi:http@0.3.0`（2026-06-11 発効）」と書いた。同日に一次ソースへ当たり直したところ、この記述は誤りであることが確定した。

確定事実:

- `WebAssembly/WASI` リポジトリは **v0.3.0 を 2026-06-11 に公開**している。
- `WebAssembly/wasi-http` リポジトリは **0.3.0 を未公開**である。0.3 系の最新タグは `v0.3.0-rc-2025-09-16`（2025-09-16 公開）で、リポジトリ全体の最新リリースは 0.2 系の `v0.2.8`（2025-10-07）である。`main` の `wit/` ディレクトリのパッケージ宣言は `wasi:http@0.2.8` であり、0.3 系は `wit-0.3.0-draft/` ディレクトリにあって、そのパッケージ宣言は `wasi:http@0.3.0-rc-2025-09-16` である。
- したがって [[000098]] の当該記述は、**WASI コアの発効日を wasi-http に付け替えたもの**である。**2026-08-08 時点で wasi:http 0.3.0 は未発効**である。ただし「rc から一切動いていない」わけではない — 版名は `0.3.0-rc-2025-09-16` に据え置かれたまま、`wit-0.3.0-draft/` の中身は更新されており、下で引く `service` / `middleware` / `handler` の形は **2025-10-23 の world 再設計で入った**（draft ディレクトリの最終更新は 2025-11-03、リポジトリの最終 push は 2025-11-25）。**タグは 11 か月、draft の中身は 9 か月動いていない**というのが正確な状態である。
- [[000098]] の他の記述は draft の型としては正しく、訂正は日付と発効状態に限られる — `service` / `middleware` world の response body が `stream<u8>` + `future<trailers>` であること、「読まない」がゼロコストなので hook の有無という概念が消えること、`response` の headers が immutable で変更は新 response の構築になること、はいずれも維持する。

### `wit-0.3.0-draft/worlds.wit` の実体（同日、同一次ソース）

同ディレクトリの world 定義は、`middleware` が `handler` を **export かつ import** する形であり、`handler` の唯一の関数は `request` を受けて `result<response, error-code>` を返す **async** 関数である。

ここから 3 点が確定事実として読める:

1. `request-decision` / `response-decision` に相当する型が無い。**ハンドラは response を返すのであって decision を返さない。**
2. `handle` は **async** である。
3. middleware は次段の `handler` を import するので、「変更せず続行」は guest が import 経由で次段を呼ぶ形になる。**ホストは型レベルでも実行時にも「何も変わっていない」を知らされない。**

3 は本プロジェクトにとって単なる語彙の違いではない。[[000038]] のゼロコピー素通しも [[000098]] が `%continue` を素のアーム（payload なし）にした判断も、「読まない / 変えない」をホストが型から先に知れることに依拠している。収斂はその前提を構造的に消す。

### 現行契約における `path` の二義性（確定事実）

- `wit/world.wit:25-26` — `http-request.path` は「path including query, e.g. "/api?x=1"」と文書化されている。フィルタは判断のためにクエリを見る必要があるので、これは正しい選択である。
- `crates/server/src/access_log.rs:18-20` — アクセスログは意図的にクエリ**無し**のパスを出し（`proxy.rs` が `uri.path()` を捕まえる）、それをセキュリティ特性として述べている。運用ログにクエリを漏らさないので、これも正しい選択である。
- つまり**同じ名前が 1 ホップ違いで 2 つの意味を持っている**。どちらの選択も正しく、正しくないのは共有された名前だけである。

### レスポンス経路が能力を語っていない（開発者調査、Alt 本番運用フィードバック、2026-08-08）

現行契約はレスポンス側の合成能力を確かに持っている:

- `wit/world.wit:62-73` — `response-decision::replace(http-response)` が存在し、上流レスポンスを破棄して**ボディ付き**の合成レスポンスを送る（`http-response.body: list<u8>` は `:33-37`）。
- `wit/world.wit:187-188` — `on-response` の doc コメントは「`resp.body` is always empty (header-only): the upstream body streams zero-copy past the chain … `replace` SYNTHESISES a body, it never reads one」。
- `wit/world.wit:68-71` — `replace` 自身の doc コメントは「Distinct from the request side's `short-circuit`: nothing is short-circuited here …」。

**どちらの doc コメントも正確だが、どちらも不変条件と「その機構が何で*ない*か」の話であり、ユースケースを述べていない。**

一次データ: 注意深い読者が、自分が vendored した 0.3.0 の**同じファイルの 20 行下**にある `replace` を見落とし、「フィルタは上流のレスポンスボディを書き換えられない」から「上流のステータスに応じた合成レスポンスは不可能」と結論して、本番の accepted regression として記録した。原因は、レスポンス経路の doc コメントが全て否定形で始まり、能力を述べていないことである。「レスポンスボディを変えられるか」を探す読者は "header-only" と "always empty" に先に当たって読み止まる。契約の欠落ではなく、記述順の帰結である（P3 が「判断は型で」を要求するなら、その型が何を可能にするかは型の隣で読めなければならない）。

### 0.4.0 の現在のスコープ（確定事実）

[[000098]] の 0.4.0 は `filter-body` world に `on-response-body` を足すものであり、基底の `filter` world は無変更である。**したがって現在の 0.4.0 は、ヘッダのみのゲストにとって非破壊のバンプである。** 本 ADR はこの性質を意図的に手放す。

## Decision

### 1. `http-request.path` を `path-with-query` に改名し、0.4.0 のスコープに含める

これにより 0.4.0 は基底 `filter` world のゲストにとっても**ソース破壊的**になる。これを受容する。ロード時アダプタにより 0.1 / 0.2 / 0.3 のデプロイ済みコンポーネントは従来どおり動く（[[000064]] の互換ポリシー、[[000071]] / [[000073]] のレール）。

根拠は機会費用である。破壊的バンプは 0.4.0 で**既に開いている**（[[000098]] の `request-body-decision` 同形化）。1.0 の後にこの改名を行うことは実質不可能になるので、いまが唯一安い機会である。

綴りは **`path-with-query`** を採る。`path-and-query` ではない。[[000020]] が `wasi:http` への収斂を committed な方向として置いている以上、改名先は収斂先の語彙に揃える——draft の `request` リソースは同じ概念を `get-path-with-query` / `set-path-with-query` と命名している（取得日 2026-08-09、一次ソース `wit-0.3.0-draft/types.wit`）。前置詞 1 語ずれた名前を選べば、収斂時にもう一度改名することになり、「いまが唯一安い機会」という本項自身の論拠と衝突する。Rust の URI 型が同じ概念を `path_and_query` と綴ることは承知しているが、本契約の収斂先はそちらではない。

### 2. アクセスログ側の `path`（クエリ抜き）は改名しない

**名前が違うこと自体が意味の違いを表す**形にする。契約は「クエリを含む判断材料」を `path-with-query` として、運用ログは「クエリを含まない出力」を `path` として、それぞれ自分の名前で宣言する（P12）。二つの正しい選択が一つの名前を共有する状態を、名前の分岐で解消する。

### 3. [[000098]] Context にある wasi:http の発効日を訂正する

確定事実: **wasi:http 0.3.0 は 2026-08-08 時点で未発効**である。

projected: [[000020]] の収斂の時間軸は、WASI コアの発効ではなく **wasi-http 自身のリリース**に従属する。[[000098]] の再検討条件 (a) が言う「収斂が成立した時点」は、本 ADR 以後、wasi-http が 0.3.0 を実際にリリースした時点を指す。

### 4. decision variant が収斂をどう生き延びるかを、未解決として明示的に記録する

上記 `middleware` world の 3 点から、収斂は「無かった語彙の獲得」ではなく **fast path の前提の入れ替え**である。ハンドラが decision ではなく response を返し、次段呼び出しが guest 側の import になる以上、[[000038]] のゼロコピー素通しと [[000098]] の `%continue` bare arm が守っている性質（ホストが「何も変わっていない」を型で知れること）を手放す判断を伴う。

**その判断は本 ADR では行わない。** ここで行うのは、それが未解決であることを台帳に載せることだけである。これは [[000098]] の再検討条件が扱う export 探針格子の引退（`stream<u8>` の遅延読みに置換される、計画された取り壊し）**とは別の問題**である。前者は機構の置換、後者は宣言された意味論の可否である。

### 5. レスポンス経路の doc コメントを能力先行に書き換える

不変条件（`resp.body` は常に空、上流ボディはゼロコピーで素通しされる、`replace` は合成であって読み取りではない）は残すが、**先に何ができるかを述べる**。加えて、上流のステータスに応じてボディ付きの合成レスポンスを返すレシピを `docs/writing-a-filter.md` に実例として追加する。これは `replace` が存在する正典的な理由であり、現在どこにも文書化されていない。

### 検討した代替案と却下理由

- **改名せず doc コメントで差異を明示する** — 0.4.0 をヘッダのみゲストにとって非破壊のまま保てる。しかし名前が 1 ホップ違いで 2 つの意味を持つ状態を凍結することになり、1.0 の後の改名は実質不可能になる。却下。
- **WIT の record にエイリアスを足して両方の名前を出す** — 移行期に両方の名前で読めれば破壊を回避できるが、WIT にその機構が無い。却下。
- **アクセスログ側の名前を契約に揃える** — 名前の衝突自体は解消するが、運用者向け出力の語彙を契約に従属させることになる。依存の向きが逆である。却下。
- **0.4.0 を「契約の棚卸し」にして、フィルタが `init` で静的なレスポンスヘッダ貢献を宣言する経路も同時に入れる** — 破壊の回数を最小化できるが、静的ヘッダの用途は fast path 側の宣言的な仕組み（[[000100]] の `[route.headers]`）が引き取ったので、契約側で急ぐ理由が無くなった。契約は必要になったときに動かす。却下。
- **本 ADR で収斂の可否そのものを決める** — 一次ソースはタグが rc のまま 11 か月、draft の中身も 9 か月動いておらず、決める材料が揃っていない。決めないことを決めて、材料が揃う条件を再検討条件に書く方が正直である。却下。

## Consequences

### Pros
- `path-with-query` は名前が中身を宣言する（P12）。契約と運用ログの語彙が 1 ホップ違いで衝突する状態が、両者の名前を分けることで解消する。
- 改名の破壊コストが、既に開いている 0.4.0 の破壊的バンプに相乗りする。破壊の**回数**は増えない。
- 外部事実の訂正が一次ソース付きで残り、[[000020]] の収斂ゲートが「WASI コアが出た」ではなく「wasi-http が出た」で判定されるようになる。誤った日付に基づいて収斂スライスを前倒しする芽を摘む。
- decision variant の収斂リスクが、収斂スライス着手時ではなく**いま**、名前の付いた未解決事項として台帳に載る。
- レスポンス経路の能力先行ドキュメントにより、開発者調査で観測された誤読（`replace` の見落とし）が再発しにくくなる。契約の形を変えずに読み手側の失敗モードを塞ぐ。

### Cons / Tradeoffs
- **0.4.0 に移行する全ゲストがソースを 1 行直す。** デプロイ済みコンポーネントは影響を受けない（ロード時アダプタ）が、再ビルドする側には確実に手が入る。
- ホストが同時に受理する契約版が増え、**ロード時アダプタの維持コストが上がる**。[[000098]] が既に記録した並走コストに、フィールド写像が 1 本足される。
- decision variant の収斂を未解決のまま残すので、[[000020]] の方針と現行契約の間の緊張は解消しない。**本 ADR はそれを可視化するだけである。**
- doc コメントの書き換えとレシピ追加は契約の形を変えないため、conformance では検証できない。同種の回帰は再びレビューでしか捕まらない。
- **再検討条件**: (a) wasi-http が 0.3.0 を実際にリリースしたとき（[[000020]] の収斂判断を再開する）; (b) decision variant を wasi:http 型の上の Plecto 側ラッパとして表現できる見通しが立ったとき; (c) sync と async の実行モデル差が fast path に与える帰結を測ったとき。
