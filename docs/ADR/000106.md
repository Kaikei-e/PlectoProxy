# filter に outbound TLS capability を wasi:sockets の in-repo vendor と独自 bindgen 再実装で貸与し、平文 outbound-tcp の意味を保つ

## Status
proposed（accept は再実装 spike の成立後。条件は Decision 末尾の「Gate」に固定する）

## Date
2026-08-13

## Affected Components
- host — feature `outbound-tls`（off-by-default）: vendored WIT + 独自 bindgen による `wasi:sockets/tcp` 実装、rustls 握手、TLS 済み stream の resource push
- control/manifest — `[filter.outbound_tls]` セクションの追加と、その fail-closed 検証群（feature 不在・IP リテラル・endpoint 重複・空 allowlist）
- control/manifest/content_hash — TLS 素材三ファイルを [[000097]] の二層分割へ配分（公開材料 2 + 秘密材料 1）
- CI / release — named runtime profile `capabilities` の構成変更（`outbound-http` + `outbound-tcp` + `fat-guest` + `outbound-tls`）
- wit — 変更なし（`plecto:filter` 契約は不変。貸すのは WASI 語彙であって Plecto 契約ではない）
- docs — `writing-a-filter.md` の Tier 表と hardening に TLS 脚の意味論を追記

## Context

**外部事実（2026-08-13 取得、一次ソースで裏取り済み）**

- RESP を話す共有ストアの公式セキュリティ文書は、防御を「非公開網への配置 ≠ 認証（ACL named user + `AUTH`）≠ 暗号化（TLS）」の三層として並べ、**`AUTH` は平文であり盗聴を防がない**と明記する。TLS はストア側 6.0+ の確定機能で、既定はクライアント証明書を要求する mTLS、サーバ認証のみへ緩めることもできる。したがって「AUTH だけ」の輸送は資格情報を素で流す経路である。
- サーバ証明書の検証は**二つの別規範**からなる。RFC 5280 の certification path validation と、接続先ホスト名を証明書の service identity に照合する RFC 9525（RFC 6125 を obsolete。DNS-ID、IP リテラルなら IP-ID）。TLS 1.3 の正文は RFC 9846。片方だけでは検証したことにならない。
- **`wasi:tls` は Phase 1 提案**（Portability Criteria 未記入、wasmtime 側の host 実装は draft / experimental）。確定事実として能力面の正文に据えられる段階にない。
- ALPN（RFC 7301）の IANA レジストリに RESP の protocol ID は登録されていない。提示すべき値が存在しないので、ALPN extension は送らない（「空の ALPN」は RFC 7301 の語彙として成立しない）。

**内部事実（同日のコード実査）**

- [[000060]] は Cons に「TLS over TCP はゲスト側実装に委ねる（ホストは平文 TCP の検問のみ）」と書いた。その前提は**ゲスト内で TLS が書けること**だが、rustls の暗号 provider は wasm32-wasip2 でのリンクが難しく、[[000055]] の Tier A ゲスト（zero-WASI の純コンポーネント）にはソケットも TLS も無い。[[000081]] が昇格条件に TLS 経路を置いた時点で、この実装分担は成立していない。
- **upstream 実装に facade を被せる形は構造的に採れない。** `Cargo.lock` は `wasmtime` / `wasmtime-wasi` / `wasmtime-wasi-io` を 47.0.3 に pin しており、その p2 bindgen は `"wasi:sockets/tcp.tcp-socket": crate::sockets::TcpSocket` と resource 型を固定 map する。`TcpSocket` 型自体は公開だが、構成子（`new` / `new_accept`）と p2 stream 化（`p2_streams`）は `pub(crate)` であり、外部 crate が「TLS 済み stream を中身に持つ socket」を作る口は開いていない。`tcp-create-socket` の戻り契約も同じ型に固定される。
- **既存の SSRF 床はこの新しい脚に自動では付いてこない。** 現行の connect 検問は `TcpGuard::configure_wasi_ctx` が `WasiCtxBuilder::socket_addr_check` に載せた閉包で発火し、それを呼ぶのは `wasmtime-wasi` の TCP 実装だけである。判定本体 `TcpGuard::permits`（allowlist・reserved 床・private opt-in・IP pin・per-request 接続予算）は I/O を持たない純関数だが **module private** で、自前 resource からは呼べない。
- **壁時計上限と接続予算も自動では立たない。** `WasmtimeRuntime::drive_call` は `outbound_tcp` state からのみ `io_deadline` を解決する（既定 5000ms / 上限 30000ms、接続予算 既定 4 / 上限 64。いずれも `options.rs` で host clamp）。epoch interruption はホストの socket I/O でブロックした guest に届かないため、`[filter.outbound_tcp]` を宣言しない TLS-only フィルタは握手と読取りで**無限にブロックできる**。
- 二層 content hash（[[000097]] Decision 3）は `crates/control/src/manifest/content_hash.rs` に `mix_public_material` / `reload_fingerprint` として着地済みで、`upstream.tls.ca` / `upstream.tls.client_cert` / `upstream.tls.client_key` というラベル規約もある。同 ADR の不変則は「`build_active` が読むファイルの in-place ローテーションは必ず reload gate を通過させる」であり、新しいファイル参照は必ずどちらかの層へ足すことになる。
- [[000079]] の `capabilities` profile は現在 `outbound-http` + `outbound-tcp` + `fat-guest` の三点であり、feature 名 = profile 名（umbrella feature）で drift を構造的に防いでいる。
- WIT の in-repo vendor 自体は前例がある（Tier B ゲストが `wit/deps/wasi-sockets-0.2.0/` を含む 6 パッケージを VCS 追跡している）。ただし**ホスト側に vendored WIT を持つのは初**であり、`wasmtime-wasi` の pin と lockstep になる。

関係する Tenet / Fork: deny-by-default capability、fail-closed、単一バイナリ・運用の単純さ、データプレーンで panic 禁止。

## Decision

平文の `[filter.outbound_tcp]`（[[000060]]）の意味は**一切変えない**。TLS は別の能力 `[filter.outbound_tls]` として新設し、off-by-default の feature `outbound-tls` に隔離する。ホストが TCP を開き rustls（aws-lc-rs、[[000051]]）で握手し、guest には復号済み stream を貸す。guest から見た API とワイヤ上のアプリケーションバイト列は不変で、`plecto:filter` 契約にも変更はない。

1. **実装モデルは全面再実装である。** `wasi:sockets@0.2.x` の WIT を in-repo に vendor し、`tcp` と `tcp-create-socket` を Plecto 自身の型へ map した独自 bindgen で実装する。`wasi:io` は逆に制御が要らないので `with:` で upstream へ alias し、TLS 済み stream は `InputStream` / `OutputStream` の実装として resource table へ push する。**upstream `TcpSocket` の差替え・継承ではない**（Context のとおり、その口は存在しない）。

2. **vendored WIT は `wasmtime-wasi`（および `wasmtime-wasi-io`）の pin と lockstep で保守する。** `Cargo.lock` の pin を上げる手順に vendored WIT の差分確認を必須項目として組み込む。追随が破綻した場合の縮退先は private WIT の TLS resource（Plecto 独自 interface + 契約版）であり、これを再検討条件に明記する。

3. **policy の発火点は TLS resource 側が自前に持つ。** 共用するのは policy の**純関数**——`TcpGuard::permits` の判定と、ホスト自前の vetted `ip-name-lookup`（allowlist 内の名前だけを解決し、全解決結果を分類してから pin する）——であって、`WasiCtxBuilder::socket_addr_check` という発火点ではない。TLS resource は connect の**前に** `permits` を明示的に呼ぶ。実装事項として `permits` の可視性を TLS 実装から呼べる範囲へ広げ、名前解決は vetted lookup が pin した結果だけを使って TLS connect 時に再解決しない。**呼び忘れが静かに通る形**なので、TLS 脚の負例回帰とセットでのみ着地させる。

4. **TLS-only 宣言でも壁時計上限と接続予算が常に立つ。** `[filter.outbound_tls]` は `io_deadline_ms` と `max_connections` を `outbound_tcp` と同型・既定付きで**自前に**持つ。両セクションを宣言したフィルタでは、hook 呼出しの壁時計上限は宣言された outbound セクション群から `min`（厳しい方）で解決し、接続予算は section ごとに独立して数える（平文脚と TLS 脚の予算を混ぜない）。

5. **排他は endpoint 単位。** `[filter.outbound_tcp]` と `[filter.outbound_tls]` は併存できるが、同一 `host:port`（host は小文字化して比較）が両 allowlist に現れたら validate で fail-closed にする。同じ endpoint を平文と TLS で二重に貸さない。これは単なる衛生ではなく well-formedness の条件でもある: 一つの world に `wasi:sockets/tcp` の実装は一つしか載らないため、両宣言時は Plecto の再実装が平文脚も担い、**connect 先の endpoint が輸送（平文 / TLS）を一意に決められる**必要がある。

6. **identity は entry の hostname に一本化する。** TLS allow entry の `host` は hostname 必須で、**SNI = 証明書の検証名 = entry の `host`** の三者は常に同一とする。section 単位の `sni` キーは持たず、guest にも自由な SNI を与えない。検証は RFC 5280 の path validation と RFC 9525 の service identity 照合の**両方**で行う。IP リテラル entry は v1 の validate で拒否する（証明書の IP identity 照合を持たないため）。ALPN extension は送らない（Context の RFC 7301 / IANA 事実）。

7. **reload / content hash は [[000097]] Decision 3 の適用であり、新規決定ではない。** `[filter.outbound_tls]` の三ファイルは既存の二層分割にそのまま乗る:
   - `ca_path`（必須）と `client_cert_path`（任意）は **`mix_public_material` 側**へ、`upstream.tls.ca` / `upstream.tls.client_cert` と同型のラベルで足す。identity は filter id + endpoint（一フィルタが複数 endpoint を持ち得るため、section だけでは同定できない）。
   - `client_key_path` は **`reload_fingerprint` 側**へ `Zeroizing` 読みで足す（低エントロピー秘密のオフライン総当たり oracle を公開 config version に作らないという同 ADR の理由がそのまま効く）。
   - 三ファイルとも [[000095]] の `[filter.config_files]` 経路は通さない。両端 trim と UTF-8 必須は PEM / PKCS#8 を壊し得るうえ、秘密鍵が WASM メモリに乗る。ホスト専用パスとして control が読み、鍵ファイルには `[upstream.tls]` の client key と同じ所有者限定の権限規律を課す。
   - SIGHUP の no-op 判定（公開 version と reload フィンガープリントの両一致）で `Unchanged` にならなかった経路でのみ、host が `ClientConfig` を再構築する。**gate を迂回する第二の証明書導入機構は作らない。**

8. **[[000079]] の named runtime profile に `outbound-tls` を加える。** `capabilities` は `outbound-http` + `outbound-tcp` + `fat-guest` + `outbound-tls` になり、無印（minimal）は従来どおり最小攻撃面を保つ。feature 名 = profile 構成という規律は維持し、feature を持たない binary で `[filter.outbound_tls]` が宣言されたら **manifest validation で fail-closed**（`outbound_tcp` / `outbound_http` と同一の規則）。compile-time inclusion ≠ runtime grant の注記も同様に適用する。同じ manifest を conformance の試験前提として渡した場合、この failure は component の world 非適合（`fail`）ではなく binary feature 不足として `environment` に落とす（[[000108]] Decision 3）——貸せない能力は環境の問題であって、契約の問題ではない。

**検討した代替案と却下理由:**

- **`wasi:tls` を Linker に載せる** — 標準語彙に寄せられれば vendored WIT も再実装も不要になる。しかし 2026-08-13 時点で Phase 1（Portability Criteria 未記入、wasmtime 側は draft / experimental）であり、能力面の正文を提案段階の仕様に賭けることになる。却下（再検討条件 (b) に予約）。
- **ゲスト内 rustls（[[000060]] 当時の分担のまま）** — wasm32-wasip2 での暗号 provider リンクが困難で、[[000055]] の zero-WASI 純コンポーネントではソケットも TLS も持たないため原理的に不成立。polyglot の前提（同じフィルタが言語を跨いで書ける）を壊す。却下。
- **sidecar / 別プロセスでの TLS 終端** — ホスト↔別プロセス間が平文で残り、暗号化の目的を局所的に打ち消す。単一バイナリ・運用の単純さにも反する（[[000060]] が HTTP ブリッジを却下したのと同型）。却下。
- **`socket_addr_check` に依存する「facade」実装** — 二重に成立しない。(i) upstream の resource 型が固定 map かつ構成子非公開で技術的に組めない。(ii) 仮に組めても自前の TLS 脚は `socket_addr_check` を通らないため、allowlist・reserved 床・IP pin・接続予算の**すべてが TLS 脚だけ素通り**する fail-open になる。「同一 code path を共用する」と書いて実装するのが最も危険な形なので、却下理由として明示的に残す。
- **既存 `[filter.outbound_tcp]` に `tls = true` を足して黙って TLS 化する** — 変更面積は最小だが、既に宣言された manifest の意味が変わり、operator が読んだ宣言と実際の輸送が乖離する。能力の貸与単位も「平文 TCP」か「TCP + TLS」か曖昧になる。却下（平文 `outbound-tcp` の意味は不変、が本 ADR の前提）。

**Gate（本 ADR を accepted へ上げる条件）**: 本 ADR は proposed である。accept は **vendored WIT + 独自 bindgen による再実装 spike が成立したときに限る**。spike の合格条件は二群で、(i) resource table・pollable・half-close・error mapping・deadline・pool teardown が通ること、(ii) TLS 脚の SSRF 負例——allowlist 外 IP への connect が deny される / reserved 床（loopback・link-local metadata）が最広の `allow_private` opt-in でも deny される / ホストが解決していない未 pin の IP が deny される / 同一 request 内で `max_connections` を超えた connect が deny され、deny された試行は予算を消費しない / TLS-only 宣言のフィルタで hook 呼出しが `io_deadline_ms` で打ち切られる——が全て緑になること。成立しなければ実装スライスへ進まず、private WIT の TLS resource を**別 ADR + 別契約版**で判断する（同一スライス内で黙って切り替えない）。

## Consequences

### Pros

- 資格情報とレート制限キーが平文で流れない経路が初めて成立し、[[000081]] が昇格条件に置いた輸送の一項を満たせる状態になる（昇格判断そのものは [[000107]] の担当）。
- `plecto:filter` 契約は不変で、guest API もワイヤ上のアプリケーションバイト列も変わらない。既存の RESP 実装と多言語ゲストがそのまま TLS 経路に乗る。
- SSRF 判定が純関数として一箇所に残り、平文脚と TLS 脚が**同じ判定**を共有する（発火点は二つでも、判定の正本は一つ）。
- 秘密鍵は host だけが読み、guest メモリにも公開 config version にも現れない（[[000097]] の二層分割と [[000095]] の trim 経路回避の合わせ技）。
- 隔離の型（feature gate + per-filter 宣言 + オプトイン不能の床）が [[000036]] / [[000060]] に続く三例目となり、profile の増分は umbrella feature 一つで済む。

### Cons / Tradeoffs

- **vendored WIT と `wasmtime-wasi` の lockstep が恒久的な保守債務になる。** pin を上げるたびに WIT の差分確認が要り、upstream が p2 の resource 表現を変えれば再実装の追随が要る。ホスト側 vendored WIT はリポジトリ初の形であり、前例の少なさもコストに含まれる。
- **検問の発火点が二つになる**（`socket_addr_check` と TLS resource の明示呼び出し）。呼び忘れは静かに通るため、負例回帰が事実上の床であり、テストが落ちれば設計上の不変条件が壊れたと読む必要がある。
- ホスト側の socket 実装コードが純増する。rustls の client 経路自体は既に依存木にあるため供給網の純増は小さいが、データプレーンに近いコード量としては増える。
- v1 は IP リテラル entry を持たないため、DNS 名を持たない endpoint には TLS 脚を使えない（平文 `outbound_tcp` を使うか、名前を用意する運用になる）。
- ローテーション時に既存の pooled TLS 接続をどう扱うか（新規接続だけ新 `ClientConfig` を使い既存は drain するか、pooled instance を recycle して即時破棄するか）は本 ADR では選択しない。実装スライスで規定し、選んだ方を E2E で固定する。
- **再検討条件**: (a) vendored WIT の lockstep が破綻したとき（upstream の版上げに追随できない、または差分が再設計を要求する）は private WIT の TLS resource へ縮退する; (b) `wasi:tls` が Phase 3 以上かつ wasmtime に安定実装が入ったら語彙をそちらへ寄せ、本 ADR の再実装を撤去候補とする; (c) 証明書の IP identity 照合を実装し、pin テーブルと矛盾しない検証名規則を決められたら IP リテラル entry の拒否を再考する; (d) [[000060]] 再検討条件 (a)（`wasi:sockets` 0.3 系での形状変化・wasip3 収斂）が発火したときは本 ADR も同時に再評価する; (e) 再実装 spike が不成立なら本 ADR は accept されず、別 ADR + 別契約版へ差し替わる。
