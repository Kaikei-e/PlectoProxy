# Redis reference の production 昇格条件を 10 項目の反証可能なチェックリストとして再確定し、cost 入力の検証を必須に加える

## Status
proposed（accept は [[000106]] と同じ Gate に置く — 後述 Decision 末尾）

## Date
2026-08-13

## Affected Components
- `filter-ratelimit-redis` — 昇格条件を輸送・資格情報の 4 点から 10 項目へ拡張（cost 入力検証と RESP transaction 処理を新規に必須化）
- control/manifest — `[filter.outbound_tls]` 宣言と `[filter.config_files]` の password 解決が昇格条件の入力になる
- plecto CLI — PIXIT 付き `plecto package` の verdict が昇格条件の一つになる
- docs/hardening — 運用手順（ACL 永続化・失効・cost ヘッダの剥がし）を条件の一部として書き切る

## Context

[[000081]] は Decision 2 で昇格条件を 4 点に置いた: (i) ACL user + `AUTH`、(ii) TLS（または同等に検証可能な暗号化）、(iii) 資格情報を manifest の平文に埋めない配布、(iv) `on_backend_error` と local floor の相互作用を E2E で固定したまま維持。本 ADR はこの 4 点を出発点として保ちつつ、その後に判明した二種類の差分を吸収して条件を再確定する。

**差分 1 — secret 経路は既に閉じた（確定事実）。** [[000095]] が `[filter.config_files]` を manifest 層に導入し、パスワード文字列のファイル間接参照が WIT に新能力を足さずに成立した。000081 の条件 (iii) は新しい設計を要さず、既存機構の**使用を要求する**条件に落ちる。ただし 000095 の意味論は UTF-8 必須・両端 trim であり、PEM / PKCS#8 を壊し得るうえ秘密鍵が WASM メモリに乗る。CA・証明書・鍵は同じ経路に載せられない。

**差分 2 — 輸送・資格情報の 4 点だけでは production と呼べない（確定事実、2026-08-13 のコード実査）。**

1. **cost 入力が無検証。** `dynamic_cost` は `cost_header` の値を `parse::<u64>()` に通すだけで、下限クランプも上限も持たない。`"0"` はパース成功なので既定へフォールバックせず、`INCRBY key 0` はキーを作って現在値を返すだけでカウンタを進めない。結果として `count <= limit` が恒真になり、global 層を丸ごと迂回できる。キーは `rl:{route_tag}:{client_identity}` とクライアント単位に分かれるので他クライアントの加算も効かず、native local floor は `RateLimitKeyKind` の既定が `Route`（route 全体の総量床であって per-client 上限ではない）なので下の床も残らない。fast path が ingress で剥がすのは forwarded / client-IP 系で、任意の名前の cost ヘッダは素通りする。既定側も同じで、`[filter.config].cost` は `parse().ok()` の値をそのまま使うため `cost = "0"` の宣言で同じ穴が開く（非数値・負値・u64 範囲外はパース失敗で既定へ戻る）。u64 に収まりつつ RESP の 64-bit signed 範囲を超える値は `INCRBY` が `-ERR` を返し、`on_backend_error = "allow"` では同じく素通りになる。
2. **曖昧な write を再送する。** `consult()` は `send_pipeline()` の `Err` を種類で分けずに新規接続で同じ `INCRBY` を一度再送する。稀な応答消失だけでなく、`INCRBY` の integer 応答を読み終えた**あと**に `EXPIRE` が `-ERR`（AUTH 導入後なら `-NOPERM`）を返す確定的な経路でも再送が起き、条件が揃えば毎リクエスト二重加算になる。
3. **RESP パーサが 3 prefix しかない。** `+` / `-` / `:` のみで、配列 `*` と bulk string `$` を持たない。未知 prefix はエラーを返すが行は消費済みで、以降の読み位置がずれる。隔離された一組として `MULTI` / `EXEC` を扱う余地が現状の実装面に無い。
4. **接続は pooled instance に持続する。** trusted 前提の thread-local に `RespConn` を保持して再利用する（判断状態ではない通信資源）。接続確立時に一度だけ `AUTH` を送る設計（projected）と組み合わせると、ストア側の `ACL SETUSER … off` やパスワード変更**だけ**では既存接続が生き続け、資格情報の失効が即時に効かない。

**外部一次ソースの層（確定事実）。** Redis / Valkey の公式セキュリティ文書は trusted network・認証（ACL による named user、`AUTH username password`）・TLS を別々の層として並べ、「平文上の `AUTH` は盗聴を防がない」と明記する。`AUTH` は ACL 上つねに許可されるためコマンド許可に `+auth` は要らない。`ACL SETUSER` の効果は in-memory であり、aclfile への `ACL SAVE` を欠くと再起動で `plecto-rl` が消え `default` が `nopass +@all` に戻る — このときフィルタは失敗するだけなので、運用者はロックダウン済みと誤認したままストアだけが全権素通しで残る。TLS 側の検証は二段が別々の規範で、RFC 5280 の certification path validation と RFC 9525 の service identity 照合（DNS-ID）は片方だけでは満たされない。Transaction は `EXEC` まで他 client を割り込ませない隔離を与えるが rollback は与えず、queue 時エラーは `EXECABORT`、実行時エラーは `EXEC` 配列の要素に現れる。

**projected**: 項目 2 が要求するホスト側 TLS 能力 `[filter.outbound_tls]` は [[000106]] が proposed 段階で持つ interface であり、実装モデル（vendored WIT + 独自 bindgen による再実装）の成立は spike 待ちである。公開 conformance battery の既定 pin（項目 8 の判定基準）も 1.0.0 のままで、2.0.0 は opt-in である。

**status の意味について。** 本 ADR が accepted になることは「demo-only 宣言と昇格条件という decision を採択した」ことであって、「`filter-ratelimit-redis` が production-ready になった」という status ではない。実装状況は 10 項目が全緑かどうかで別に測る。000081 が proposed のまま「昇格条件はある」と読まれてきた曖昧さを、ここで言葉として分離する。

関係する Tenet / Fork: fail-closed、deny-by-default capability、フィルタはステートレス、安全 × 運用の単純さ。

## Decision

**[[000081]] Decision 2 の 4 点を、次の 10 項目へ改める。すべて必須で、部分実装（`AUTH` だけ、TLS だけ）では昇格しない。**

1. **ACL named user + `AUTH username password`。** ゲスト実装と運用ガイドの両方。ストア側は `default off`、`~rl:*`、`resetchannels`、`-@all` + フィルタが実際に送るコマンドのみ（`+ping` `+incrby` `+expire` `+multi` `+exec`。`+auth` は不要）。**合格判定は設定手順の実行ではなく、ストア再起動後の観測**とする: admin user からの `ACL LIST` が上記の `plecto-rl` と `default off` を返すこと。永続化は aclfile + `ACL SAVE` を正とし、in-memory だけの設定はこの条件を満たさない。検証を `PING` で止めない（`PING` は AUTH と `+ping` しか通さず、キーパターンの綴り違いを素通しする）。
2. **`[filter.outbound_tls]` を宣言し、ホストが RFC 5280 の certification path validation と RFC 9525 の service identity 照合の両方でサーバ証明書を検証する。** 片方だけでは緑にしない — path が通っても名前照合を外した実装はこの項を満たさない。v1 の allow entry は hostname 必須なので IP-ID 照合は対象外。平文 `outbound-tcp` 上の `AUTH` のみは不可。
3. **パスワードは `[filter.config_files]`（[[000095]]）。CA / クライアント証明書 / 秘密鍵はホスト専用パス**で読み、000095 の trim 経路を通さず、ゲストメモリに載せない。
4. **`on_backend_error` の宣言必須を維持する**（[[000061]]）。fail-open を選んだ構成では local floor が唯一の上限になることを hardening に書く。
5. **write の送信開始後に起きた曖昧な失敗は再送しない。** 接続を捨て、宣言済み `on_backend_error` に従う。再接続してよいのは接続確立・`AUTH`・`PING` の**書込み前**の失敗だけ。`MULTI` / `INCRBY` / `EXPIRE NX` / `EXEC` を一組として扱い、`EXECABORT`・配列要素の error・要素数/型の不一致では接続を捨てる。rollback や exactly-once は主張しない。
6. **fail-open を許す production manifest は local floor を必須化し、N replica での合成上限を記述する。** 許可 burst は概ね `N × local burst` まで合成され、local `rate` と global `limit/window` の整合が要る。
7. **E2E 集合を固定する**: `AUTH` 成功 / `WRONGPASS` / `NOPERM` / TLS 検証失敗 / `EXEC` 応答消失 / **ストア側 revoke 単独では既存接続が生き続けること**（確立済み接続に対して `ACL SETUSER … off` やパスワード変更を行っても consult は成功し続け、`CLIENT KILL USER` 相当で切って初めて再接続 → `AUTH` 失敗 → `on_backend_error` に落ちる）。最後の一本は「失効の即時性はストア側操作の組み合わせで決まり、Plecto 側の reload では決まらない」ことを test で言い切るためのものである。
8. **PIXIT manifest 付き `plecto package` の S1 と dynamic MUST が緑。** PIXIT は本番と同じ低下（`load_options()` + `resolved_config(base_dir)` の対）を通し、`[filter.config_files]` 由来の `redis_password` が `host-config::get` までゲストに届くことを条件に含める。PIXIT 無しでは能力不足として赤になること（緑にならないこと）も同時に固定する。
9. **cost 入力を検証する。** `cost_header` 由来の値も宣言済み既定 `cost` も、ゲスト側で **1 以上にクランプ**する。新設の必須 config `max_cost` を超える値は受理せず backend へ送らない。加えて、cost ヘッダは**先行する信頼済みフィルタが発行し、edge で同名ヘッダを剥がす**運用前提であることを hardening に明記する — ゲスト側のクランプと `max_cost` は最後の砦であって、剥がしの代わりではない。
10. **棚（署名済み OCI artifact）に載せるのは 1–9 が全緑になったあとの別判断**とする（[[000080]]）。それまでは demo-only 表記を維持する。

**000081 から持ち越して変えない判断**: 現行構成の demo-only 宣言（000081 Decision 1）、trusted network を production security の代用にしないこと（同 3）、着手タイミングを発信・trial の要求に従属させること（同 4）、[[000053]] / [[000061]] の配置判断は不変で昇格は同一 reference filter の輸送・入力の硬化であること（同 5）。アルゴリズム刷新（GCRA / sliding window / Lua）は引き続き対象外。

**検討した代替案と却下理由**:

- **(A) 4 点のまま昇格させる** — 却下。cost 迂回（`"0"` で `count <= limit` が恒真）と曖昧 write の再送を抱えたまま production と宣言することになる。4 点は輸送と資格情報の床であって、迂回経路と入力検証の床ではない。実測された穴を条件外に置くと、チェックリストが「緑なのに素通しできる」状態を許す。
- **(B) cost 迂回は fast path の ingress ヘッダ剥がしだけで塞ぐ** — 却下（運用前提としては項目 9 に採るが、単独では不十分）。fast path が剥がすのは forwarded / client-IP 系で、任意の名前のヘッダを剥がす汎用機構は routing 設定面を増やす。剥がし忘れ・チェーン順の誤りが静かに全開放になるため、宣言と同じ場所（filter config）に立つゲスト側クランプを最後の砦として重ねる。
- **(C) `cost_header` 機能そのものを削除する** — 却下。重み付き admission は [[000061]] Decision 2 が用意した設計で、[[000105]] の token-cost starter と同じ線にある。危険なのは機能ではなく無検証であり、削除は表現力を失うだけで信頼境界の問題を解かない。
- **(D) identity の HMAC 化（RFC 2104、ソルトはホスト管理秘密）を昇格条件に含める** — 却下。原文 identity をストアに置く PII retention は本番推奨として hardening に書くが、輸送・認証の床とは独立した任意スライスである。条件に混ぜると床が二重目的になり、部分実装の判定が曖昧になる。
- **(E) 曖昧 write を request ID + store-side deduplication で exactly-once にする** — 却下。別の algorithm / protocol であり v1 の RESP スコープを超える。公式が「transaction は隔離を与えるが rollback を与えない」と明記する以上、`MULTI` / `EXEC` で包んでも `EXEC` 実行後の応答消失は判別できない。非再送（項目 5）が v1 の正しい保守側の選択であり、原子的 dedup を導入したときだけ再検討する。
- **(F) 昇格前にアルゴリズムを GCRA 等へ刷新する** — 却下。000081 が既に却下済みで、本 ADR の対象も輸送・資格情報・入力検証の床に限られる。
- **(G) 棚への署名公開を同じ判断に含める** — 却下。[[000080]] の「directory がある ≠ 出荷」を守る。条件を満たすことと配布物を出すことは別の claim であり、release note でも区別する。

**Gate（accept 条件）**: 項目 2 が `[filter.outbound_tls]` の interface に依存するため、本 ADR の `proposed` → `accepted` は [[000106]] と**同じ Gate** に置く — 再実装 spike（vendored `wasi:sockets` WIT + 独自 bindgen で resource lifecycle・deadline・TLS 脚の SSRF 負例まで成立させること）が成立したときにだけ両 ADR を accepted へ上げる。不成立なら private WIT の TLS resource を別 ADR + 別契約版で判断し、その判断に合わせて本 ADR の項目 2 も改める（同じスライス内で黙って切り替えない）。**そして accepted は decision の採択であって、`filter-ratelimit-redis` が production-ready という status ではない。**

## Consequences

### Pros
- 昇格条件が輸送・資格情報の 4 点から、迂回経路と入力検証を含む 10 項目になり、「輸送だけ硬化して production と呼ぶ」部分実装を構造的に排除できる。
- 各項目が**観測で反証可能**になった（再起動後の `ACL LIST`、固定した E2E 集合、PIXIT 付き gate の verdict、cost E2E）。手順を実行したかではなく状態がどうかで判定する。
- cost 迂回という実在の穴（`"0"` で global 層が恒真通過）が条件化され、`0` / 負値 / 非数値 / u64 上限級の E2E で固定される。
- secret 経路は [[000095]] で既に着地しているため、条件 3 は WIT に新能力を足さずに閉じる。
- 000081 の Decision body を書き換えず amends 側に確定形を置くので、ADR グラフの append-only 規約を保ったまま判断を更新できる。

### Cons / Tradeoffs
- 条件が増えた分、昇格までの実装量が増える（ホスト側 TLS、RESP の配列 / bulk string、cost 検証、実ストアを要する E2E マトリクス）。demo-only 期間はその分延びる。
- `max_cost` は新設の必須 config であり、既存の demo manifest は宣言を足さないと `init` で trap する（trusted なので load 失敗として現れる）。この破壊性を受け入れる。
- 1 以上のクランプが保証するのは「偽装されても最小 1 は必ず引かれる」ことだけで、上限側の健全性は `max_cost` の運用値に依存する。`max_cost` を大きく取り、かつ identity の信頼（[[000061]] Decision 2 の edge model 前提）が崩れた構成では、高 cost + identity 偽装で他クライアントのバケットを枯らす経路が残る。
- fail-open で local floor を必須化しても「local floor があるから安全」ではない。既定の local floor は route 全体の総量床であって per-client 上限ではなく、合成上限は概ね `N × local burst` に開く。hardening でこの二点を並べて書かないと、項目 6 が安心材料に読み替えられる。
- **再検討条件**: (a) Gate 不成立で項目 2 の interface が private WIT の TLS resource に変わったら、本 ADR の項目 2 を改める ADR を書く。(b) `host-ratelimit` や RESP 側に refund / 原子的 dedup（request ID）が入ったら、項目 5 の「再送しない」を再評価する。(c) RESP 互換ストア側が TLS / ACL を提供しない運用が主流と判明したら、[[000081]] 再検討条件 (a)（代替バックエンドまたは別 transport の評価）へ合流する。(d) 公開 conformance battery の既定 pin が上がったら、項目 8 の判定基準となる battery version を版上げする。(e) identity の HMAC 化が実運用で必須と判明したら、hardening 推奨から 11 項目目へ格上げする。
