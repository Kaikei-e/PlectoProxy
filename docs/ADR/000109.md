# scaffold の WIT 同梱を版付き wit/deps/ 木へ拡張し、vendoring を new-filter の一点に閉じる

## Status
accepted（`--lang js` / `--lang go` スキャフォールドの RED を書く前に木の形を固定する決定。実装は後続で、
本 ADR は形と不変条件だけを確定する）

## Date
2026-08-13

## Affected Components
- plecto（CLI） — `write_wit` が deps 木を書く。契約テキストの出所は従来どおり `FILTER_WIT` 一本
- crates/plecto/templates — WASI 0.2.0 pin セットの embed 元（crate root 配下）
- wit-deps — pin セットの canonical（`plecto/wit-streaming/` と同じ、`wit/` の兄弟ディレクトリ）
- scripts/check_wit_vendoring.py — pin セットの canonical → vendored 対を追加
- examples/filters — js / moonbit の build 時コピー撤去、deps の追跡化、drift assert の統一

## Context

[[000072]] は `plecto new-filter` の WIT 取得をネットワーク `wkg` から**バイナリ同梱**へ切り替え、
「バイナリが scaffold する契約」と「バイナリのホストが実行する契約」の一致を運用ルールではなく構造で
担保した。実装は今日も単一ファイルである: `new_filter.rs` の `write_wit` は
`plecto_control::FILTER_WIT`（`plecto-host` の vendored copy の再エクスポート）を `wit/world.wit` へ
一枚書くだけで、deps ディレクトリを持たない。Rust テンプレートはこれで足りる——生成される guest は
公開 world をそのまま実装するため、外部パッケージを解決する必要がない。

同 ADR の再検討条件 (b) は「WIT が複数ファイル / 外部 deps を持つ構成に育ったら、単一 `include_str!`
では足りないため同梱方式を manifest 化する実装 ADR を切る」と書いていた。非 Rust スキャフォールドは
この条件をそのまま発火させる。JS / Go の starter は [[000063]] Decision 3 に従って**ゲスト側で自分の
world を宣言する**（`package plecto:tokenlimit-go;` / `world filter-request-body`）ため、その world が
`use plecto:filter/types@0.4.0` する以上、`plecto:filter` パッケージ本体を `wit/deps/` に置かなければ
解決できない。Go はさらに `include wasi:cli/imports@0.2.0` を合成するので WASI 0.2.0 のパッケージ群も
要る。

**in-tree は現に三形へ割れている**（コード実査、確定事実）:

- `filter-tokenlimit-go` — `wit/deps/plecto-filter-0.4.0/package.wit` を VCS 追跡し、`build.sh` が
  canonical との `diff -q` で drift を落とす。WASI は `wit/deps/wasi-{cli,clocks,filesystem,io,random,sockets}-0.2.0/package.wit`
  の 6 パッケージを同じく追跡。
- `filter-tokenlimit-js` — `build.mjs` が毎ビルド canonical（`../../../wit/world.wit`）を
  `wit/deps/plecto-filter/world.wit` へコピーし、`.gitignore` に `wit/deps/` を入れている。
- `filter-tokenlimit-moonbit` — `build.sh` が同じコピーを `cp` で行い、`.gitignore` も同様。
- （参考）`filter-hello-js` は guest 側 `wit/` を持たず、`witPath` に canonical `../../../wit/v0.3.0`
  を直接指す第三の形。

ビルド時コピー方式が置いている前提は、それ自身のコメントと矛盾する。`build.mjs` は「この guest は
starter として木の外へ持ち出される想定だから、シンボリックリンクではなくコピーにする」と書いているが、
コピー元は `../../../wit/world.wit` という**リポジトリ内の相対パス**であり、持ち出した瞬間に存在しなく
なる。持ち出し可搬性という目的に対して、手段が正面から効いていない。スキャフォールド出力に至っては
canonical パスが構造的に存在しない（[[000072]] の前提そのもの）。

サイズの確定値（実測、2026-08-13）: canonical 契約 `plecto/wit/world.wit` は 16,676 bytes、WASI 0.2.0
の 6 パッケージは合計 17,183 bytes。前者は既にバイナリに乗っており、後者が新たに乗る増分である。

関係する Tenet / Fork: [[000065]] の TTFVF（生成物がオフラインでそのままビルドできること）、
deny-by-default capability（deps の同梱は解決用テキストであって能力付与ではない）、運用の単純さ
（「どのファイルを誰が書くか」を静的に決める）。

## Decision

1. **生成 project の deps 木は `wit/deps/plecto-filter-0.4.0/package.wit` の一形に統一する。**
   ディレクトリ名にパッケージ版を含め、ファイル名は `package.wit` とする。in-tree の
   `filter-tokenlimit-js` / `-moonbit` も同形へ揃え、`wit/deps/` を VCS 追跡へ変えて `.gitignore` から
   外し、build スクリプトのコピー行を落とす。drift 検出は `filter-tokenlimit-go` と同じ `diff -q`
   assert に寄せる。本決定は**ゲストが自分の world を宣言する場合の形**であり、公開 world を直接実装する
   Rust テンプレートの `wit/world.wit` 単一ファイル形は変えない（deps が要らない構成に deps 木を強いる
   理由がない）。どちらの形でも、書き出される契約テキストの出所は `FILTER_WIT` 一本のままである。

2. **`--lang go` が同梱する WASI 0.2.0 の pin セットは `filter-tokenlimit-go` と同じ 6 パッケージ**
   （`cli` / `clocks` / `filesystem` / `io` / `random` / `sockets`）とする。これは
   `include wasi:cli/imports@0.2.0` を**解決する**ための text であって能力付与ではない——`wasi:cli` の
   `imports` world は `wasi:sockets/tcp@0.2.0` や `wasi:filesystem/types@0.2.0` まで import するが、
   出来上がる component の import 集合は `build.sh` の Tier B allowlist assert（`io` / `clocks` /
   `random` / `cli` / `filesystem` のみ、[[000063]] Decision 4）で縛られ、実際に貸すかどうかは manifest
   宣言とホスト Linker が決める。
   canonical はリポジトリ直下の `plecto/wit-deps/wasi-<pkg>-0.2.0/package.wit` に置く（`wit/` と
   `wit-streaming/` の兄弟）。**`plecto/wit/deps/` には置かない**——WIT のパッケージレイアウトでは
   `deps/` が依存パッケージの解決ディレクトリなので、そこへ WASI を置くと、ホストの bindgen や契約の
   publish 経路が読む `plecto/wit/` の解決入力に無関係なパッケージが混ざる。vendored 側は 2 箇所:
   CLI が `include_str!` する `crates/plecto/templates/wit-deps/`（`cargo package` は crate root 配下
   しか含められない。`plecto` の `include` は既に `templates/**` を持つ）と、resolver が物理コピーを
   要求する `examples/filters/filter-tokenlimit-go/wit/deps/`。この canonical → vendored 対を
   `scripts/check_wit_vendoring.py` に追加し、byte 同一性を CI ブロッキングにする。契約本体
   （`plecto/wit/world.wit` → 各 guest の `wit/deps/plecto-filter-0.4.0/package.wit`）も同じ対に載せる。

3. **vendoring は `new-filter` 時だけ**とする。`build.sh` / `build.mjs` は `wit/` 以下を一切書き換え
   ない。これは `plecto dev` の watcher 除外集合（`wit/deps/` を含む）と対になる不変条件で、除外集合が
   「書かれても再ビルドしない」を保証する一方、本決定は「そもそも build は書かない」を保証する。
   スキャフォールドが出す `build.sh` が持つのは canonical との `diff -q` ではなく、**vendored パッケージ
   の版 assert**（`wit/deps/` 側の `package plecto:filter@X.Y.Z;` を読み、guest world が `use` する版と
   一致することを確かめる）である——生成 project にはリポジトリの canonical パスが存在しない以上、
   `diff -q` は構造的に書けない。`diff -q` は canonical が隣にある in-tree example 側の assert として
   残す。

4. **同梱版を後から上げる明示 upgrade command は本決定の外**とする。生成 project の deps は scaffold
   時点で凍結し、追随したい作者は新しい `plecto` で scaffold し直すか、手で差し替える（手順は docs）。
   これは [[000072]] 再検討条件 (a)（複数契約版 scaffold の需要が実測で出たら `--contract-version` を
   再導入する）と同じ扱いで、需要が観測されてから別 ADR で判断する。

5. 本決定は [[000072]] の不変条件「スキャフォールドがホストと違う版を出せない」を、**単一ファイルから
   多言語の deps 木へ拡張**したものである。`FILTER_WIT` が単一の出所である限り、JS でも Go でも生成
   project が抱える契約テキストはバイナリのホストが実行する契約と同一で、増えたのは書き出す**ファイル
   数**だけであって信頼の連鎖は増えていない。

**検討した代替案と却下理由**:

- **無版ディレクトリ `wit/deps/plecto-filter/world.wit` に揃える（js / moonbit の現行形）** — 版が
  ファイル内の `package` 行にしか現れず、契約版の違う二つの project が木の形として区別できない。移行期
  に旧版 deps を並置することもできない。同じ project 内で wkg 由来の WASI deps（版付き）と二つの命名
  規約が混在するのも読み手に説明コストを課す。却下。
- **ファイル名を `world.wit` にする** — deps に置かれるのはワールド 1 本ではなくインタフェース群と
  ワールド 2 本を含む**パッケージ**であり、名前が中身を偽る。in-tree の WASI deps も `package.wit` で、
  そちらへ寄せるほうが一形に収束する。却下。
- **build 時コピーを維持する（現行 js / moonbit）** — 持ち出した starter でコピー元が消えるため、
  build.mjs 自身が掲げる「持ち出せる starter」を壊す。加えて build が vendoring の権威になると、
  「WIT は scaffold だけが書く」という静的な所有関係が崩れ、`plecto dev` の再ビルド周期ごとに契約
  テキストが再生成される。却下。
- **canonical へのシンボリックリンク** — 木の外へコピーすると壊れる（build.mjs のコメントが記録済み）。
  Windows やアーカイブ展開でも安定しない。却下。
- **`build.sh` が `wkg wit fetch` で取得する** — [[000072]] が却下したネットワーク依存の再導入であり、
  `plecto` 名前空間は guest から見てレジストリではなくこのリポジトリを指す（`filter-tokenlimit-go/build.sh`
  のコメントが記録済み）。[[000064]] の配布チャネルは外部作者向けに無変更で維持するが、scaffold は
  そこへ依存しない。却下。
- **WASI pin セットの canonical を `filter-tokenlimit-go` の追跡コピーにする（対を 6 本で済ませる）** —
  ファイル移動ゼロで最小だが、CLI に embed する資産の正本が example の存続に依存する。example は
  starter 帯（[[000105]]）で入れ替わりうるので、正本はリポジトリ側に置き、example も CLI も等しく
  vendored 側に置く。却下。

## Consequences

### Pros

- 生成 project と in-tree starter の木の形が一致し、「example を fork して始める」導線でパスが変わらない。
  docs が説明する形も一つになる。
- 生成物も example も、リポジトリの外へコピーしてビルドできる（canonical への相対パス依存が消える）。
- [[000072]] の構造的保証が多言語へ広がる: `FILTER_WIT` 一本から書くため、JS / Go でもホストと違う契約版
  を scaffold できない。
- drift 検出が二段で効く。`check_wit_vendoring.py` の byte 同一性（CI ブロッキング）と、in-tree example
  の `diff -q`（ビルド失敗）。黙って古い契約を主張する guest が出ない。
- 「WIT を書くのは `new-filter` だけ」が静的に決まり、`plecto dev` の除外集合と合わせて、生成物・
  binding・artifact の所有関係が全ディレクトリで一意になる。

### Cons / Tradeoffs

- `plecto` バイナリに WASI pin セットの 17,183 bytes が**無条件で**乗る（`--lang go` を使わない利用者
  にも）。契約 16,676 bytes と合わせて約 34 KB。実行時コストは無いが、embed は言語別に遅延できない。
- 版がパスに出るため、契約の版を上げるたびに `wit/deps/plecto-filter-<version>/` の rename が in-tree の
  全 guest と `check_wit_vendoring.py` の対リストへ波及する。手作業が一段増える（自動化は本決定の外）。
- 生成 project の deps は scaffold 時点で凍結する。`plecto` を更新しても既存 project は追随せず、
  Decision 4 のとおり upgrade command は無い。契約が minor bump した直後、古い project は古い契約の
  ままビルドし続ける（ロード時アダプタの範囲では動くが、新機能は使えない）。
- pin セットは WASI 0.2.0 と TinyGo の wasip2 前提に紐づく。上流が版を上げれば pin セットごと更新が
  必要で、その更新は Tier B guest とスキャフォールドに同時に効く（片方だけ上げられない）。
- **再検討条件**: (a) 版ずれの生成 project が実測で問題になったら、明示 upgrade command を別 ADR で
  判断する（[[000072]] 再検討条件 (a) と併せて評価する）。(b) pin セットが二つ以上の WASI 版を同時に
  要求し始めたら（新しい言語 Tier、wasip3 移行）、`include_str!` の羅列をやめ「版 → ファイル集合」の
  manifest 化を判断する。(c) 上流ツールが deps 木の標準レイアウトを変えたら（版付きディレクトリ名や
  `package.wit` 以外を要求するなど）、一形統一の前提が崩れるので形を再固定する。
