# plecto dev の build・watch・成果物受け渡しを言語非依存の契約として固定する

## Status
accepted（判断は 2026-08-13 の設計セッションで確定済み。実装は後続のスキャフォールド実装が RED から行い、
本 ADR は契約と不変条件だけを確定する）

## Date
2026-08-13

## Affected Components
- plecto（CLI） — build の起動口・watch の対象・成果物の受け渡し・manifest 自己書込みの 4 点を差し替え
- plecto（CLI） — scaffold 完了 message の案内コマンドを、フィルタ project root と dev 鍵の trust root が
  食い違わない形へ訂正
- examples/filters — 成果物名を固定名へ一括リネーム（`build.sh` 7 本・`build.mjs` 2 本）
- host tests / docs — 成果物名を参照している既定パス定数・README・チュートリアルの追随

## Context

[[000065]] は `plecto dev <filter-dir>` を「watch → componentize → conformance → dev 鍵署名 → OCI layout →
manifest digest 書換え → 自己 SIGHUP」のインナーループとして着地させた。その実装は今日も **Rust 一言語に
固定**されている（コード実査、確定事実）:

- `dev_cmd.rs` の `componentize` は `cargo build --target wasm32-unknown-unknown --release
  --target-dir <filter-dir>/target` を起動し、`Cargo.toml` の `[package].name` を snake_case 化した
  `target/wasm32-unknown-unknown/release/<stem>.wasm` を読んで `wit_component::ComponentEncoder` で
  component 化する。ビルド系の分岐点はここ一箇所で、cargo 以外の経路が存在しない。
- watch 対象は `<filter-dir>/src` の再帰のみ。`path_is_relevant` は `src/` 配下でないパスをすべて落とす。
  これは実機で観測された自己 rebuild ループ（`plecto dev` 自身が書く `target/` / `artifacts/` /
  `manifest.toml` の event が単一ファイル watch 下で誤報告された）への対策として [[000065]] の実装節が
  記録した割り切りで、`Cargo.toml` の編集には `plecto dev` の再起動が要る。

つまり非 Rust ゲストは、契約上は対等な市民でありながら **インナーループに入れない**。ここに言語ごとの
分岐を CLI 側へ積み増す道もあるが、その先には言語数ぶんのビルド手順が CLI のコードとして固定される。

一方、**ビルドの起動口はリポジトリ内で既に一つの慣行に収束している**。in-tree の非 Rust ゲストは 7 本すべてが
`build.sh` を持ち（`filter-hello-c` / `-go` / `-js` / `-moonbit`、`filter-tokenlimit-go` / `-js` /
`-moonbit`）、いずれも `set -euo pipefail` + `cd "$(dirname "$0")"` で始まり、ツールチェーン要件・WASI
import の allowlist assert・export 集合の assert までを自分で持っている。CLI が新しく発明すべきものは
起動口ではなく、**成果物の受け渡し規約**のほうである。

その成果物名は現状ばらけている（確定事実）:

- `build.sh` 7 本と `build.mjs` 2 本の出力はすべて `dist/filter_<snake_case>.wasm`（`filter_hello_c.wasm`
  … `filter_tokenlimit_moonbit.wasm`）で、フィルタ名がファイル名に入る。
- ホスト側テストはその名前を既定パス定数として抱えている（`crates/host/tests/polyglot.rs` の 3 本、
  `polyglot_tier_b.rs` / `tokenlimit_tier_b.rs` の各 1 本、`tokenlimit.rs` の 2 本）。
- `docs/writing-a-filter.md` の `plecto conformance` 例は `dist/my_filter.component.wasm` という**三通り目**の
  名前を書いている。

したがって固定名 `dist/filter.wasm` は既存慣行の追認ではなく、**本 ADR が新しく引く契約**であり、既存資産を
そちらへ揃える作業を伴う。

watch を project root へ広げる以上、除外集合が無いと [[000065]] が塞いだ rebuild ループが別の形で戻ってくる。
in-tree の生成物・恒久出力の実在は次のとおり（確定事実）: `filter-tokenlimit-go` は wit-bindgen-go の出力を
`--out internal` に置き `.gitignore` している。`filter-tokenlimit-moonbit` は `moon build` の恒久出力
`_build/` を持つ。`filter-tokenlimit-js` / `-moonbit` は `node_modules/` / `dist/` / `wit/deps/` を
`.gitignore` している。`plecto dev` 自身も `<filter-dir>/target/`・`<filter-dir>/artifacts/<filter-id>/`・
`manifest.toml` へ書く。

manifest の自己書込みは今日 `toml_edit` による format-preserving な書換えだが、`std::fs::write` で
`manifest.toml` を直接上書きしている。`src/` 限定 watch のもとでは無害でも、project root を見る watcher の
下では自分の書込みが自分を起こす。

初回動線にも実測可能な穴がある。`new_filter.rs` の scaffold 完了 message は `cd <name> && plecto dev .` を
案内するが、CLI は dev 鍵の置き場を `std::env::current_dir()` から解決する。案内どおり `cd` してから走らせると
**フィルタ project root と dev 鍵の trust root が同じディレクトリになり**、scaffold が manifest の `[trust]` へ
書いた `../.plecto/…` を指せず署名検証が落ちる。本 ADR は以降、`plecto dev <filter-dir>` の引数ディレクトリを
**フィルタ project root**（`build.sh` / `manifest.toml` / `dist/` を持つ側）、`.plecto/dev-key` を置く CLI の
作業ディレクトリを **workspace root** と呼び分ける。

関係する Tenet / Fork: [[000065]] の TTFVF（案内どおりに叩けば動くこと）、fail-closed（壊れたビルドを publish /
reload しないこと）、運用の単純さ（「どのディレクトリに誰が書くか」を静的に決めること）。なお `bash build.sh` は
**開発者が自分の project で自分のスクリプトを走らせる**行為であり、ホストが untrusted なゲストへ貸す能力とは
別の信頼領域にある。deny-by-default capability は WASM 実行境界の性質で、本決定はそこに一切触れない。

## Decision

`plecto dev` の 4 つの表面——build の起動口・成果物の受け渡し・watch の対象・自己書込みの扱い——を、言語に
依存しない契約として固定する。

1. **成果物契約**。`build.sh` 経路のビルドは一時ファイルへ書いてから `dist/filter.wasm` へ **atomic rename**
   する。`plecto dev` が読むのは `dist/filter.wasm` **だけ**で、`dist/` 内の glob 探索はしない。ビルドが
   失敗（非 0 終了、または `dist/filter.wasm` の欠落）したときは、前回成功した artifact がそのまま残り、
   conformance も署名も OCI layout 書込みも manifest 書換えも SIGHUP も走らない。これは [[000065]] が
   conformance について確立した fail-closed（非合格ビルドは何も触らない）を、**build 層まで下ろした**ものである。

2. **起動契約**。フィルタ project root に `build.sh` が**存在すれば**、`bash build.sh` を cwd =
   フィルタ project root で起動する。**実行ビットは見ない**。存在しなければ現行の cargo +
   `wasm32-unknown-unknown` + `ComponentEncoder` 経路を使う（Rust テンプレートの後方互換）。二経路の収束点は
   ファイルではなく **component の bytes** であり、後段（conformance → 署名 → OCI layout → digest 書換え →
   SIGHUP）は経路によらず同一のコードを通る。cargo 経路は今までどおり `dist/` を作らない。

3. **watch 契約**。watcher はフィルタ project root を再帰監視し、除外集合に該当する event を落とす。除外集合は
   実装の内部定数ではなく **versioned な契約データ**として本 ADR が持つ。debounce は現行の 300ms のままとする。

   **除外集合 v1** — project root からの相対パスが次の prefix にマッチしたら drop:

   ```
   .git/  target/  node_modules/  dist/  artifacts/  generated/  _build/  wit/deps/
   ```

   ファイル名が次の glob にマッチしたら drop（editor と rename-replace の中間物）:

   ```
   *.tmp   .#*   *~   *.swp
   ```

   **VCS の追跡状態には委譲しない**。`.gitignore` は言語ごとに違い、ゲストの project は独立した repo に置かれ得る
   （scaffold は `git init` しない）ので、監視の可否を VCS に預けると「書き忘れた無視パターン」が rebuild ループに
   化ける。集合を版付きの data として持つことで、新しいツールチェーンの恒久出力を足す判断は必ず版上げとして
   可視化される。MoonBit の `_build/` を v1 に最初から含めるのはこの理由で、既知のツールチェーンの穴を初版に
   残す理由が無い。生成コードの置き場を `generated/` に統一するのも同じ集合の一部である。

4. **不変条件**。`build.sh` は**除外集合の外に書かない**。生成 binding は `generated/`、成果物は `dist/`、
   WIT の vendoring は scaffold 時だけ（[[000109]] Decision 3 と対をなす: あちらが「build は WIT を書かない」を
   保証し、こちらが「書かれても再ビルドしない」を保証する）。唯一の例外は **収束する書込み**——lockfile の初回
   生成（`Cargo.lock` / `go.sum`）のように、余分な rebuild が一度走って止まるもの。収束しない書込みを除外集合の
   外へ出す `build.sh` は、この契約に違反している。

5. **manifest 自己書込み**。digest の書換えは (1) 直前に現ファイルを読み直して digest だけを差し替える
   read-modify-write（operator の同時編集を消さない）、(2) 同一ディレクトリの一時ファイルへ書く、(3)
   `manifest.toml` へ atomic rename、(4) 書いた bytes の full-content hash を pending として記録、の順で行う。
   watcher 側は **pending hash と一致する `manifest.toml` の event を、一致しなくなるまで全て drop する**。
   「一回だけ consume」にすると、1 回の書込みが複数 event に割れる rename-replace で余分な rebuild が走る。
   最初に hash の異なる event が来た時点で pending を捨て、operator edit として対象フィルタと `LoadOptions` を
   再解決する。operator が dev の書いた内容と bytes 単位で同一な状態へ revert した場合は自己書込みと区別できず
   rebuild しない——これは意図的な受容で、次の実質的な編集で復帰する。

6. **初回動線**。JS スキャフォールドの `build.sh` は `node_modules` が**不在のときだけ** `npm ci` を自走する
   （毎回走らせると `npm ci` が `node_modules` を作り直し、インナーループが遅くなる）。そして scaffold 完了
   message が案内するコマンドは、**そのまま実行して通る**ことを完了条件とする。案内は workspace root から
   `plecto dev <name>` を叩く形へ直し、フィルタ project root と dev 鍵の trust root を食い違わせない。

**検討した代替案と却下理由**:

- **VCS-aware 監視（`.gitignore` へ委譲する）** — 言語ごとの慣行をそのまま使えて記述量は最小だが、scaffold は
  `git init` しないので生成直後は無視パターンが一つも効かず、ゲストの project が独立 repo に置かれれば
  リポジトリ側の設定も届かない。無視パターンの書き忘れが「静かに遅い」ではなく **rebuild ループ**という形で
  出るため、失敗のコストが非対称に大きい。却下。
- **監視対象の allow-list を列挙する（`filter.js` / `main.go` / `src/` / `go.mod` …）** — 誤検知はゼロに近づくが、
  拾うべきファイル名の一覧は言語ごとに違う。つまり [[000065]] が CLI から追い出したい**言語ディスパッチが
  watcher の形で CLI に戻る**。新しい言語を足すたびに CLI のコードを触ることになり、`build.sh` へ委ねた意味が
  消える。却下。
- **`build.sh` が成果物パスを宣言する（stdout の最終行 / 環境変数）** — 複数成果物や名前の自由度に対応できるが、
  「宣言し忘れ」という新しい失敗モードを作り、宣言の書式（stdout のどの行か、ログと成果物パスをどう分けるか、
  quoting、相対/絶対）を仕様として固定・検証するコストが要る。固定パス一本ならその全部が消える。却下。
- **`dist/` 内の単一 `*.wasm` を glob で拾う** — 既存の `dist/filter_<name>.wasm` をリネームせずに済み、移行が
  無料になる。しかし中間生成物や旧成果物が同居した瞬間に曖昧になり（現に MoonBit の `build.sh` は
  `dist/.embedded.wasm` を経由する）、「どれを読んだか」がビルドごとに変わりうる。固定名は曖昧さを構造的に
  消す。却下。
- **生成コードの置き場を `.plecto-build/` にする** — dot 始まりなら大半のツールが自然に無視し、除外集合を
  短くできる。しかし Go のツールは `.` / `_` で始まるディレクトリをパッケージ探索から除外するため、そこに
  binding を置くと **Go ゲストはそもそもビルドできない**。可搬性を失う最適化は採らない。却下。
- **実行ビットで `build.sh` 経路へ分岐する** — 「実行できるものだけ実行する」は素直だが、scaffold は
  `std::fs::write` で 0644 のファイルを書く（in-tree の 7 本が 0755 なのは人手で付けた結果）。分岐条件に
  すると、生成直後の project が**黙って cargo 経路へ落ちる**——Rust ではないので当然失敗し、原因はパーミッション
  という、最も追いにくい形の失敗になる。`bash build.sh` で起動する以上、実行ビットは意味を持たない。却下。

## Consequences

### Pros

- 言語ディスパッチが CLI から消える。conformance → 署名 → OCI → digest → SIGHUP という後半は、ゲストが何語で
  書かれていても同一のコードを通る。新しい言語の追加は `build.sh` を書くことに縮む。
- 非 Rust ゲストが初めてインナーループに入れる。[[000065]] の TTFVF は Rust 以外でも計測対象になる。
- rebuild ループがクラスごと塞がる。生成物・binding・artifact・自己書込みの 4 種類すべてに対して、
  「どこへ書かれるか」（除外集合）と「誰が書くか」（[[000109]] の vendoring 一点化）が静的に決まる。
- fail-closed が build 層まで下りる。壊れたビルドは前回成功 artifact を置き換えず、`dist/filter.wasm` は
  常に「最後に成功した component」を指す。atomic rename により、途中状態のファイルが読まれることもない。
- 除外集合が versioned な data になり、実装の内部定数ではなくなる。テストが集合そのものを固定でき、
  「いつ何を足したか」が決定の履歴として残る。
- 成果物名が三通り（`dist/filter_<name>.wasm` / `dist/my_filter.component.wasm` / 未定義）から一本になり、
  docs・テスト・example・スキャフォールドが同じパスを指す。
- 案内どおりに叩けば通る初回動線になる。scaffold 完了 message が、署名検証で落ちる手順を案内しなくなる。

### Cons / Tradeoffs

- **一括リネームの波及が大きい**。in-tree `build.sh` 7 本、`build.mjs` 2 本、ホスト側テスト 4 本の既定パス定数
  （`polyglot.rs` 3 / `polyglot_tier_b.rs` 1 / `tokenlimit.rs` 2 / `tokenlimit_tier_b.rs` 1）、example README
  3 本、`writing-a-filter.md` の conformance 例を同時に直す破壊的変更になる。加えて Go ゲストの binding 出力を
  `internal/` から `generated/` へ移す是正（`.gitignore` と import 行を含む）、JS ゲストの無条件 `npm ci` を
  条件付きへ変える是正が要る。契約 0.1.0 の conformance フィクスチャはインナーループの導線に無いため、
  据え置く判断も同時に要る。
- 除外集合は versioned な契約データなので、新しいツールチェーンが未知の恒久出力を作るたびに **ADR の版上げ**が
  必要になる。手軽な「とりあえず無視パターンを足す」ができないのは意図した摩擦だが、摩擦であることは確かである。
- operator が dev の書いた manifest と bytes 単位で同一な状態へ revert した場合、自己書込みと区別できず rebuild
  しない。Decision 5 のとおり意図的な受容で、次の実質的な編集で復帰する。
- lockfile の初回生成では、収束するとはいえ余分な rebuild が一度走る。初回だけ「保存していないのに二度ビルドされた」
  ように見える。
- `bash build.sh` は POSIX シェルの存在を前提にする。Windows ネイティブでは動かず、WSL 等が前提になる。cargo 経路は
  従来どおりシェルに依存しないので、Rust だけは影響を受けない。
- ビルドは開発者マシン上の任意コード実行である。`plecto dev` が走らせるのは開発者自身の project の `build.sh` で
  あって、ホストが untrusted ゲストへ貸す能力とは別の信頼領域だが、CI がこの経路を踏む場合は「誰が書いた
  `build.sh` か」が信頼の前提になる点は明示しておく。
- **再検討条件**: (a) `build.sh` がホスト依存（ツールチェーンの版・OS・PATH）で再現不能になったら、言語別の
  ピン済みコンテナビルドを評価する（再現性と運用の単純さのトレードオフ）。(b) 除外集合 v1 の外に恒久出力を置く
  ツールチェーンが増えたら v2 として版上げする——その際、集合が長くなりすぎたなら「build.sh が書き先を宣言する」
  却下案を再評価する余地がある。(c) Windows ネイティブでの `plecto dev` 需要が実測で出たら、起動口の抽象を
  シェル非依存にする判断を別 ADR で行う。
