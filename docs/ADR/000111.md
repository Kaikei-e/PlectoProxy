# 実行時に尊重できない `otlp_endpoint` の値を validate と起動で fail-closed に拒否する

## Status

accepted — 実装は本スライスの後続コミットで行う（TDD、RED → GREEN）。

## Date

2026-08-15

## Affected Components

- control plane（`plecto-control`）— `crates/control/src/manifest/observability.rs` に `Observability::validate()` を新設。`State::validate()` / `Listen::validate()` と同列に `validate_manifest`（`crates/control/src/lib.rs:384-385` の並び）へ配線し、起動経路は `build_state_backend` が `state.validate()` を再呼びする先例（`lib.rs:540`）に倣って `add_otlp_buffer`（`lib.rs:560-569`）からも同じ検査を呼ぶ
- fast path（`plecto-server`）— `crates/server/src/otlp.rs:55-72` の `traces_uri` は変更しない。manifest を経ずに `ServeConfig` を組むライブラリ利用者に対する fail-soft の最終防壁として残る
- docs — `docs/features.md` の Observability 行と `docs/operations.md` に、輸送制約と推奨構成（後述）を 1 行ずつ
- CHANGELOG — pre-1.0 の Changed。移行先（ローカル collector の平文 endpoint を指す）を明記する

## Context

`[observability] otlp_endpoint`（[[000040]] が導入）は OTLP/HTTP collector の base URL を取り、
exporter が `/v1/traces` を付与する。輸送は平文 HTTP のみで、`crates/server/src/otlp.rs:51` の
クライアントは TLS 経路を持たない。`https://` を渡したときの挙動は fail-soft である:
`traces_uri`（`otlp.rs:55-72`）が `error!` を 1 行出して export を無効化し、データプレーンは動き続ける。

問題は**その手前に一度も止まる場所が無い**ことである。`plecto validate`（[[000046]]）の
`validate_manifest`（`crates/control/src/lib.rs:370-418`）は `manifest.observability` を一度も読まず、
`Observability` は `validate()` を持たない素の serde struct である。実測（開発者調査 — Alt 本番運用
フィードバック第 2 次、2026-08-15）: `otlp_endpoint = "https://collector.example.invalid:4318"` に対して
`plecto validate --resolve` は `manifest OK` / exit 0 を返す。運用者が得るのは緑の validate、清潔な起動、
1 行の error ログ、そして**永久に空のトレース**である。制約の初出はソースのエラーメッセージであり、
`docs/features.md` / `docs/ROADMAP.md` は「OTLP network export」とだけ述べる。

これは [[000101]] が塞いだ `[chain]` と構造的に同じ形——「検証を通るが実行されない設定」——の
**値レベルの再発**である。[[000101]] は不変条件を「manifest のフィールドは検証されるか実行されるかの
どちらかであってはならず、両方であるか、拒否されるかのいずれか」と立てた。`otlp_endpoint` の
`https://` はフィールドではなく値だが、同じ試験に落ちる: validate が受理する値を、serving バイナリは
尊重しない。

外部規範との整合も確認した（一次情報は OTLP Exporter 仕様
<https://opentelemetry.io/docs/specs/otel/protocol/exporter/>、Stable）:

- 仕様は endpoint の URL について "The implementation MUST honor the following URL components:
  scheme (`http` or `https`) …" とし、OTLP/HTTP では "OTLP/HTTP always uses the scheme provided
  for the endpoint" ——スキームが輸送セキュリティの唯一の決定因で、gRPC の `insecure` に相当する
  逃げ道は無い。**したがって現行実装は「http-only が仕様適合」なのではなく、MUST honor の
  平文サブセットを実装している**。この位置づけを docs にもそのまま書く。
- `https://` を受理して平文で送る・黙って既定値に読み替える、のどちらの fail-soft も仕様の
  precedent に無い。宣言的設定ファイルに適用されるのは fail fast の precedent である:
  configuration/sdk（"Parse SHOULD return an error if … does not conform"）と error-handling 原則 2
  （"The API or SDK MAY fail fast … because of a bad user config … but MUST NOT cause the
  application to fail later at runtime"）。**manifest は宣言的設定ファイルなので、静的拒否への移行は
  この precedent に乗る変更**であり、現行の「実行時に沈黙で無効化」は precedent の無い第三の形である。
- TLS collector へ出したい運用者への標準解は collector の **agent パターン**
  （<https://opentelemetry.io/docs/collector/deploy/agent/>: "a Collector instance that runs
  alongside the application or on the same host, such as a sidecar or DaemonSet"）——producer は
  ローカル collector へ平文 OTLP/HTTP で出し、TLS は collector が張る。gateway パターンの利点として
  仕様側が挙げる "centrally managed credentials" は、TLS 資材を producer でなく collector に置く
  根拠でもある。

`CLAUDE.md` コア原則との関係: **fail-closed**（設定ミスが静かに起きない）を設定面の値レベルへ適用し
直すものであり、データプレーンには一切触れない（テレメトリの設定ミスで配信を止めない、という
[[000040]] の判断は維持する——止めるのは「設定を受理する時点」であって「リクエストを流す時点」ではない）。

## Decision

1. **`Observability::validate()` を新設し、`otlp_endpoint` が `Some` のとき「スキームが `http://`
   であること」「base URL としてパース可能であること」を検査する。** 違反は `ControlError` の専用
   エラーで fail-closed に拒否する。`https://` も `grpc://` も裸の `host:port` も同じ拒否に落ちる——
   仕様の MUST honor が挙げる集合の外か、実装が尊重できないスキームだからである。一方で
   **ポート省略やパス無しは拒否しない**（仕様が明示的に許す形。ポート既定は RFC 7230 の規則に従う）。
   フィールドの意味は [[000040]] のまま base URL セマンティクス（exporter が `/v1/traces` を付与、
   `OTEL_EXPORTER_OTLP_ENDPOINT` 相当）であり、これも docs に明記する。
2. **検査は静的検証と起動の双方で効かせる。** `validate_manifest` への配線（`plecto validate` /
   [[000046]]）に加え、`build_state_backend` が `state.validate()` を build 経路で再呼びする先例
   （`crates/control/src/lib.rs:540`）に倣い、起動経路の `add_otlp_buffer` からも同じ検査を呼ぶ。
   validate だけに置くと、manifest を直接読ませた起動が素通りする非対称が残るためである。
   なお `[observability]` は startup-fixed（[[000040]]、content hash 対象外）なので、reload 側に
   新しい検査点は生じない。
3. **診断は次の一手を渡す。** [[000101]] 決定 2 と同じ規律: 「輸送は平文 OTLP/HTTP のみ（TLS export
   は未実装）」「TLS collector へは同一ホストのローカル collector（agent パターン）を平文で指し、
   TLS は collector に張らせる」の二点をエラーメッセージに含める。
4. **`docs/features.md` と `docs/operations.md` に制約を 1 行ずつ明記する。** 「平文 OTLP/HTTP のみ。
   TLS collector へはローカル collector（agent パターン）経由」。`docs/ROADMAP.md` の M5 "landed" は
   据え置く——機能は landed であり、これは境界条件である。
5. **`plecto-server` の `traces_uri` fail-soft ガードは据え置く。** manifest 検証を経ない
   ライブラリ利用者（`ServeConfig` を直接組む consumer）への最終防壁であり、その場合の
   「データプレーンを止めない」は依然正しい。manifest 経路では本決定によりこのガードへ
   到達しなくなる。

### 検討した代替案と却下理由

- **TLS export を実装する** — 根本解だが、CA バンドル・クライアント証明書・検証ポリシーという
  設定面が一式付いてくる。標準解（agent パターン）が存在し、TLS 資材の管理はそもそも collector 側に
  置くのが仕様側の推奨でもある。需要の一次データも無い（当該運用者は同一 Docker network 内の
  collector に平文で出しており実害が無い）。却下（再検討条件として残す）。
- **実行時 fail-soft のまま docs だけ直す** — [[000101]] が同じ形で確認したとおり、fail-closed な
  製品において、検証を通るが実行されない設定の答えはドキュメントではない。散文は実地で読まれない。却下。
- **警告して未設定扱いにする（export を黙って無効化）** — OTel の env-var 面の precedent
  （enum の "warn and gracefully ignore"）に似るが、endpoint の型は String でありこの規則の対象外。
  なにより「トレースが出ない」という現象そのものが今回の被害であり、それを仕様面で追認する形になる。却下。
- **起動でのみ拒否し validate は素通しにする** — `plecto validate` の緑は CI ゲートとして使われる
  （[[000046]]）。文字列を見れば決まる検査を実行時まで遅らせる理由が無く、`deny_unknown_fields` が
  タイポに対して果たしている役割と同じ場所で果たすべきである。却下。

本決定は新しい設計原則を導入しない。[[000101]] の不変条件を manifest フィールドの**値**へ拡張する:
**validate が受理する値は、serving バイナリが尊重する値でなければならない。**

## Consequences

### Pros

- 「緑の validate ＋ 清潔な起動 ＋ 空のトレース」という組み合わせが構造的に成立しなくなる。
- 診断が agent パターンを名指しするので、拒否に当たった運用者は標準構成へ検索なしで到達する。
- 現行の「実行時に沈黙で無効化」という precedent の無い挙動が、宣言的設定の fail fast という
  文書化された precedent に揃う。
- `plecto validate` の緑が `[observability]` にも及び、静的検証と serving 実体の乖離が一つ減る。

### Cons / Tradeoffs

- **`https://` を書いていた既存 manifest は起動が止まる。** その構成でトレースは元々 1 本も
  出ていないので実運用の損失は無いが、「動いていたプロセスが上げ替えで起動しなくなる」体験では
  ある。CHANGELOG の Changed に移行注記（ローカル collector の平文 endpoint を指す）付きで載せる。
- manifest 経路とライブラリ直組み経路で挙動が二層になる（前者 fail-closed / 後者 fail-soft）。
  二層であること自体は `build_state_backend` と同型で、ライブラリの API 文書に一行で足りる。
- スキーム検査は輸送実装と暗黙に結合する。TLS export を実装する日が来たら、この検査の受理集合を
  同じ変更で広げること（広げ忘れると今度は「実装が尊重できる値を validate が拒否する」逆向きの
  乖離になる）。
- **再検討条件**: TLS export の需要が一次データとして立ったとき（agent パターンを置けない制約環境
  など）、TLS export の実装と受理集合の拡張を一つの決定として設計する。
