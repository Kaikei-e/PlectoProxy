# route に運用者が名指しできる名前を与え、リクエスト系メトリクスへ `route` ラベルを足す

## Status

proposed — 決定の記録であって着地報告ではない。実装は本スライスに含めず、後続スライスが RED から行う。

## Date

2026-08-15

## Affected Components

- manifest（`plecto-control`）— `Route`（`crates/control/src/manifest/route.rs:16`）に任意の `name: Option<String>` を追加。既定値は `match.path_prefix`（`RouteMatch.path_prefix` は必須フィールドなので常に定まる）。解決後の名前が衝突する manifest は validate / 起動 / reload で拒否
- fast path（`plecto-server`）— `ServerMetrics`（`crates/server/src/metrics.rs`）の `plecto_requests_total`（現在 `status_class` の固定 5 スロット、`metrics.rs:94`）を route 名でキーした系列に拡張。`plecto_rate_limited_total` にも `route` を足す。duration ヒストグラムは今回入れない（後述）
- アクセスログ — `route` フィールドを契約に追加（[[000099]] 決定 2 の手続きに従い CHANGELOG の Changed へ）
- docs — `docs/operations.md` のフィールド契約表と、メトリクスの series budget の記述

## Context

[[000099]] は route ラベルを**却下**し、再検討条件 (a)（route ラベルと `[route] name` の設計）に置いた。
却下理由は二つ: `ServerMetrics` がプロセス寿命を持つためカーディナリティが「現行 manifest の route 数」
ではなく「起動以降に存在した全 route 名の履歴」で有界になること、そして route に名前が無く
`[route] name` の設計（必須/任意、未設定時の扱い）を先に要すること。本 ADR はその設計を行う。

再検討条件 (a) の文言は「**複数の運用者**から per-route の内訳要求が出たとき」であり、厳密には
満たされていない——一次データは同一運用者の第 2 次フィードバック（開発者調査 — Alt 本番運用
フィードバック第 2 次、2026-08-15）である。それでも今決めておく理由は状況の変化にある:
0.7.0 で `[route.timeouts]`（[[000102]]）と `[route.headers]`（[[000100]]）が入り、**route は設定の
単位として明確に太った**。タイムアウトもヘッダも per-route で宣言できるのに、その route が 5xx を
出しているかは per-route で観測できない。宣言の単位と観測の単位の乖離は、宣言面が成熟するほど
広がる。加えて同フィードバックの実測で、15 ルートの構成が今もログ・メトリクス・エラーのどこでも
route を名指しできないことが確認された（0.8.0 時点の `plecto_requests_total` のラベルは
`status_class` のみ）。status を proposed に置くのはこのためで、受理は「決めた設計が要求と
釣り合うか」の判断として別途行う。

外部規範（一次情報を当日確認）:

- Prometheus 公式のラベル指針は、値集合が**有界で既知**のラベルを本来の用途とし、リクエスト由来の
  非有界値を明示的に禁じる（"Do not use labels to store dimensions with high cardinality …
  such as … other unbounded sets of values" —
  <https://prometheus.io/docs/practices/naming/>）。route 名は manifest 宣言由来なので正しい側に居る。
  一方で同じ指針は "try to keep the cardinality of your metrics below 10" / "over 100 …
  investigate alternate solutions" とも言う（<https://prometheus.io/docs/practices/instrumentation/>）。
  route × 5 status class は経験則の 10 を数ルートで超えるので、**予算化された例外**として扱う必要がある。
- HTTP メトリクスのセマンティクス標準は、route 属性を「マッチした route テンプレート」と定義し、
  低カーディナリティを MUST とし、**生の URI path による代用を MUST NOT とする**
  （<https://opentelemetry.io/docs/specs/semconv/http/http-metrics/>）。route にマッチしなかった
  リクエストへリクエスト由来の値を貼ることは、この両規範に同時に反する。
- ラベル値の欠落は表現できない: 空文字のラベル値はラベル不在と同値であり
  （<https://prometheus.io/docs/concepts/data_model/>）、同一 MetricFamily 内の系列は同じラベル集合を
  持つべき（OpenMetrics）。**「無名 route はラベル省略」という設計は成立せず、既定値は実在する
  非空値でなければならない**——`name` の既定を `path_prefix` の値に定める根拠がこれである。
- 系列が既知集合なら 0 で事前登録するのが指針（"export a default value such as 0 for any time
  series you know may exist in advance"）。manifest 宣言由来だからこそ可能になる性質で、
  リクエスト由来ラベルでは原理的に満たせない。
- ヒストグラムは classic 形で 1 ラベル集合あたり `buckets + 2` 系列を要する
  （<https://prometheus.io/docs/practices/histograms/>）。route ラベルをカウンタに足すコストの
  約一桁上であり、**per-route ヒストグラムを禁じる規範は無い**（参照実装自身が handler ラベル付き
  duration ヒストグラムを出している）が、コストとして先送りする判断は "start with no labels and
  add more labels over time as concrete use cases arise" の線に乗る。

`CLAUDE.md` コア原則との関係: [[000029]] 採用基準 (i) の observability = native 適格の内側であり、
[[000099]] が立てた「出力の形は実装レイヤの既定に委ねず、運用者向けの面として明示的に選ぶ」の続きである。

## Decision

1. **`[[route]]` に任意の `name` を足し、既定値を `match.path_prefix` の値とする。** 必須にしない——
   単純な manifest に手を増やさない（運用の単純さ）。既定が常に定まるのは `path_prefix` が
   `RouteMatch` の必須フィールドだからであり、空文字ラベルの禁則により「未設定なら省略」は
   設計として成立しない（Context の規範）。
2. **解決後の名前集合の一意性を fail-closed に検証する。** host / method / header / query の差だけで
   分かれた route は `path_prefix` を共有し得る（[[000034]]）。既定名が衝突する manifest は
   validate / 起動 / reload で拒否し、診断は「どの route に明示 `name` を書くか」を名指しする。
   黙って連番を振らない——観測面の識別子を実装が発明すると、運用者のダッシュボードが manifest の
   並び替えで壊れる。
3. **`plecto_requests_total` と `plecto_rate_limited_total` に `route` ラベルを足す。カウンタ先行、
   duration ヒストグラムは今回入れない。** ヒストグラムの見送りは規範ではなくコストの判断である
   （`routes × (buckets + 2)`）。per-route レイテンシの要求が立ったときに、bucket 数の削減や
   native histogram を含めて別途決める。
4. **route にマッチしなかったリクエストは固定センチネル `route="unmatched"` で数える。** 除外では
   なくセンチネルにするのは、`plecto_requests_total` の合計がリクエスト総数であり続けるためである。
   値は固定文字列であり、リクエスト由来の値（生 path / Host）は**決して**入れない（Context の
   MUST NOT）。manifest は `name = "unmatched"` の宣言を予約語として拒否する。
5. **系列は manifest 由来の全 `route × status_class` を 0 で事前登録し、reload で新 route を追加
   登録する。除去された route の系列はプロセス寿命の間残す（値は凍結）。** [[000099]] が挙げた
   「履歴で有界」という性質はこの設計で受容する——カウンタを reload で消すと `rate()` が欠落と
   リセットを区別できなくなるためで、上限は「プロセス起動以降に宣言された route 名の和集合 × 5」、
   これも運用者の宣言でのみ増える。exposition のラベル値エスケープは [[000099]] 実装時の先例に従う。
6. **series budget を docs に明記する。** `plecto_requests_total` は経験則（cardinality < 10）を
   意図的に超える数少ない系列であると宣言し、上限が manifest 有界であること、目安（例: 20 route ×
   5 class = 100 系列）を `docs/operations.md` に書く。予算を暗黙にしない。
7. **アクセスログに `route` フィールドを足す。** [[000099]] 決定 2 の契約手続きに従い、型付き一覧へ
   追記し CHANGELOG の Changed に載せる。unmatched は同じセンチネル値。これで route は
   ログ・メトリクスの両面で同じ名前で名指しできる。

### 検討した代替案と却下理由

- **`name` を必須にする** — 一意性は単純になるが、1 route の manifest にも手を増やす。既定値が
  常に定まり衝突時のみ明示を要求する形（決定 1+2）が、書く量と安全性の釣り合いで勝る。却下。
- **`name` フィールド無しで `path_prefix` をそのままラベルにする** — フィールド追加が要らない。
  しかし prefix 共有 route を区別できず（決定 2 の衝突がそのまま観測面の混線になる）、prefix の
  変更が運用者のダッシュボードを黙って壊す。名前は「manifest の編集と観測面の同一性を切り離す」
  ためにある。却下。
- **unmatched を系列から除外する** — カーディナリティは 1 減るが、`plecto_requests_total` の合計が
  「route にマッチした分だけ」という但し書きを恒久的に背負う。no-route 404 はまさに運用者が
  気づきたい信号でもある。却下。
- **`plecto_route_info` 型（info metric）で name → path_prefix / upstream 等を正規化して持つ** —
  OpenMetrics の "Labels which could be applied many MetricFamilies are candidates for being
  moved into _info metrics" に沿う設計で、将来 route の属性を増やすなら正しい形。ただし今日
  ラベルは `route` 1 個であり、正規化するものがまだ無い。info metric の「プロセス寿命中不変
  SHOULD」と reload の相性という論点も付く。要求が `route` 以外の属性に及んだときの再検討条件に
  置く。却下（現時点）。
- **duration ヒストグラムにも同時に足す** — 決定 3 のとおりコストで先送り。要求の一次データは
  「どの route が 5xx を出しているか」であり、カウンタで答えられる。却下（現時点）。

本決定は [[000099]] を amend し、その再検討条件 (a) を設計として具体化する。新しい設計原則は
導入しない。要点は「**観測面の識別子は運用者の宣言に由来し、実装が発明せず、リクエストが
汚染しない**」の一点である。

## Consequences

### Pros

- 「そのルートだけ 504 が出ている」に `/metrics` が答えられる。宣言の単位（route）と観測の単位が
  一致し、[[000102]] / [[000100]] で太った route 設定面の帰結を per-route で確認できる。
- ラベル値集合が manifest 有界かつ事前登録されるので、欠落系列の PromQL 問題（存在しない系列との
  演算）が構造的に起きない。
- アクセスログとメトリクスが同じ `route` 名を使い、ログ→メトリクス間の突き合わせが名前だけで通る。
- 一意性検証により、観測面の識別子の衝突が設定ミスとして validate で死ぬ（fail-closed）。

### Cons / Tradeoffs

- **系列数が route 数に比例して増える。** 予算は manifest 有界だが、多ルート構成では exposition の
  サイズとスクレイプコストが目に見えて増える。決定 6 の budget 明記で暗黙化を防ぐに留まる。
- **除去された route の系列がプロセス寿命の間残る。** 長寿命プロセスで route を頻繁に入れ替える
  運用では、凍結系列が蓄積する。restart で消えるので有界だが、気になる運用者への説明を docs に要する。
- `name` の追加はアクセスログ契約とメトリクス面の同時変更であり、[[000099]] 決定 2 の手続きに
  従った CHANGELOG 記載と `.ja.md` 同期を要する。
- `route="unmatched"` は予約語になる。既存 manifest がこの名前を使っていた場合のみ移行が要る
  （実在の可能性は低いが、拒否は breaking として Changed に載せる）。
- **再検討条件**:
  - (a) per-route レイテンシの要求が一次データとして立ったとき — duration ヒストグラムへの
    `route` ラベルを、bucket 数と native histogram を含めて決める。
  - (b) route の属性（upstream 名・filter chain 等）でのスライス要求が立ったとき —
    `plecto_route_info` 型の正規化を決定 5 の系列寿命論点と併せて設計する。
  - (c) `plecto_filter_*` の filter-ID ラベル（[[000099]] 再検討条件 (c)）が立ったとき — 本 ADR の
    予算化・事前登録・センチネルの枠組みをそのまま適用できるかを確認する。
