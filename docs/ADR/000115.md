# 権威境界と資源の寿命をセキュリティレビューに基づいて補強する

## Status

accepted

## Date

2026-09-10

## Affected Components

- `plecto-server` — route/filter/forward に渡す authority を統一し、接続数に加えて処理中リクエストと残存データを数える。
- `plecto-control` — 各 filter の request body 出力を上限内に制限し、OCI source の解決先を宣言した root 配下に限定する。
- `plecto-host` — HTTP response body と TCP socket の実際の寿命を数え、起動時に永続状態の quota を復元する。
- reference filters / CI — 認可先を operator config に固定し、CORS の曖昧な入力を拒否し、独立 workspace の依存も検査する。

## Context

複数の担当による ingress、transport、WASM、host state、outbound、reference filter、供給網のレビューで、
権威の選択と資源の計数が処理の途中で分かれる問題を確認した。URI authority と `Host` が矛盾すると、
route の認証ポリシーと転送先に渡す host が一致しない。HTTP/3 の切断後も task を detach すると、
既に応答先のない処理が続く。body や socket が残っていても request hook や response headers の完了時点で
permit を返すと、同時数やメモリの制限を超えて資源を保持できる。永続 backend に対して quota をゼロから
開始することも、再起動を境に既存状態を無料で扱う抜け道になる。

[[000027]] が記録した「起動時に quota をリセットする」という制約を本 ADR で解消する。既存の接続 cap、
per-request 接続試行 budget、guest memory cap はそれぞれ有効だが、HTTP 多重化、trusted Store に残る
socket、transport 内の DATA frame、再起動後の保存量を単独では制限できない。

回帰テストでは、authority 不一致による未認証 route の選択、切断後に残る QUIC 処理、次の filter に届く
16 MiB 超の変換出力、未読 outbound body、65 個目の保持 socket、Redb の再オープン後の quota 回避、
キャンセル後や早期応答後の permit 早期返却を再現した。追加機能を有効にした全体検証では、共有 outbound
Tokio runtime の最終参照を async context で破棄すると CLI・shutdown・load failure が panic する問題も確認した。

この決定は [設計原則](../design-principles.ja.md) の P4（deny-by-default / fail-closed）と
P11（データプレーンで panic 禁止）を具体化する。権威と所有の境界を明示し、安全と単一ノードでの運用の単純さを優先する。

## Decision

1. **Ingress の authority を一度確定する。** route/filter/forward より前に URI authority と `Host` を検証し、
   大文字小文字・末尾 dot・既定 port を考慮して矛盾を拒否する。重複 `Host`、不正 authority、HTTP/1.1 の
   `Host` 欠落は 400 とする。HTTP/1.0 の Host-less form は維持する。HTTP/2・HTTP/3 で URI authority が
   あればそれを権威とし、任意の `Host` は一致を要求する。adapter が origin-form URI と単一の有効な `Host`
   だけを渡す互換経路では、その host を URI に設定する。両方欠落は拒否する。
   [RFC 9113 §8.3.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.3.1) の direct client が送る
   `:authority` 要件と、この adapter 互換経路は区別する。
   [RFC 9114 §4.3.1](https://www.rfc-editor.org/rfc/rfc9114.html#section-4.3.1) は HTTP/3 で authority または
   `Host` を要求する。単に `Host` を優先する代案は route と upstream の境界を再び分けるため採用しない。
2. **HTTP/3 の切断で残存 task を中止する。** 接続終了時の `JoinSet::detach_all` を `abort_all` に変更する。
   正常な graceful drain は先に処理を回収する既存経路を維持する。接続の寿命を超えた無制限な継続を認めない。
3. **request body の変換出力にも 16 MiB cap を課す。** chain 内の各 guest 出力を、次の filter や upstream に
   渡す前に検証する。超過は 502 / `request-body-guest-oversize` とする。入力のみの検査では、guest による増幅を制限できない。
4. **outbound HTTP の同時数を body の寿命まで保持する。** semaphore permit を response body の EOF・error・drop
   まで持たせる。dispatch からの absolute deadline で DNS/connect/headers/body を囲い、guest が body を poll
   しなくても driver の watchdog が停止させる。停止後も未読 body を保持する限り slot は使用中とし、次に terminal
   を観測するか drop するまで返却しない。headers の到着だけで slot を返す方式は採用しない。
5. **TCP live socket を Store 64 / Host 1,024 に制限する。** `wasi:sockets` resource の create/drop に計数を置き、
   create 失敗は予約を戻し、child resource による drop 失敗では slot を返さない。Store 破棄でも残量を返す。
   Host の枠は loaded filter と reload をまたいで共有する。既存の `max_connections` は per-request の接続試行数であり、
   意味を変更しない。trusted guest が未接続 socket を保持する場合も数える。
6. **永続状態の使用量を起動時に復元する。** `KvBackend::visit_entries` が整合した inventory を streaming callback
   で列挙し、Host の engine/runtime を生成する前に namespace ごとの entries と guest key/raw value bytes を復元する。
   MemoryBackend は lock、RedbBackend は read transaction で走査する。KV/counter/rate-limit の合算上限は namespace
   100,000 entries / 64 MiB、Host 5,000,000 entries / 1 GiB。読み取り不能、不正 namespace、計数 overflow は起動失敗。
   over-cap の既存状態は計上して警告し、増加を拒否しつつ対応 API による同サイズ更新・縮小・削除を許す。
   raw value の実際の長さを更新差分にも使う。全行コピーや、未対応 backend を空とみなす代案は採用しない。
7. **全 transport 共通で request lifetime を最大 1,024 に制限する。** `ServerState` の semaphore を入口で
   `try_acquire` し、飽和時は queue に積まず 503 / `request-overloaded`。blocking guest 呼び出し、background body
   drain、upgrade tunnel、response body、transport が保持する upload/response DATA まで参照を渡す。
   body 検査の共有予約予算 1 GiB も同様に、キャンセル後の blocking 処理と残存 transport data が終わるまで保持する。
   [`Bytes::from_owner`](https://docs.rs/bytes/1.12.1/bytes/struct.Bytes.html#method.from_owner) に permit を付随させ、
   frame の clone が body wrapper より長生きしても計数を維持する。
   response の予約は圧縮を終えた最終 DATA に付随させる。圧縮は新しい allocation を生成するため、入力側の
   `Bytes` だけに予約を持たせても出力には引き継がれない。検査から圧縮の組立までは応答と予約を同じ所有値で渡す。
   接続数だけの制限や、response headers / handler future の完了時に全枠を返す方式は採用しない。

並列のハードニングとして、全 host-state API の key を 1,024 bytes 以下とし、outbound の reserved floor に
`fec0::/10` を加えた。OCI source は非空の relative normal path に限定し、canonicalize 後も root 配下を要求する。
root 自体の symlink は許すが、中間 symlink による脱出は許さない。カレントディレクトリの bare manifest は従来どおり解決する。
`filter-extauthz` の認可先は `[filter.config] authz-url` とし、client の `x-authz-url` を採用しない。
CORS は重複 Origin / preflight request headers に許可を返さず、拒否も含めて適切な `Vary` を保持する。
actual response の CORS ヘッダーは operator 設定から構成し、upstream 由来の許可で拒否や credentials 設定を
上書きさせない。拒否時は既存の CORS 許可を削除する。最終応答のヘッダーで判定する
[Fetch の CORS check](https://fetch.spec.whatwg.org/#cors-check) に対し、この filter の operator 設定を権威とするための選択である。
admin の non-loopback bind は `plecto validate` で警告する。

供給網では、root workspace の既存全ポリシー検査に加え、追跡済みの独立 Cargo.lock を CI が動的に発見して
advisory 検査する。追加ツールの release archive はバージョンと SHA-256 を固定する。JWT の
RUSTSEC-2023-0071 例外は public-key verification のみを使う当該 guest の設定に閉じ、全体では無視しない。

共有 outbound runtime は Host と loaded filter が `Arc<OutboundRuntime>` で所有する。最後の参照の Drop で
`shutdown_background()` を呼び、async context 内の通常 `Runtime::drop` による panic を避ける。
Host だけの特殊な Drop では loaded filter が最後の owner になる経路を扱えないため、共有所有型に置く。
[Tokio 1.53.1 の仕様](https://docs.rs/tokio/1.53.1/tokio/runtime/struct.Runtime.html#method.shutdown_background) に従い、
開始済みの blocking DNS/I/O が同期的に終了する保証はしない。

追加レビューで、圧縮後の DATA が残る間に body 予約を返す経路と、CORS の拒否応答に upstream の許可が
残る経路を再現し、修正前の失敗を確認した。回帰テストは gzip / br / zstd、over-cap の両転送モード、
非圧縮で最後の DATA clone / slice まで予約を保持することと、実 WASM・response chain で CORS 設定が
upstream の許可を置き換えることを検証する。

最終検証では標準構成の 725 tests、`plecto/capabilities,plecto-host/streaming-body` を有効にした 819 tests が成功した。
いずれも failure / ignored は 0。`cargo clippy --all-targets --all-features --locked -- -D warnings`、
`cargo build --release --locked`、workspace と変更した guest の rustfmt、WIT vendoring 検査も成功した。多言語の外部 toolchain を必要とする
`polyglot-conformance` の実行と、CI 専用の全ジョブ実行をこの検証結果に含めない。

## Consequences

### Pros

- route、filter、upstream が同じ ingress authority を使い、曖昧な入力を policy 適用前に拒否できる。
- 切断・キャンセル・早期応答・再起動をまたいでも、保持している資源が quota の計数から消えない。
- WIT の変更や追加の外部サービスなしに、既存の sandbox と単一ノードの境界を補強できる。
- 再現テストにより、単なる status code だけでなく、残存 task、socket、frame、予約枠の寿命を検証できる。

### Cons / Tradeoffs

- request 1,024、socket 64 / 1,024 は固定の安全上限。長時間 tunnel や slow peer も枠を使用する。
  運用実績から構成可能にする場合も、有限の既定値と同じ寿命テストを維持する。既存の
  `plecto_requests_in_flight` metric は headers までの処理数であり、新しい admission の使用量ではない。
- DATA frame ごとの owner には小さな allocation が増える。payload 自体の追加コピーは行わない。
  最適化は早期応答・frame clone・キャンセルの回帰テストを維持した上で行う。
- 独自 `KvBackend` の既定 `visit_entries` は Unsupported で起動失敗となる。整合した inventory 実装への移行が必要。
  callback から backend に再入せず、backend の更新を一つの Host に所有させる。外部 writer の変更は quota に反映されない。
- 起動走査は entry 数に比例し、namespace ごとの tally を保持する。巨大な旧データでは起動時間が増える。
  1,024 bytes 超または UTF-8 で表せない旧 key は現在の API から操作できず、バックアップ後に停止状態で offline cleanup
  が必要。組み込み cleanup CLI はない。論理 quota は Redb ファイルの物理サイズ上限ではない。
- `streaming-body` preview は既定で off、production request path に未接続で、wall-clock I/O timeout も未実装。
  production 接続前に outer timeout と stalled I/O の cancellation/resource 回収テストを必須とする。
- 検証は上記構成と再現ケースに対する結果であり、すべての攻撃や外部構成の安全を保証するものではない。
