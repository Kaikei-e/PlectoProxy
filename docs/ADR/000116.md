# route の既定名に match.host を含め、host で分けたバーチャルホストを衝突させない

## Status

accepted — 本 ADR の変更（既定名規則）は実装・テストと同じ変更で着地する。[[000112]] 自体の実装は bf1c6c9（RED）/ a2725da（GREEN）で、いずれも未リリース（旧既定値を載せた公開リリースは無い）。

## Date

2026-09-25

## Affected Components

- manifest `Route::resolved_name` in `plecto-control` — `match.host` が宣言されている場合は `<host><path_prefix>`（host は小文字化、`path_prefix` はそのまま）を解決名とし、未宣言時は従来の `match.path_prefix` を返す
- `docs/operations.md` / `docs/operations.ja.md` naming section — route 解決名（naming）の既定値規則およびアクセスログの `route` フィールド契約の記述を更新
- `CHANGELOG.md` — `[Unreleased]` の `[[route]] name` 既定値およびマニフェスト検証（名前重複の fail-closed 拒否）の移行注記を改訂

## Context

[[000112]]（決定 1〜7）は route に運用者が名指しできる名前を与え、リクエスト系メトリクス（`plecto_requests_total` / `plecto_rate_limited_total`）へ `route` ラベルを追加する設計を定め、実装された（コミット `bf1c6c9` RED / `a2725da` GREEN、未リリース。旧既定値を搭載した公開リリースは存在しない）。

しかし、同 ADR の決定 2（解決後の名前集合の一意性を fail-closed に検証する。既定値は `match.path_prefix`）を実装したことで、最も一般的な多ルート構成であるバーチャルホスト——すなわち `path_prefix = "/"` を共有し `match.host` のみで分岐する複数の `[[route]]`——が既定で一意性違反の衝突（collision）を起こすことが判明した。これにより、各 route に明示的な `name` を付与しない限り、既存のバーチャルホスト構成のマニフェストはアップグレード後に `plecto validate`、起動、および SIGHUP reload のすべてで検証失敗し拒否されることになる。

[[000112]] の Cons / Tradeoffs に挙げられていた破壊的リスクは固定センチネル `unmatched` の予約語化のみであり、このバーチャルホストのケースは想定されていなかった。

リポジトリ内の実証（in-repo evidence）として、フルテストスイートの実行においてまさにこの問題によって 2 つのフィクスチャが失敗した:
1. `plecto/crates/server/tests/authority.rs` の host 分割ルート（`public.example` と `protected.example` がいずれも `path_prefix = "/"`）
2. `routing_adr34.rs` の method / header / query 分割ルート
加えて、canary example（ヘッダ分割）でも同様の衝突が確認された。

本問題は、`CLAUDE.md` のコア原則である「運用の単純さ（operational simplicity）」（単純なマニフェストに追加の手間を課さない）と「fail-closed」（曖昧な識別子の重複を許さず安全側に倒す）の調和に関わる。host + path-prefix による分割は運用者が既に宣言した明確な識別境界であり、これを既定名に反映させることで運用の単純さを損なわずに安全な fail-closed 一意性を両立させる必要がある。

## Decision

[[000112]] の決定 1 のみを amend する。

1. **`match.host` が宣言されている場合、route の既定名を `<host><path_prefix>` とする。**
   - host は小文字化（lower-case）する。[[000034]] においてルーティングは host を case-insensitive に照合するため、ルーティングが区別しない大文字小文字の差異を route 名が区別してはならない。
   - `path_prefix` はそのまま（verbatim）連結する。
   - 例: host `Public.Example` + `path_prefix = "/"` → `public.example/`
   - 例: host `api.example` + `path_prefix = "/v1"` → `api.example/v1`

2. **`match.host` が未宣言（wildcard / 全 host 対象）の場合、既定名は従来どおり `match.path_prefix` を維持する。**

3. **[[000112]] の他の決定事項（決定 2〜7）はすべて変更なく維持する:**
   - 解決後の名前集合の一意性検証は依然として fail-closed である（method / headers / query のみの差異で分割された route は、引き続き明示的な `name` を要する）。
   - `name = "unmatched"` は予約語として拒否し続ける。
   - 明示的な `name` 宣言が常に最優先される（明示 `name` が勝つ）。
   - route 名は常にマニフェスト宣言由来であり、決してリクエスト由来ではない。結合される host は `[route.match]` で**宣言された match 値**であり、受信リクエストの Host / authority ヘッダ値ではない（これは [[000112]] の Context が MUST NOT とした、リクエスト由来の値をラベルに入れない不変条件を守るためである）。

本決定は [[000112]] 決定 1 を amend するものであり、新しい設計原則は導入しない。`CLAUDE.md` コア原則の運用の単純さ（operational simplicity）と fail-closed の整合を維持する。

**検討した代替案と却下理由:**

- **[[000112]] をそのまま維持し、全バーチャルホストに明示的な `name` を要求する** — アップグレード時に最も一般的なマルチホスト構成のマニフェストを読み込めなくする。host + prefix は運用者が宣言した時点で既に一意な識別子として成立しており、明示名を強制しても可観測性上の実質的な利益（observability gain）がない。却下。
- **method / headers / query も既定名に含める** — 名前が過度に長くなり、ヘッダやクエリのマップ順序に依存して脆弱になる（order-sensitive）。また、それらの軸によるトラフィック分割は比較的稀であり、分割を行う運用者は通常その意図に応じた明確な名前を選ぶべきである。却下。
- **衝突時に連番を自動付与する（auto-number）** — [[000112]] 決定 2 で既に却下された方針。マニフェスト内の route の並び替えによってメトリクス系列の識別子が暗黙に変わり、運用者のダッシュボードやアラートを破壊する。却下。
- **セパレータ形式（例: `public.example|/`）や構造化された 2 ラベル構造（`host`, `route`）にする** — `<host><path_prefix>` という単純な連結で既に馴染み深い authority + path の形状として自然に読める。また 2 つ目のラベルを増やすと、単一の名前が既に担っている情報のためにラベルの組み合わせ爆発が起き、[[000112]] で定めた系列予算（series budget）を乗算で圧迫する。却下。
- **宣言された host の大文字小文字（case）をそのまま維持する** — ルーティング上は同一ホストとして扱われるルート（[[000034]]）に対して、大文字小文字の違いだけで 2 つの名前が存在し得ることになり、ルーティングと観測面の整合性を損なう。却下。

## Consequences

### Pros

- バーチャルホスト（vhost）マニフェストがマニフェストの修正なし（zero edits）でそのままロード・起動し続ける。
- ダッシュボード上で既定名自体がどのホスト・パス向けのルートかを自己記述的（self-describing）に示す。
- ラベル値は依然としてマニフェストの静的宣言に有界（manifest-bounded）であり、リクエスト由来のカーディナリティ爆発を起こさない。

### Cons / Tradeoffs

- host 指定を持つ route の既定名は、宣言された host を変更するたびに変化する（`path_prefix` が既に持っていた性質と同様。ダッシュボードやアラートの恒久的な安定性を保つには明示的な `name` を設定することが推奨される）。
- route 名の文字列が長くなる（`<host><path_prefix>`）。
- method / headers / query のみで分割された route は、依然として既定名が衝突するため明示的な `name` の指定が必要である。
- **再検討条件**: 運用現場の実態として method / headers / query 分岐による名前衝突が頻発し運用の摩擦となっている報告が寄せられた場合、既定名の生成規則をこれらの軸へ拡張することを再検討する。
