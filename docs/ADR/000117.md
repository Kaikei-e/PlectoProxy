# wasmtime 49.0.1 へロックステップ更新し、default-on 化された wide-arithmetic proposal をエンジンで明示無効化する

## Status
accepted

## Date
2026-09-25

## Affected Components
- `plecto/Cargo.toml` — `wasmtime` / `wasmtime-wasi` / `wasmtime-wasi-http` を 48.0.2 → 49.0.1、`wit-component` を 0.254 → 0.258。`spike/streaming-async/host` の独立 workspace も同時に bump
- `crates/host/src/engine.rs` / `streaming.rs` — `config.wasm_wide_arithmetic(false)` を GC / exception-handling の明示 off の隣に追加。`i64.add128` を含む component の拒否をテストで固定
- `crates/host/src/outbound_tcp.rs` — `HostResolveAddressStream::drop` が 49 で `async fn` になったことへの追随のみ
- `crates/host/Cargo.toml` — test 専用の `wat` を 1.258 へ
- `.github/workflows/ci.yml` / `release.yml` — wasm-tools CLI を 1.258.0（sha256 固定）へ

## Context

wasmtime 49.0.0 が 2026-09-21、49.0.1 が 2026-09-24 にリリースされた（MSRV 1.96.0 — 現行 toolchain
1.97.1 で無風）。一次ソース（crates.io、wasmtime の RELEASES.md、`v49.0.1` タグの `Cargo.toml`、
GitHub Security Advisories）で確認した事実:

- **セキュリティ修正**: 2026-09-24 に 49.0.1 / 48.0.3 / 36.0.16 が同時に出され、4 件の advisory を修正した。
  現行の 48.0.2 はいずれも影響範囲にあった。
  - GHSA-m63x-6p34-q65x（medium）— `call_ref` と exception `catch` で fuel 計量の一部が落ち、fuel 消費が指数的に増幅する
  - GHSA-jqpg-j7w6-42pr（low）— dynamic record lifting が hostcall の fuel 上限を超えて確保する
  - GHSA-c9gc-w9vx-w86p（medium）— `wasmtime-wasi-http` の outgoing body 書き込みで guest がホストメモリを枯渇させうる（DoS）
  - GHSA-j2g9-4prp-pf6h（medium）— `wasmtime-wasi` のファイルシステム datetime オーバーフローで guest がホストを panic させうる
- **新規 default-on proposal**: 49.0.0 で **wide-arithmetic** proposal（`i64.add128` / `i64.sub128` /
  `i64.mul_wide_*`）がデフォルト有効になった。[[000096]] が bump 手順として定めた「default-on 監査」に
  該当する。
- **同梱 wasm-tools 系列**: 49.0.1 は wasm-tools 0.258 系列（`wit-component` / `wit-parser` /
  `wasmparser` 0.258.0）を同梱する。[[000114]] により `wit-component` と CI の wasm-tools CLI はこの系列に
  揃える必要がある。
- **API 変更**: 本リポジトリに効いたのは `wasmtime_wasi` の `HostResolveAddressStream::drop` が
  `async fn` になった点のみ。WASIp2 で `WasiHttpHooks` が走るようになった変更（新メソッドはデフォルト実装つき）と、
  `wasmtime-wasi(-http)` で `p3` がデフォルト feature になった変更は、どちらもコード変更なしでビルドとテストが通る。

関係する Tenet は「deny-by-default capability」（[[000006]]）と「データプレーンで panic 禁止」。
後者は GHSA-j2g9-4prp-pf6h に直結する。Plecto はフィルタにファイルシステムを貸していないため
直接の到達経路はないが、影響範囲に入った依存を残す理由もない。

## Decision

1. **`wasmtime` / `wasmtime-wasi` / `wasmtime-wasi-http` を揃えて 49.0.1 へ bump する**。
   部分 bump で wasmtime スタックが二重にならないよう、workspace manifest に集約する既存方針を維持する。
   49.0.0 ではなく 49.0.1 を下限にするのは、上記の advisory 修正を確実に取り込むため。
2. **wide-arithmetic を両エンジン Config（`engine.rs` / `streaming.rs`）で明示的に無効化する**。
   GC / exception-handling（[[000096]]）と同じ扱い。挙動の差分をゼロに保つため、
   `i64.add128` を含む core module / component が engine に拒否されることをテストで固定する。
3. **`wit-component` を 0.258 へ、CI / release の wasm-tools CLI を 1.258.0 へ上げる**（[[000114]] の系列一致）。
   test 専用の `wat` はエンコーダの一致を必要としないので、最新の wasm-tools 系列を追う既存方針のまま 1.258 以上とする。

検討した代替案:

- **48.0.3 へのパッチ bump に留める** — advisory は 4 件とも 48.0.3 でも修正されるため、
  セキュリティの観点だけなら足りる。却下した理由は、Stage 1 以来の host async 線（[[000021]]）を
  最新 major に追随させる方針を取っていることと、48 系への backport が今後も続く保証がないこと。
  bump の差分は wide-arithmetic の off と `drop` の async 化の 2 点に収まり、コストが小さい。
- **wide-arithmetic を有効のまま貸す** — 算術命令が増えるだけで capability は増えず、sandbox 境界への
  直接の影響は小さい。それでも却下するのは、「ホストが貸すと決めていない wasm 機能面へ untrusted
  フィルタを到達させない」という [[000096]] の原則に例外を作らないため。貸すなら、利用するフィルタの
  需要が出た時点で専用 ADR で決める。
- **`wasmtime-wasi(-http)` を `default-features = false` にして `p3` を外す** — 依存木はわずかに縮むが、
  streaming / outbound 経路はすでに `component-model-async` を有効にしている。feature 一覧を
  手で維持するコストに見合わないため、今回は見送る。

具体化する Tenet: 「deny-by-default capability」をエンジンの wasm 機能面で維持すること
（[[000096]] で定めた bump 手順の 3 回目の適用）。

## Consequences

### Pros
- 4 件の advisory（fuel 計量の欠落・wasi-http のメモリ枯渇 DoS・wasi の datetime panic ほか）の影響範囲から外れる。
- untrusted フィルタへの露出面が 48 系と同一のまま 49 系に乗れる（挙動差分ゼロの bump）。
- 拒否テストによって、将来 Config の明示 off が誤って消えたときに CI が落ちる。

### Cons / Tradeoffs
- 明示 off が必要な proposal が 3 つになり、両エンジン Config に同じ設定が重複して並ぶ。
  次に default-on 化されるものが出たら、共通の関数に括り出すことを検討する。
- wasm-tools 系列の bump に伴い、CI の wasm-tools CLI の sha256 を手作業で更新する運用が引き続き残る。
- 多言語 guest の conformance（`polyglot-conformance` / `fat-guest`）と `cargo deny` は、この bump の
  ローカル検証では回しておらず、CI に委ねる。
- 再検討条件: wide-arithmetic を必要とするフィルタ（暗号・多倍長演算など）の需要が現れたとき。
  あるいは wasmtime がこの proposal を無効化できなくしたとき。
