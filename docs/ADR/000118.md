# glibc mallocアリーナ上限の既定を32へ引き上げる

## Status
accepted

## Date
2026-09-28

## Affected Components
- **fast path (plecto-server)** — `cap_malloc_arenas()` の出荷既定値を 4 から 32 へ変更。環境変数 `PLECTO_MALLOC_ARENA_MAX` の文字列パース（未指定・不正文字列は 32、負数は no-op、0 は上書きなし）を純関数 `parse_malloc_arena_max` として分離・検証。
- **benchmarks (bench/perf, harnesses)** — `bench-server` に加え、`load-balancing`・`tls-http`・`swap-bench` の全 4 通常 proxy ハーネスが Tokio ランタイム起動前に `cap_malloc_arenas()` を呼ぶよう統一。`run-perf.sh` は `BENCH_MALLOC_ARENA_MAX` 未指定時に環境変数を設定せず Rust 既定 32 を直接利用し、明示指定時は `PLECTO_MALLOC_ARENA_MAX` のみを注入し親環境の `MALLOC_*` / `glibc.malloc.*` を清掃、`LD_PRELOAD` を拒否。`arena_sweep.py` は `--arenas default,32` で出荷既定と明示 32 の同一挙動検証に対応。
- **operations (docs/operations.md, operations.ja.md)** — メモリアロケータ調整の仕様、基準ホストでの RSS 増加（peak +55%, settled +42%）、初期 cap 4 の維持方法（`PLECTO_MALLOC_ARENA_MAX=4`）、メモリ優先時の調整出発点（4〜16/24）、0（外部 glibc 設定尊重）を明記。

## Context

[[000038]] では、header-only フィルタの body ゼロコピー素通し（決定 1）に加え、body バッファが残る経路での glibc マルチアリーナ断片化を抑制するため、プロセス起動時にアリーナ上限を 4 に固定した（決定 2）。当時の「スループット悪化なし」という判断は、大きな body を扱う低 RPS 経路での観測に基づいていた。

2026-09-26 にローカルベンチマークを出荷構成（exec-time pinning による proxy 対 generator の物理コア分離、生データ保持）へ刷新したところ（この時点では upstream は同居 in-process）、高 RPS の認証（`/trusted`）および rate-limit 経路において、cap 4 で大幅なスループット低下が観測された（実アリーナ数や malloc mutex ロック待ちは直接計測しておらず、競合等の内部機構は仮説）。認証スループットにおいて、N=4（平均 72.15 kRPS）は N=32（平均 95.2 kRPS）比で約 24.2% 低く、glibc 既定（N=0、平均 97.45 kRPS）比で約 26.0% 低い。また rate-limit 経路でも N=4（平均 69.25 kRPS）は N=32（平均 81.55 kRPS）比で約 15.1% 低く、glibc 既定（平均 83.1 kRPS）比で約 16.7% 低い低下が確認された。

これを受け、2026-09-27 に以下の問題点を修正してアリーナ上限の選定試験を実施した:

1. **RSS 帰属と時間軸の分離**:
   - 旧計測（`run-perf.sh body`）の RSS は proxy と同居 upstream の合算値であり、負荷中の単一サンプルであった。
   - proxy、upstream、generator を別プロセス・排他的な物理コアに固定し、親環境から継承した `MALLOC_*` 環境変数および `GLIBC_TUNABLES`（`glibc.malloc.*`）を除去して upstream の条件を全セルで揃えた。各巡に upstream 直結の対照を置いて生成器・upstream が律速していないことを確認した上で、proxy 単体の負荷中 peak RSS（200ms 周期）と負荷停止後 15 秒の保持量（settled RSS）を独立して時系列採取する分離計測器 `bench/perf/arena_sweep.py`（手順: [`bench/methodology.md`](../../bench/methodology.md#2026-09-27--アリーナ既定値を判断するための分離計測t3)）を導入した。
2. **中間候補の再評価と T1 gate 帯の誤用是正**:
   - 有限値を 16 までしか測らず、glibc 既定で較正された T1 gate の帯を根拠に中間案を棄却していた判断を撤回した。ゲートの帯は既存条件の回帰検知用であり、既定値の選択基準にしてはならない。24 および 32 を候補に加え、スループットと RSS のトレードオフを再評価した。

### 分離計測条件（2026-09-27 選定試験）

- **ホスト**: x86_64、Intel Core i7-13700K（P コア 8 基 / SMT2 ＋ E コア 8 基、計 24 論理コア）、63GiB RAM、Linux 6.14、glibc 2.39。CPU governor は powersave、turbo は既定のまま。
- **コア分離**: proxy=`0-11`（P コア 6 基）、upstream=`16-19`（E コア 4 基）、generator=`12-15,20-23`（P コア 2 基 + E コア 4 基）。全プロセスが排他的な物理コアを使用。
- **測定構成**: proxy の `PLECTO_MALLOC_ARENA_MAX` のみを変更（4, 16, 24, 32, 0）。0 は `mallopt` による上書きを行わず glibc の既定動作に委ねる。親環境の malloc/tunables は除去、upstream は全セル同条件。
- **順序**: 4→16→24→32→0、続いて 0→32→24→16→4 の昇順・降順 2 巡。
- **RSS 計測**: `(N, route, round)` ごとに新規 proxy を起動。1MiB POST × 50 並列（VU）、warm-up 5 秒 ＋ 本計測 15 秒。`smaps_rollup` を 200ms ごとに読み、負荷中の最大値を peak、負荷停止後 15 秒の最後 2 秒平均を settled とする。
- **スループット計測**: 50 接続。oha で `/baseline` → `/noop-pooled` → `/trusted`（認証）を各 10 秒（初回 5 秒 warm-up）、3 回インタリーブ。rate-limit は k6 で 1000 key、各 5 秒 warm-up ＋ 10 秒計測、baseline と 2 回比較。各巡に upstream 直結の対照を実施。

関係する Tenet / 原則: **セルフホスト性 × 運用の単純さ**（多様な環境で破綻しない合理的な出荷既定値と、簡潔な環境変数上書き導線）、**根拠に従う**（分離計測による実測データに基づく選定）。

## Decision

[[000038]] の決定 2（アリーナ上限 4 の設定）を amend し、glibc malloc アリーナ上限の出荷既定値を **32** へ引き上げる。決定 1（header-only フィルタの zero-copy bypass）は維持する。

### 1. 既定値 32 の選定理由

2 巡の平均において、N=32 は glibc 既定動作（0）と比較してスループット低下を認証で -2.3%、rate-limit で -1.9% の小差に抑えつつ、body 経路の proxy 単体 peak RSS を約 335 MiB から約 260 MiB（-22.4%）、停止後 settled RSS を約 257 MiB から約 198 MiB（-23.0%）へ抑制した。

**「glibc 既定に近い高 RPS 処理能力と、body 経路でのメモリ保持抑制を両立する」** ことを 32 の選定理由とする。

この 32 は基準ホストでの交換条件に基づく heuristic であり、すべてのデプロイ先・コア構成での普遍的最適やロック競合皆無を保証するものではない。

### 2. 検討した代替案（選択肢として維持）

本決定は他の中間案や極端案を無価値として排除しない:

- **案 A: 既定 0（glibc の既定・外部設定に委ねる）** — 最大性能を追求する選択肢。しかし 32 を超える追加利得はわずか（認証スループット +2.4%）である一方、body peak RSS は約 260 → 335 MiB（約 +29%）と本実測条件内で大きく増加するため出荷既定からは外す。性能を最優先する運用者は `PLECTO_MALLOC_ARENA_MAX=0` で選択可能とする（外部環境設定を尊重し、Plecto は上書きしない。「無制限」を意味するものではない）。
- **案 B-alt: 16・24（メモリ優先の構成）** — 4 より大幅に処理能力を回復しつつ、32 よりもメモリ保持量を抑える選択肢（停止後 RSS は 16 で約 158 MiB、24 で約 182 MiB）。旧 gate 帯の境界を理由に排除せず、メモリ制約の厳しい環境における実用的な調整の出発点として残す。
- **案 C: 既定 4 の維持** — RSS を最も抑えるが、高並行時の処理能力を大きく失う（認証スループットが N=32 比で約 24.2% 低下、glibc 既定比で約 26.0% 低下）。出荷既定からは外すが、`PLECTO_MALLOC_ARENA_MAX=4` により従来の低メモリ動作をそのまま維持可能とする。

### 3. 設定仕様とプラットフォーム境界

- **環境変数 `PLECTO_MALLOC_ARENA_MAX`**:
  - 未指定または不正な文字列（非数値）: 出荷既定値 `32` を適用。
  - `4`: 従来の動作仕様（[[000038]]）を維持。
  - `4`〜`16`（または `24`）: メモリフットプリントを優先する場合の調整範囲・出発点。
  - `0`: `mallopt` による上書きを行わず、glibc の外部設定（システム設定、tunables、組み込み既定）へ委ねる。
  - 負数（`-1` 等）: 既存互換性のための no-op。
- **プラットフォーム**: Linux GNU (glibc) 環境でのみ動作。musl や macOS 等ではコンパイル時に no-op。
- **反映タイミング**: `mallopt(M_ARENA_MAX)` は新たなアリーナ生成のみを制限し既存アリーナを回収しないため、Tokio ランタイム生成前のプロセス起動時に 1 度だけ適用する。変更の反映にはリロード（`SIGHUP`）ではなく再起動（`restart`）を要する。

### 4. ハーネスおよびベンチマークランナーの統制

出荷バイナリと測定環境の挙動乖離を防ぐため、以下を実施した:

- `bench-server`, `load-balancing`, `tls-http`, `swap-bench` の全 4 通常 proxy ハーネスが、ランタイム起動前に `cap_malloc_arenas()` を呼ぶよう統一。
- `run-perf.sh` において `BENCH_MALLOC_ARENA_MAX` 未指定時は `PLECTO_MALLOC_ARENA_MAX` を注入せず Rust 既定（32）を直接テスト。明示指定時は `PLECTO_MALLOC_ARENA_MAX` のみを注入し、startup の `MALLOC_ARENA_MAX` は直接設定しない。親環境のアロケータ環境変数を清掃し、`LD_PRELOAD` を拒否。
- `arena_sweep.py` は `--arenas default,32` で出荷既定と明示 32 の実測比較が可能。

### 5. 実装確認（T3 分離計測）および回帰ゲート較正（T1 gate）

実装完了後、同一 release binary および現行 runner により実装検証および回帰ゲートの確認を実施した:

1. **T3 分離計測による出荷既定（default）対 明示 32 の実測比較**:
   - `arena_sweep.py` により出荷既定（環境変数未設定、Rust 既定 32）と明示指定（`PLECTO_MALLOC_ARENA_MAX=32`）の 2 巡計測を実施。両条件で `complete` ファイルが生成され、HTTP 失敗はゼロ。
   - 2 巡平均結果（default / explicit32）:
     - `/trusted` 認証: 96,281.3 / 94,982.7 rps
     - `/ratelimit`: 82,305.3 / 81,917.9 rps
     - `/body`: 2,090.1 / 2,098.5 rps
     - body 経路 proxy 単体 peak RSS: 256.51 / 256.00 MiB
     - 負荷停止後 15 秒 RSS: 185.93 / 199.21 MiB
   - （※ baseline は oha と k6 で負荷モデルが異なるため合算平均は算出しない）。2 巡の測定値は実測比較のための記録であり、統計的同等性を検証・保証するものではない。

2. **T1 gate 観測値とゲート許容帯（apikey_cost_us）の較正**:
   - 同一 release binary / 現行 runner による T1 gate 測定（`run-perf.sh gate`、生データ: `performance/data/runs/gate-default-run1-20260928`, `gate-default-run2-20260928`）:
     - run1: `dispatch_floor_us` 4.5397 ± 0.0540 µs (pass), `apikey_cost_us` 1.4053 ± 0.0716 µs (旧帯 0.3..1.2 に対して fail), 他全項目 pass (9 pass, 1 fail)
     - run2: `dispatch_floor_us` 4.5860 ± 0.0600 µs (pass), `apikey_cost_us` 1.4210 ± 0.0451 µs (旧帯に対して fail), 他全項目 pass (9 pass, 1 fail)
     - micro 層は保存 criterion baseline `main` が存在しないため情報層 skip。
   - 対照測定として同一バイナリ・同一 runner で glibc 既定（`BENCH_MALLOC_ARENA_MAX=0`、生データ: `performance/data/runs/gate-glibc-control-20260928`）を実施:
     - `apikey_cost_us` は 1.1052 ± 0.1744 µs となり、不確実性区間が旧上限 1.2 をまたいだため PASS ではなく **INCONCLUSIVE (exit code 2)** を記録（他 9 項目は pass）。
   - **観測結果の解釈とゲート上限の再較正**:
     - これらの実測値は特定のベンチマーク構成およびホスト状態下での観測結果であり、単一の cap 0 対照やホスト変動を考慮すると、数値変動の要因をアリーナ上限のみへ排他的に因果帰属できるものではない。
     - 一方で、既定値 32 の採用自体は前日 T3 のスループット／RSS トレードオフに基づき決定済みであり、ゲート帯は cap の選定基準ではなく既存期待値の回帰検知用である。
     - 基準ホストでの運用上の再較正（統計的信頼区間の保証ではない）として、default32 実測の最大中心値 1.421 + 3 × 最大 half-range 0.0716 ≈ 1.636 を切り上げ、`gate_tolerances.toml` の `apikey_cost_us` **hi を 1.2 → 1.7** へ改定（lo 0.3 および他全帯・判定方式は維持）。
     - 改定後の帯（0.3..1.7）に対し、独立した `explicit32` の T1 gate holdout 実測（生データ: `performance/data/runs/gate-explicit32-validation-20260928`）を実施し、ゲート正常終了（exit code 0、10 pass, 0 fail, 0 inconclusive）を確認した。
       - 実測値: `dispatch_floor_us` 4.5796 ± 0.1892 µs (pass), `apikey_cost_us` 1.2994 ± 0.2035 µs (pass; 新帯 0.3..1.7 内), `ratelimit_tax_us` 4.3764 ± 0.0745 µs (pass)。固定レート tail p50（pooled 0.1262 ms, apikey 0.0146 ms, respctx -0.0288 ms）、`enforce_allowed_ratio` 0.9166、`rr_spread_req` 0、`ejection_transition_s` 1 s、`ejection_stray_failed` 0 も全項目 pass（informational: pooled p99 0.1517 ms, respctx p99 -0.0009 ms, enforce limited 0.7800; criterion micro は保存 baseline main 不在のため情報層 skip）。

## Consequences

### Pros
- 認証や rate-limit などの高 RPS 処理において、glibc 既定に近いスループットを回復した（既定 4 比で認証スループット約 +32%、約 72k → 95k rps）。
- glibc 既定（0）と比較して、1MiB body 経路における proxy 単体の peak RSS を約 22%、負荷停止後 settled RSS を約 23% 抑制した。
- 全通常 proxy ハーネスの起動経路が統一され、既定値の二重管理と測定乖離が解消した。
- `PLECTO_MALLOC_ARENA_MAX=4`（ベンチマークでは `BENCH_MALLOC_ARENA_MAX=4`）を指定することで、従来のアリーナ上限 4 を維持し、フットプリントや挙動を比較・検証できる（新通常ランナーは startup の `MALLOC_ARENA_MAX` 注入を外し `PLECTO_*` 経由で `mallopt` を呼ぶため、過去の測定値そのものの完全再現を保証するものではない）。

### Cons / Tradeoffs
- 既定値 4 との比較において、1MiB body 経路の proxy 単体 peak RSS は約 167 → 260 MiB (+55%)、停止後 settled RSS は約 140 → 198 MiB (+42%) 増加する。
- 本セットアップにおいて、T1 gate の `apikey_cost_us`（逆 RPS 差による marginal cost）は glibc 既定（N=0）の約 1.11 µs（inconclusive）から約 1.41〜1.42 µs（旧帯 fail）への増加が観測された。この限界コスト差は、body 経路のメモリ保持抑制と引き換えに受け入れた運用上のトレードオフとして扱う。
- 32 は基準ホストでの測定に基づく heuristic であり、ハードウェア構成（極端な多コアやメモリ制約コンテナ）によっては 4〜16 への個別調整が必要となる場合がある。
- 観測された peak RSS は 200ms サンプリングでの観測値であり、停止後 15 秒の settled RSS も長期定常値の上限を保証するものではない。
- 性能計測の p99 は閉ループ飽和時の待ち時間であり、固定レートでの tail SLO 改善を主張するものではない。
- 再検討条件:
  - `stream<u8>` による bounded chunk 処理（[[000020]]）や body バッファのプール化が導入され、body 経路の大規模な線形一時割り当てが解消された場合。
  - ワーカースレッドの生成方式や `spawn_blocking` の割り当て・スレッド構成に変更があった場合。
  - 多コアサーバーや著しく異なるコアトポロジにおいて、32 での顕著なロック競合またはメモリ過多が観測された場合。
