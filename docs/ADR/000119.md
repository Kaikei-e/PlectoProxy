# trusted かつ非ブロッキングなフィルタの header フックを async worker 上で直接実行し、残りを blocking pool へ引き継ぐ

## Status
accepted

## Date
2026-09-29

## Affected Components
- **host（plecto-host）** — フィルタごとに `runs_inline` をロード時に決め、`try_on_request` / `try_on_response` は idle な pooled インスタンスが取れたときだけゲストを呼ぶ（取れなければ `WouldBlock`、ゲストは呼ばない）。呼び出し後の返却・recycle・trap 処理・breaker は blocking 経路と同じ `execute_pooled` を共有する。`KvBackend` に `may_block()` を追加（既定 true、`MemoryBackend` だけ false）。
- **control（plecto-control）** — header チェーンを inline で進め、最初に `WouldBlock` になったフィルタの位置と、その時点までの編集済み request / response を `Pending` で返す。`_from` はその位置から、従来と同じ順序（request は順方向、response は逆方向）と同じ decision 処理で残りを走らせる。
- **server（plecto-server）** — header フックの呼び出し 3 箇所は、まず worker 上で inline dispatch を呼ぶ。`Pending` のときだけ残りを `spawn_blocking` に渡す（admission permit はこれまでどおり closure に move する）。inline 経路のパニックは `catch_unwind` で受けて、`spawn_blocking` 経路の `JoinError` と同じ 502 に写像する。
- **manifest（plecto-control）** — `[[filter]]` に `dispatch = "auto" | "blocking"` を追加する。既定は `auto`。`blocking` は host の `LoadOptions` を経て `runs_inline` を false にする。
- **observability** — 上記 2 つのメトリクスを host で lock-free に集計し、`/metrics` に出す。
- **benchmarks** — `bench/perf/gate_tolerances.toml` の 2 つの帯を移動した（Consequences 参照）。

## Context
[[000013]] はフィルタチェーンを `tokio::task::spawn_blocking` で blocking pool に載せる橋を架け、[[000021]] はその撤去を body 契約（`stream<u8>`）と同梱で Stage 2 に置いた。どちらも、橋が要る理由として「wasmtime の `Store` は `!Send` なので `.await` をまたげない」を挙げていた（同じ説明がコードコメントと `plecto-server` の CONTEXT にもあった）。

開発者調査では、noop フィルタのルートが低負荷の固定レート（baseline 天井の約 1%）でも baseline より p50 で +0.12 ms 遅いことが指摘された。1 呼び出し 2.9 µs（criterion）のゲスト実行では説明がつかず、1 リクエストあたり 2 往復する blocking pool へのハンドオフが疑われた。この仮説を推測で扱わず、次の順で確かめた。

**事実確認（wasmtime 49.0.1 のソースと docs.rs）**
- `Store<T>` は `T: Send` なら `Send` である。`runtime.rs` の `_assertions_runtime` が `Store<()>` の `Send + Sync` をコンパイル時にアサートしており、`call_async` が返す future の `Send` も同様に静的にアサートされている。`store.rs` にある `unsafe impl Send/Sync` は `StorePtr` 向けだけなので、`Store<T>` の `Send` はフィールドからの自動導出である。コンポーネントの `call_async` は `Data: Send` を要求するだけである。
- このホストはすでに `FilterRuntime::Instance: Send` を要求しており、それでコンパイルが通っている。pooled インスタンスも複数の blocking スレッドをまたいで使われている。つまり「`!Send` だから」は成り立っていなかった。
- off-worker にしていた本当の理由は別にある。ゲストは epoch 期限まで同期的に走り、その間スレッドを占有し得る。

**計測（参照ホスト: i7-13700K。proxy を P コア 6 物理 = 12 論理 CPU に exec 時ピン留めし、生成器は残りのコア。loopback、bench-server、50 接続、oha。root 不要の計測器で `/proc/<pid>/task/*/schedstat` と `status` を 250 ms ごとに追跡した）**

変更前（HEAD `22f94ad`）の noop-pooled は、天井負荷で次のとおりだった。

| 指標（1 リクエストあたり、全スレッド合計） | noop-pooled | baseline |
|---|---|---|
| 自発的コンテキストスイッチ | 5.09 回 | 0.87 回 |
| CPU 時間 | 103 µs | 57 µs |
| runqueue 待ち | 76 µs | 3 µs |
| スレッド数 | 80 本（blocking スレッドが接続数ぶんに膨張） | — |

ゲスト実行が約 3 µs なのに CPU が +46 µs 増えている。差の大部分はスレッド間の受け渡し（futex による起床と待機）と、blocking スレッドの runqueue 競合だった。

## Decision
**header フック（`on-request` / `on-response`）に限り、実行してよいフィルタは async worker 上で直接（同期的に）実行し、それ以外はチェーンの途中から従来の blocking pool に引き継ぐ。** この決定は [[000021]] の Stage 2 のうち「`spawn_blocking` 撤去」の一部を body 契約から切り離して前倒しするもので、true async 化そのものは Stage 2 に残す。

1. **適格性はロード時に決め、フェイルセーフに倒す。** 次のすべてを満たすフィルタだけが inline 実行できる。
   - isolation が `Trusted`（pooled インスタンスを再利用する）。
   - import が `host-log` / `host-clock` / `host-config` / `types` だけである。state 系（`host-kv` / `host-counter` / `host-ratelimit`）は `KvBackend::may_block()` が false のときに限って許す。redb は `Increment` / `TryAcquire` を含めて flat-combining のコミット完了（周期的に `Durability::Immediate` = fsync）を reply channel で待つため、ブロックし得る。
   - outbound HTTP / TCP も WASI も持たない。
   - manifest で `dispatch = "blocking"` を宣言していない（Decision 5）。
   - `plecto:filter/` 以外の import や未知の interface が一つでもあれば不適格にする。`may_block` の既定は true なので、外部実装の backend は明示的に opt-in しない限り inline にならない。
2. **worker 上では待たず、インスタンスも作らない。** inline 経路が取るのは idle インスタンスだけ。次のどれかに当たれば、そのフィルタでチェーンを止め、編集済みの状態を持ったまま blocking pool で続きを走らせる。
   - pool が上限（既定 cap = `min(available_parallelism, 8)` は worker 数を下回り得る）に達して空きがない。
   - インスタンスがまだ作られていない。
   - recycle 後でインスタンスが作り直し待ち。
   - breaker が open している。

   Condvar での有界待ち（最大 `checkout_timeout` 250 ms）も、instantiate + init（trusted の init 期限は最大 5 s）も worker には載らない。
3. **意味論は変えない。**
   - decision の適用、short-circuit / replace での停止、trap / deadline の fail-closed 写像（[[000012]] の breaker を含む）、span の発行は、blocking 経路と同じコードを通す。
   - チェーン途中での引き継ぎは、フィルタ k の直前で分けるだけで、フィルタは各 1 回しか走らない。
   - パニックも同じ扱いにそろえる。blocking 経路では、パニックは `JoinError` → `ServerError::ChainJoin` を経て 502 に写像され、接続は生きたままだった。inline 経路は dispatch を `catch_unwind` で包み、`ServerError::ChainPanic` として同じ 502 の経路に乗せる。パニックしない経路の追加コストは実質ない。一次防御は「データプレーンで panic 禁止」のままで、これは多層防御である。
4. **inline 適格なら outbound runtime を持たない、を構造で保証する。** `WasmtimeRuntime::drive` は、outbound 用の tokio `Runtime` を持つと `block_on` する。これを worker 上で呼ぶとパニックになる。そこで `rt` を付けるかどうかと `runs_inline` を同じ値（`needs_rt`）から導き、「`runs_inline` なら `rt` はない」が付与条件の将来の変更でも崩れないようにした。outbound を付けた trusted フィルタが inline にならないことはテストで固定した。
5. **全体スイッチは設けず、フィルタ単位で狭める宣言だけを用意する。**
   - スパイクでは環境変数で A/B できるようにしたが、製品には残さない（運用の単純さ）。
   - 代わりに `[[filter]] dispatch = "auto" | "blocking"` を用意する。既定は `auto`（適格なら inline）。`blocking` は pooled のまま header フックを blocking pool で動かす。
   - 権限を狭める方向にしか働かず、inline を強制する値は存在しない。deny-by-default と矛盾しない。
   - `pool_size` と同じく trusted 専用で、untrusted に書くと validate で弾く。
   - これがないと、再検討条件 (a) が現実になったとき、運用者が製品内で取れる手段は untrusted 化（スループット約 1/25）しかなかった。
6. **再検討条件を観測できるようにする。** host 集約のメトリクスを 2 つ追加する（カーディナリティは有界）。
   - `plecto_filter_inline_fallbacks_total{reason}`：inline 適格なフィルタが blocking pool へ回った回数。`reason` は `pool_exhausted` / `pool_filling` / `breaker_open` の 3 つ。
   - `plecto_filter_inline_duration_seconds`：inline 実行時間のヒストグラム。
7. **body フックは blocking pool のまま。** バッファ全体を処理するので、CPU 時間が body サイズに比例し、上限が header フックよりずっと大きい。

Tenet との関係:
- fail-closed：エラーの写像は不変。
- deny-by-default：能力はロード時に固定し、未知の能力は不可にする。
- データプレーンで panic 禁止：`WouldBlock` はエラーではなく継続として扱う。
- 運用の単純さ：プロセス全体のノブは増やさない。増やすのは、フィルタ単位で権限を狭める宣言 1 つだけで、既定のままなら何も設定しなくてよい。

いずれにも反しない。

### 検討した代替案
- **untrusted を含む全フィルタを inline にする** — 却下。untrusted は毎回 fresh instantiate（mmap / munmap と TLB shootdown の膝）を行い、しかも他人のコードである。それが epoch 期限（既定 100 ms）まで worker を占有すると、同じ worker 上の全接続が head-of-line で止まる。
- **true async（worker 上で `call_async` を await し、`Store::epoch_deadline_async_yield_and_update` や `UpdateDeadline::YieldCustom(tokio::task::yield_now)` で協調的に譲る）** — 長く走るゲストでも worker を明け渡せる最終形だが、今回は見送った。これをやるには次がすべて要り、これは [[000021]] の Stage 2 そのものである。
  - `run_pooled` の async 化（Condvar checkout を async のバックプレッシャに置き換える）
  - `pollster` の除去
  - host / control 公開 API の async 化

  計測では、コストの主因はスレッド往復だった。inline 同期実行だけでディスパッチ床の約 2/3 を回収できたので、段階を分ける。
- **`tokio::task::block_in_place`** — 却下。worker を blocking スレッドに転換し、run queue を別の worker へ移すので、ハンドオフと起床のコストが残る。multi-thread ランタイムでしか使えない制約もある。
- **空きがないときは worker 上で待つか、インスタンスを作る** — 却下。worker が最大 250 ms（checkout 待ち）、あるいは最大 5 s（init）塞がる。
- **プロセス全体の切り替えノブ（環境変数など）で inline を無効化できるようにする** — 却下。全フィルタが道連れになるうえ、運用ノブが増える。問題を起こすのは特定のフィルタなので、フィルタ単位で狭める宣言（Decision 5）で足りる。
- **trusted pool を worker 数ぶん常に確保する** — 今回は見送った。上限 8 は、複数フィルタでエンジン全体の pooling 予算（256 スロット）を分け合う前提の値である（[[000012]]）。フォールバック率を見てから判断する（再検討条件）。

## Consequences

### Pros
同一ホストで、変更前バイナリと変更後バイナリを交互に 3 回ずつ起動し、各指標の中央値を比べた。全リクエストが 200 だった。

- ディスパッチ床（noop-pooled − baseline、閉ループの逆数スループット `1e6/rps`）は **4.06–4.21 → 1.41–1.44 µs/req**。
  - proxy が 12 論理 CPU で飽和している条件では、逆数スループットに CPU 数を掛けると 1 リクエストあたりの CPU 時間にほぼ一致する。変更前は 4.1 × 12 ≈ 49–51 µs に対して、実測の CPU 差（noop − baseline）が 46 µs。変更後は 1.43 × 12 ≈ 17 µs に対して 19 µs だった。
  - 床 4.1 µs のうち約 2.7 µs がハンドオフだった。以前の「約 2.0 µs が spawn_blocking 分」という帰属は過小評価だった。
- 天井スループット：
  - noop-pooled：**100.2k → 146.6k rps（+46%）**
  - trusted（apikey、memory backend）：**87.9k → 123.1k rps（+40%）**
  - apikey 自身のコスト（trusted − noop-pooled）は 1.38–1.42 → 1.30 µs でほぼ不変。つまり、減ったのはフィルタの仕事ではなく受け渡しのコストである。
- 低〜中負荷のレイテンシ（`--latency-correction` 付き固定レート、p50）：
  - 500 rps：noop-pooled 0.352 → **0.256 ms**、trusted 0.391 → **0.291 ms**（baseline 0.216–0.222 ms）
  - 2,000 rps：noop-pooled 0.406 → 0.361 ms、trusted 0.451 → 0.398 ms（baseline 0.291–0.292 ms）
  - noop の対 baseline 差は +0.13 ms → +0.04 ms になった。
- スケジューリング（noop-pooled、天井）：自発的コンテキストスイッチ 5.09 → 0.79 回/req（baseline 並み）、CPU 103 → 76 µs/req、runqueue 待ち 76 → 0.7 µs/req、スレッド数 80 → 35 本。
- T1 gate を 2 回回した結果：
  - `dispatch_floor_us` 1.4386 ± 0.1045 / 1.4987 ± 0.1843
  - `ratelimit_tax_us` 1.7348 ± 0.0405 / 1.7771 ± 0.0232
  - 他の 11 項目（`apikey_cost_us`、各 tail、rr、ejection など）はすべて旧帯の中に収まった。

  帯は `dispatch_floor_us` 0.9–2.1、`ratelimit_tax_us` 1.2–2.4 に移した。blocking 経路への退行（床 ~4.1 µs、税 ~4.6 µs）は帯の外に出るので検出できる。
- 「`!Send` だから」という誤った説明を、コード、CONTEXT、Cargo のコメントから取り除いた。
- 運用者は再検討条件を `/metrics` で観測できる。問題のあるフィルタだけを `dispatch = "blocking"` で worker から外せるので、untrusted に落とす必要はない。

### Cons / Tradeoffs
- **trusted な inline フィルタの CPU 時間は proxy の worker 上で消費される。** 最悪の場合、同じ worker 上の他タスクが per-request の epoch 期限（`request_deadline_ms`、既定 100 ms）まで待たされる。trusted が「署名済みで運用者が信頼したコード」であるという前提に依存している。per-request の仕事が重い trusted フィルタには、`dispatch = "blocking"` を宣言するか、仕事を init に寄せる（operations ドキュメントに明記した）。
- **inline 化した後も、未説明の CPU が残っている。** 変更後も noop は baseline より約 19 µs/req 多く CPU を使う。ゲスト呼び出し 2 回分（request と response で約 3 µs ずつ）を引いても、約 13 µs が説明できていない。pool 上限によるフォールバックは、上記のとおり約 0.3 µs/req にすぎない。残る候補は次のとおりで、いずれも未分解である。
  - ヘッダの詰め替え（`headers_to_vec` の往復や、契約アダプタでの clone）
  - span の発行
  - pool のロック

  分解には inline 経路のプロファイルが要るが、参照ホストでは `perf` に root が要るため取れていない。
- **root 不要の schedstat 計測器（コンテキストスイッチ/req、runqueue 待ち/req、CPU/req）は、まだハーネスに入っていない。** 今回の判断の根拠を直接測れる道具なので、T3 フェーズとして `run-perf.sh` に取り込むのが次の作業になる（別 PR）。
- **redb 構成（`[state] backend = "redb"`）では、state 系フィルタに恩恵がない。** apikey のような KV 読み取り中心のフィルタも blocking pool 経路のままになる。
- **pool の上限が worker 数を下回ると、飽和時に一部がフォールバックする。** 天井負荷でも、フォールバックは 1% 未満にとどまる。
  - 既定の上限 8 と、worker 数に合わせた 12 を、交互起動 3 回ずつで比べた。
    - `pool_exhausted`：trusted の天井で 0.74% → 0.01%/req に下がった。
    - スループット：noop 145.2k → 145.7k rps、trusted 122.1k → 123.6k rps で、差は誤差の範囲だった。
    - ディスパッチ床：1.34–1.42 µs と 1.39–1.47 µs で変わらなかった。
  - つまり、上限 8 による取りこぼしは測れる大きさではない。既定値は据え置く。
  - 残るフォールバックの大半は `pool_filling`（noop の天井で約 0.7%/req）である。原因は recycle（65,536 呼び出しごと）で、作り直しは blocking 経路でしか起きないので、その間は inline 経路が空きを見つけられない。天井負荷では、各インスタンスが約 2 秒ごとに作り直される。
  - コストに換算すると約 0.3 µs/req で、下記の未説明分の主因ではない。
- recycle（既定で 65,536 リクエストごと）のときは、Store の解放だけが worker 上で起きる。作り直しと init は blocking 経路で起きる。
- **公開 API と manifest の面が増える。**
  - API：`KvBackend::may_block`（既定メソッドなので既存実装は壊れない）、`LoadedFilter::{runs_inline, try_on_request, try_on_response}`、`TryHookOutcome`、`InlineRequestOutcome` / `InlineResponseOutcome`、`ConfigSnapshot::dispatch_{request,response}_{inline,from}`、`LoadOptions` の dispatch 指定。
  - manifest：`dispatch` は互換ポリシー上ずっと残る。
- **再検討条件**
  - (a) trusted フィルタの CPU 占有が他接続の p99 を押し上げる事例が出たら（`plecto_filter_inline_duration_seconds` の裾で観測する）、次の 2 段で対処する。
    - 暫定：該当フィルタに `dispatch = "blocking"` を宣言する。
    - 恒久：true async と epoch の async yield（[[000021]] Stage 2）を前倒しする。
  - (b) `plecto_filter_inline_fallbacks_total{reason="pool_exhausted"}` が無視できない規模になったら、trusted pool の既定サイズ（上限 8）を worker 数に合わせて見直す。参照ホストの天井負荷では 0.74%/req で、上限 12 にしても効果は誤差の範囲だった。`pool_filling` が大きい場合は、recycle の作り直しを事前に行う（空きがなくなる前に blocking 経路で作っておく）ことを検討する。
  - (c) redb 構成で state 系フィルタのコストが問題になったら、読み取り専用 KV の分離か async host call（[[000021]]）を検討する。
  - (d) wasmtime の `Store` / `call_async` の `Send` 境界が変わったら、本 ADR の前提を確認し直す。
