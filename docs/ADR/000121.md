# ホストが貸す全 WASI capability（fat-guest / outbound-http / outbound-tcp / streaming-body）を WASI 0.2 と WASI 0.3（@0.3.0）の並走に対応させる

## Status
accepted

## Date
2026-10-24

## Affected Components
- `crates/host/src/stdio.rs` — `StdioStream` に `tokio::io::AsyncWrite` を実装し、`StdoutStream::async_stream` を `AsyncReadStream::new(tokio::io::empty())` の無音スタブから `Box::new(self.clone())` へ置換
- `crates/host/src/state.rs` / `runtime.rs` / `util.rs` — `add_wasi_base_p3`（`wasmtime_wasi::p3::{clocks,random,cli}::add_to_linker`）を追加し、`add_inert_filesystem` で `wasmtime_wasi::p3::filesystem::add_to_linker`（preopens 空で構造的 inert）も登録。`wasi_minimal` および `streaming-body` の実行時は `block_on_wasi`（`wasmtime_wasi::runtime::with_ambient_tokio_runtime`）を介して P3 clock wait にタイマードライバを供給
- `crates/host/src/outbound_http.rs` — `wasmtime_wasi_http::p3::WasiHttpHooks` が `p2::WasiHttpHooks` の re-export であることを活用し、`wasi:http/client@0.3.0#send` が同一の `HostState::send_request`（allowlist・IP-pinned SSRF ガード・per-frame/total timeout・ボディサイズ上限・同時実行枠）を通ることを単体テストで検証
- `crates/host/src/outbound_tcp.rs` — 名前解決＋SSRF 分類＋IP pin ロジックを 0.2/0.3 共用の `resolve_vetted` に抽出し、`wasi:sockets/ip-name-lookup@0.3.0`（`PlectoTcpLookup`）と `wasi:sockets/types@0.3.0`（`PlectoTcpSockets`、および派生ストリーム寿命に追随する `P3SocketLease` / `P3StreamCompletion`）を実装
- `crates/host/src/host.rs` / `streaming.rs` — 貸与された capability スライスに限り `@0.2.x` と `@0.3.0` を対で `Linker` に登録し、未貸与 capability の `@0.3.0` import が `LoadError::MissingCapability` で fail-closed になることを単体テストで固定
- `crates/host/CONTEXT.md` / `docs/ROADMAP.md` — Fat guest・Outbound HTTP・Outbound TCP・M3/M6 の記述を WASI 0.2 + 0.3 並走に合わせて更新

## Context

[[000021]] で M3 Stage 1（wasmtime 46 以降の Component Model async + `call_async` 駆動）を着地させ、[[000120]] で
`wasmtime` / `wasmtime-wasi` / `wasmtime-wasi-http` 50.0.0 へロックステップ更新したことで、エンジンと `HostState` の
トレイト実装（`wasmtime_wasi::p3::ResourceView`、および 0.2 と統合された `WasiView` / `WasiHttpView`）はすでに
WASIp3（WASI `@0.3.0`）に対応している。

しかし、ホストの `Linker` 登録と各 capability アダプタを一次ソース（[`bytecodealliance/wasmtime` `v50.0.0/crates/wasi/src/p3/`](https://github.com/bytecodealliance/wasmtime/tree/v50.0.0/crates/wasi/src/p3)
および [`v50.0.0/crates/wasi-http/src/p3/`](https://github.com/bytecodealliance/wasmtime/tree/v50.0.0/crates/wasi-http/src/p3)）に照らして監査した結果、
以下の 4 点で WASI 0.3（`@0.3.0`）対応が未完であることが判明した:

1. **Linker への `@0.3.0` 登録の欠落**:
   `Host::load`（`crates/host/src/host.rs`）と `StreamingFilterRuntime::load`（`crates/host/src/streaming.rs`）は
   `wasi:*@0.2.x` のみを `Linker` に登録しており、`wasi:cli/*@0.3.0`・`wasi:clocks/*@0.3.0`・`wasi:random/*@0.3.0`・
   `wasi:filesystem/*@0.3.0`・`wasi:http/{types,client}@0.3.0`・`wasi:sockets/{types,ip-name-lookup}@0.3.0` を import する
   WASIp3 ゲストは capability を明示貸与していても `MissingCapability` でロードに失敗する。
2. **WASIp3 stdio（`wasi:cli/{stdout,stderr}@0.3.0#write-via-stream`）の無音破棄**:
   [[000113]] で wasmtime 48 の `StdoutStream` トレイト統合に追随した際、`StdoutStream::async_stream` を
   `Box::new(AsyncReadStream::new(tokio::io::empty()))` のスタブで満たしていた。WASIp2 の `get-stdout` は `p2_stream` を
   呼ぶため動いていたが、WASIp3 の `wasi:cli/{stdout,stderr}@0.3.0#write-via-stream` は `async_stream()` が返す
   `Box<dyn AsyncWrite + Send + Sync + Unpin>` に guest の `stream<u8>` を copy する（`crates/wasi/src/p3/cli.rs`）。
   そのため WASIp3 ゲストの stdout/stderr 出力が `StdioBridge`（[[000063]] の `host-log` 統合・16 KiB/req 予算）に届かず無音で捨てられていた。
3. **WASIp3 `wasi:sockets@0.3.0` における capability 境界の構造変化**:
   WASIp2（`0.2.x`）では TCP と UDP が別 interface（`wasi:sockets/tcp-create-socket` vs `udp-create-socket`）に分かれており、
   UDP interface を Linker に登録しないことで UDP を構造的に拒否し、`tcp-create-socket` と `tcp` のみをカスタム実装
   （`PlectoTcpCreateSocket` / `PlectoTcp`）に差し替えて `TcpSocketQuota` と `listen` 拒否を強制していた（[[000060]] / [[000115]]）。
   一方、WASIp3（`0.3.0`）では `wasi:sockets/types@0.3.0` 1 つの interface に `tcp-socket` と `udp-socket` の両 resource が統合され、
   かつ `wasmtime_wasi::p3::sockets::add_to_linker` の既定実装は `udp-socket.create` と `tcp-socket.listen` を許可し、
   ホストの `ip-name-lookup@0.3.0` も DNS リゾルバを直接引いて `WasiCtxBuilder::socket_addr_check` を通さない。
   したがって `wasmtime_wasi::p3::sockets::add_to_linker` をそのまま呼ぶと、[[000060]] と [[000115]] の不変条件
   （allowlist 外の名前解決拒否・IP-pinned connect・live TCP socket 枠・UDP 禁止・受動 `listen` 禁止）がすべて破綻する。
4. **WASIp3 `wasi:http@0.3.0` のフック共有条件**:
   `wasmtime-wasi-http` 50.0.0 の `p3` 実装（`crates/wasi-http/src/p3/bindings.rs`）では、`p3::WasiHttpHooks` は
   `p2::WasiHttpHooks` の re-export であり、`wasi:http/client@0.3.0#send` は内部で `Request::into_http` により
   リクエストを変換した上で同じ `WasiHttpHooks::send_request` を呼ぶ。したがって `wasmtime_wasi_http::p3::add_to_linker` を
   登録すれば、[[000036]] / [[000115]] で実装した `HostState::send_request`（scheme/host/port allowlist、全 A/AAAA の
   SSRF 分類と IP-pinned connect、per-frame/total timeout、`BoundedBody` による応答サイズ上限、`RequestLifetime` による
   ボディ消費完了までの同時実行セマフォ保持）が 0.2 と 0.3 の双方に無変更で効く。

関係する Tenet は「deny-by-default capability」（[[000006]]）、「データプレーンで panic 禁止」、および Fork 2
（`plecto:filter` 独自ワールドを保ちつつ標準 WASI 型・capability 語彙へ収斂する、[[000002]] / [[000020]]）である。

## Decision

Plecto ホストが貸し出す全 WASI capability スライスにおいて、既存の WASI 0.2（`@0.2.x`）と完全に対称なセキュリティ・資源境界のもとで
WASI 0.3（`@0.3.0`）interface を並走登録する:

1. **WASIp3 stdio ブリッジの直結（`crates/host/src/stdio.rs`）**:
   - `StdioStream` に `tokio::io::AsyncWrite` を実装する。`poll_write` はバックグラウンドタスクを起こさず、同期の
     `p2_stream`（`OutputStream::write`）とまったく同じ `self.bridge.inner.lock().unwrap_or_else(PoisonError::into_inner).write(self.kind, buf)`
     を即座に実行して `Poll::Ready(Ok(buf.len()))` を返す。
   - `StdoutStream::async_stream(&self)` は `Box::new(self.clone())` を返す。これにより `wasi:cli/{stdout,stderr}@0.3.0#write-via-stream`
     からの出力も同一の `StdioBridge`（4 KiB/line 上限、stdout+stderr 合算 16 KiB/req の `ByteBudget`、改行分割と制御文字サニタイズ、
     trap 時の `drain_final()` 回収）を通る。
2. **最小 WASI スライスと inert filesystem の 0.2 / 0.3 並走（`crates/host/src/state.rs`）**:
   - `add_wasi_base_p3` を新設し、`wasmtime_wasi::p3::{clocks, random, cli}::add_to_linker` の 3 パッケージのみを登録する
     （filesystem も sockets も含めない。なお WASI 0.3 では `stream<T>` / `future<T>` が Component Model 組み込み型になったため
     `wasi:io` パッケージは存在しない）。
   - `add_inert_filesystem` で 0.2 に加えて `wasmtime_wasi::p3::filesystem::add_to_linker`（`wasi:filesystem/{types,preopens}@0.3.0`）を登録する。
     `HostState::build_wasi_ctx` は `preopened_dir` を一切呼ばないため、`get-directories` は常に空リストを返し、ホスト FS への到達経路はゼロのままである。
   - `StreamingFilterRuntime::load`（`streaming-body` feature）でも `add_wasi_base` とともに `add_wasi_base_p3` を登録する。
   - outbound を持たない fat guest と streaming の同期実行では、`block_on_wasi` が
     `wasmtime_wasi::runtime::with_ambient_tokio_runtime` 内で Store を poll する。P3 clocks の `wait-for` / `wait-until` が
     直接作る Tokio timer を、呼び出し元にランタイムがない場合にも駆動する。
3. **Outbound HTTP の 0.2 / 0.3 並走（`crates/host/src/host.rs` / `outbound_http.rs`）**:
   - `outbound-http` feature 有効かつフィルタに `outbound_http` ポリシーが宣言されている場合（または PIXIT 検証用の空ポリシー）、
     `Host::load` で `add_wasi_base` + `add_wasi_base_p3` とともに `wasmtime_wasi_http::p2::add_only_http_to_linker_async` および
     `wasmtime_wasi_http::p3::add_to_linker`（`wasi:http/{types,client}@0.3.0`）を登録する。
   - `wasi:http/client@0.3.0#send` は `HostState` の `WasiHttpHooks::send_request` に直結し、0.2 の `outgoing-handler` と同一の
     allowlist・SSRF ガード・IP pin・サイズ上限・タイムアウト・同時実行枠を強制する。
4. **Outbound TCP の 0.2 / 0.3 並走と `wasi:sockets@0.3.0` カスタム検問（`crates/host/src/outbound_tcp.rs`）**:
   - `wasmtime_wasi::p3::sockets::add_to_linker` の一括登録は**使わない**。代わりに `wasmtime_wasi::p3::bindings::sockets::{ip_name_lookup, types}::add_to_linker`
     に Plecto 独自のホスト実装 `PlectoTcpLookup` / `PlectoTcpSockets` を渡す:
     - **`PlectoTcpLookup`（`wasi:sockets/ip-name-lookup@0.3.0`）**: 0.2 と共用の `resolve_vetted` を呼び、
       (a) `allowed_hosts`（完全一致・大文字小文字無視）に含まれるホスト名のみ解決を許し、
       (b) 解決された全 A/AAAA レコードを `outbound::classify` で検査し（1 つでも禁止レンジがあれば解決自体を `ErrorCode::AccessDenied` で拒否）、
       (c) 全レコード通過時のみ per-request の `pinned_ips` に登録して返却する。
     - **`PlectoTcpSockets`（`wasi:sockets/types@0.3.0`）**:
       - `HostTcpSocket::create`: Store ごと 64、Host 全体 1,024 の同時 live socket 枠を検査し、
         超過時は `ErrorCode::OutOfMemory`（0.3 の `error-code` では 0.2 の `new-socket-limit` が廃止されたため資源上限超過に対応する標準コード）で fail-closed。
         ソケット resource と送受信ストリームの完了 consumer が `Arc<P3SocketLease>` を共有し、最後の所有者が閉じた時点で枠を解放する。
         完了 consumer はホストが保持し、ゲストが socket と完了 future を先に drop しても、残るストリームの FD を計上し続ける。
       - `HostTcpSocketWithStore::connect`: `Accessor::with_getter::<WasiSockets>` と `Access::<T, WasiSockets>::new` を介して
         内部実装に委譲し、`WasiCtxBuilder::socket_addr_check`（`OutboundTcpGuard::check`）で `(ip, port)` の allowlist / IP pin /
         per-request `max_connections` 予算を強制する。
       - `HostTcpSocketWithStore::listen`: 無条件で `Err(ErrorCode::AccessDenied.into())` を返し、受動待ち受けを禁止する。
       - `HostUdpSocket::create`: 無条件で `Err(ErrorCode::AccessDenied.into())` を返す。`udp-socket` インスタンスが一切生成されないため、
         `bind` / `connect` / `send` / `receive` 等の全 UDP 操作は到達不能となる。

検討した代替案:

- **`wasmtime_wasi::p3::sockets::add_to_linker` をそのまま呼び、`socket_addr_check` だけに頼る** — 却下。
  upstream の `p3::sockets::add_to_linker` は (1) `ip-name-lookup@0.3.0` で `socket_addr_check` を通さず任意のホスト名を DNS 解決でき（情報漏洩・オラクル化）、
  (2) `tcp-socket.create` で per-filter の live socket 枠（[[000115]] F4）が効かず、
  (3) `udp-socket.create` が成功し、`socket_addr_check` も `SocketAddrUse::UdpBind` / `UdpConnect` / `UdpOutgoingDatagram` を拒否するものの、
  FD 枯渇や不要なカーネルソケット確保を許してしまう。`p3::bindings::sockets` の generated trait を直接実装して `PlectoTcpLookup` / `PlectoTcpSockets` を挟むことで、
  0.2 と寸分違わぬ境界を維持できる。
- **WASI 0.2 を廃止して 0.3 のみに切り替える** — 却下。
  現時点の言語ツールチェイン（Rust `wasm32-wasip2`、TinyGo `wasip2`、ComponentizeJS、MoonBit 等）の大半は `@0.2.x` を出力する。
  同一 `Linker` 上で `@0.2.x` と `@0.3.0` はパッケージバージョンで名前空間が分離されており衝突しないため、並走させることで既存の全フィルタと
  新しい WASIp3 フィルタの双方を単一バイナリでそのまま実行できる。

具体化する Tenet / Fork:
- `CLAUDE.md` コア原則「deny-by-default capability」「データプレーンで panic 禁止」
- Fork 2（`plecto:filter` 独自ワールドと標準 WASI capability の収斂、[[000002]] / [[000020]]）

## Consequences

### Pros
- `wasi = "minimal"`（`fat-guest`）、`outbound-http`、`outbound-tcp`、`streaming-body` の全スライスで、WASI 0.2（`@0.2.x`）と
  WASI 0.3（`@0.3.0`）、および両者を混在させるコンポーネント（例: ランタイム基盤は `wasi:cli@0.2.x` だが HTTP クライアントは
  `wasi:http/client@0.3.0` を使う等）が同一ポリシー・同一資源上限のもとで動作する。
- WASIp3 ゲストの `wasi:cli/{stdout,stderr}@0.3.0#write-via-stream` が `StdioBridge` に統合され、OTLP span event への
  ログ集約と 16 KiB/req 予算が 0.2 とまったく同じように効く。
- `wasi:sockets/types@0.3.0` で統合された `udp-socket` と `tcp-socket.listen` を trait 実装層で構造的に遮断し、
  DNS rebinding 防止（IP pin）と live socket 枠（`TcpSocketQuota`）を 0.3 でも完全に維持できる。

### Cons / Tradeoffs
- `outbound_tcp.rs` が `p2` と `p3` の両方の `wasi:sockets` バインディング trait を実装するため、コード量が約 250 行増える
  （ただし名前解決・SSRF 検査・IP pin のコアロジックは `resolve_vetted` 関数に一元化されており、ポリシー判定の重複はない）。
- 再検討条件: `wasm32-wasip3` ターゲットが Rust Tier 2 に昇格し、`plecto:filter` 本体契約の次世代メジャー版で
  `plecto:filter-streaming`（`stream<u8>`）を本固定する際（[[000021]] / [[000025]] の再検討条件）。
