# HTTP/1.1 Upgrade トンネル寿命にわたる接続上限ガード保持と T2/T1 性能計測ハーネスの除染・数理整合化

## Status
accepted

## Date
2026-10-24

## Affected Components
- `crates/server/src/listener.rs` / `dispatch.rs` / `proxy.rs` / `tests/upgrade.rs` — `ConnGuards`（グローバル `MAX_CONNECTIONS` セマフォ permit と per-IP `PerIpConnGuard`）を `Arc<ConnGuards>` で `upgrade_switch` のバックグラウンドトンネルタスクへ move し、WebSocket 等の長寿命 Upgrade トンネルが閉鎖されるまで接続スロットを保持（HTTP/1.1 のみ。h2 ストリームには `None`）。E2E 回帰テスト `upgraded_tunnels_hold_their_per_ip_connection_slot_until_closed` を追加
- `crates/control/benches/fastpath_inst.rs` — `group(algo: &str, hash: &str)` で初回 pick をウォームアップし、`lb_pick` / `lb_pick_maglev` が `-> Arc<UpstreamGroup>` を返すことで `UpstreamGroup` の teardown（`Endpoints` / `Vec<Arc<UpstreamInstance>>` / `MaglevTable` 等の解放）を命令数カウントから除外
- `bench/loadgen/src/openloop.rs` — `sleep_until(scheduled - 1ms)` と `tokio::task::yield_now()` を組み合わせ、1 ms タイマーホイール量子化による到着時刻の系統的遅延を除去
- `bench/perf/gate_verdict.py` / `gate_tolerances.toml` / `test_gate_verdict.py` / `run-perf.sh`（gate tier）— `enforce()` の期待許可レートを `apply_bucket`（[[000026]]）の離散 1 秒ティック補充式に一致（帯域 `[0.90, 1.10]` は従来どおり）。`ci_half` を paired round 差分の 95 % Student-t 半幅 `t_{0.975,n-1}·s/√n` へ改め `n` 列を追加、gate を 8 round × 短窓（偶数 round で順序反転）へ再設計、`GATE_POOL_FROM` で再実行時に round をプール（`build_id.txt` 不一致は拒否）
- `bench/perf/proc_cpu.py` / `ratelimit-cpu.js` — 固定レート 20k/s でのプロキシ CPU-µs/req を `/proc/<pid>/task/*/schedstat` から採取し、`ratelimit_cpu_us_per_req` を info 行として出力
- `bench/perf/ipc_check.py` / `test_ipc_check.py` — gungraun 命令数と Criterion 時間から暗黙 IPC を求め、`> 5` を違反とする任意の自己整合チェック
- `bench/perf/run-perf.sh` / `bench/k6/weighted-mix.js` / `performance/README.md` / `bench/methodology.md` / `bench/plan.md` — Phase 10.2（WebSocket トンネル RSS 計測）をクリーンな `bench-server` 上で `10.1 handshake` / `10.3 echo` より先に `--conns 250` で実行し実保持数 `held` で除算。`weighted-mix.js` で全 4 クラスの `p99.9` を CSV 出力し、公開ドキュメントの表記・RFC 番号・3 桁精度を一貫化

## Context

`v0.15.2`（`2026-10-24`、commit `1061a79`）で取得した T2/T1 性能スナップショット（`performance/data/v0.15.2-1061a79/`）の実測値を、Plecto 自身の設計不変条件（[[000048]] の Upgrade 資源会計、[[000092]] の per-source-IP 同時接続上限、[[000113]] の命令数ベンチ teardown 除染、[[000026]] の host-ratelimit トークンバケット意味論）および待ち行列理論の物理境界に照らして精査した結果、以下の 4 点の乖離が判明した:

1. **HTTP/1.1 `101 Switching Protocols` 昇格後の `MAX_CONNECTIONS` / `MAX_CONNECTIONS_PER_IP` ガード早期解放（[[000048]] / [[000092]] の不変条件漏れ）**:
   - [[000048]] Decision 6 は「トンネルも既存の資源会計に乗せる」と定め、circuit breaker permit（[[000028]]）と LB の `Pick` guard を `proxy.rs` の `upgrade_switch` が spawn するトンネルタスクへ move していた。
   - 一方、[[000027]] のグローバル接続上限（`MAX_CONNECTIONS = 10,000`）の `OwnedSemaphorePermit` と [[000092]] の送信元 IP 別同時接続上限（`MAX_CONNECTIONS_PER_IP = 256`）の `PerIpConnGuard` は、`crates/server/src/listener.rs` の `serve_conn` ローカル変数として保持されたままだった。
   - hyper の `http1::Builder::serve_connection(..).with_upgrades()` は、応答ヘッダ `101 Switching Protocols` を書き出した直後に `Ok(())` で完了し、ソケット所有権は `hyper::upgrade::on(req)` 経由で `upgrade_switch` の別タスクへ移る。そのため `serve_conn` のスタックフレームが 101 応答直後に終了し、トンネルが生きているにもかかわらず `_permit` と `_ip_guard` が即座に drop されていた。
   - この結果、単一 IP（`127.0.0.1`）から `plecto-loadgen ws --mode hold --conns 1000` を打った Phase 10.2 で 256 の上限が効かず 1,000 本すべてのトンネルが通り（CWE-770 / [[000092]] のバイパス）、さらに `10.1 handshake`（`500/s × 20 s` = 10,000 回の Upgrade バースト）と同じ `bench-server` プロセスをそのまま使い回したため、`idle_rss` がクリーン起動時の `42.0 MB`（`footprint.txt`）ではなく `76.5 MB`（`76,452 kB`）だった。差の 34.5 MB はバースト後にアロケータが解放済みメモリを保持している分と読むのが最も自然で（アリーナ上限 32 では起きやすい）、その場合は新規トンネルが既存の空きチャンクを再利用するので `~8.8 KB/tunnel`（`8,778 B/tunnel`、`76.5 → 85.0 MB`）は過小評価になる。ただしアロケータの使用中バイト数は計測しておらず、これは推論である。

2. **`crates/control/benches/fastpath_inst.rs` における `UpstreamGroup` teardown の命令数混入（[[000113]] の除染漏れ）**:
   - [[000113]] Decision 6 で `crates/host/benches/wasm_inst.rs` の fixture を返り値化し、測定ブロック外で drop させることで callgrind 命令数から teardown を除染した。
   - しかし `crates/control/benches/fastpath_inst.rs` の `lb_pick`（Round-Robin / P2C）および `lb_pick_maglev` は、`#[library_benchmark]` 関数の末尾で `group()` が生成した `Arc<UpstreamGroup>` をそのまま drop していた。そのため 1 回の `pick()` 本体ではなく、`UpstreamGroup`（`Endpoints`、`Vec<Arc<UpstreamInstance>>`、`MaglevTable` の `Box<[usize]>`、`String` 群）の `dealloc` および初回 pick 時のスレッドローカル RNG / `arc_swap` 遅延初期化コストが支配的となり、3 アルゴリズムすべてが `2,114` / `2,377` / `2,277` 命令というほぼ同一の teardown 値に張り付いていた。

3. **T1 ゲート `enforce_allowed_ratio` の連続時間近似による `-8.3%` 系統誤差と `ci_half` の統計的定義**:
   - `crates/host/src/backend.rs`（[[000026]]）の `apply_bucket` は、`(tokens, last_refill_ms)` をミリ秒単位で保持し、`let intervals = now_ms.saturating_sub(last) / spec.refill_interval_ms;` の整数除算で経過インターバル数を求めて `intervals * spec.refill_tokens` を加算する離散ティック方式である（ベンチマークハーネスでは `RL_REFILL_INTERVAL_MS = 1000`）。
   - したがって長さ $W$ 秒の計測窓（Phase 4.2 の T1 ゲートでは $W = 10\text{ s}$、`capacity = 2,000`、`refill_tokens = 1,000`、`refill_interval_ms = 1,000`）において、$t = 0$ で初期バースト `capacity` を引き出した後に発火する補充ティックは $t = 1, 2, \dots, W - 1$ のちょうど $W - 1 = 9$ 回であり、窓全体の理論最大許可数は $\text{capacity} + (W - 1) \times \text{refill} = 11,000\text{ req}$（$1,100.0\text{ req/s}$、30 秒の T2 窓では $2,000 + 29 \times 1,000 = 31,000\text{ req} = 1,033.3\text{ req/s}$）となる。
   - `bench/perf/gate_verdict.py` の `enforce()` は連続時間式 $\text{capacity}/W + \text{refill} = 1,200.0\text{ req/s}$ を分母にしていたため、正確に動作している実装（実測 `1,099.9 req/s`）に対して常に `1099.9 / 1200.0 = 0.9166` を算出していた。帯域 `[0.90, 1.10]` の下限からわずか 1.7 % 上に張り付いた状態で、実装が正しくても下側の退行余地がほとんど残っていなかった。
   - あわせて、`gate_verdict.py` の `ci_half` は反復 $n = 2..3$ 回の標本半範囲 `(max - min) / 2` だった。$n = 2$ でこれは標準誤差 $s / \sqrt{2} = 1\text{ SE}$ にちょうど等しく、$t_1$ 分布下の被覆率は 50 % にすぎない（95 % 区間には $t_{0.975, 1} = 12.71$ 倍が要る）。保存済みの 2026-10-21〜24 の生 round（5 run）を 95 % t 区間で再判定すると、`ratelimit_tax_us` は 5 run すべてが当時の帯の下端 0.9 を跨いで INCONCLUSIVE になる（例: `20261024T042039Z` の `1.1967 ± 0.8007 µs`。Decision 3 で下端を 0.5 に移した後の帯でも 5 run 中 3 run が INCONCLUSIVE）。旧方式の「全 PASS」は判定力を過大に見せていた。さらに INCONCLUSIVE 時の運用は「再実行して PASS を採用」で、選択バイアスを生む構造だった。
   - 同じ生データで `ratelimit_tax_us`（k6 閉ループ）は 5 run 中 4 run で同じ run の `dispatch_floor_us`（oha）より小さい（確認 run で `1.20` vs `1.29 µs`。2026-10-25 の 4 run を含めると 9 run 中 7 run）。tax = floor + bucket 参照という加法モデルでは起こりにくく、k6 の `/baseline` 腕が生成器自身の天井付近（~117k–155k rps）で走っていて逆スループット差分が圧縮されている、と読むのが最も自然である（推論）。異なる生成器の差分は足し引きできず、生成器から独立した不変量の候補が要る。
   - 命令数層でも、v0.9.0 の `wasm_inst` 表（`on_request` pooled 507,977 命令 vs Criterion 2.88 µs）は 5.4 GHz で IPC ≈ 33 を要求する物理的に不可能な組で、二層の自己整合を機械的に確かめる仕組みが無かった。

4. **`plecto-loadgen openloop` の 1 ms タイマーホイール量子化と `weighted-mix` のクラス別 `p99.9` 欠落**:
   - Phase 2.2（`openloop`、目標 `100,000 req/s`、64 ワーカー）の実測スループットは `103,026 req/s` であり、64 個の in-flight スロットすべてが飽和していても Little の法則による平均ワイヤ滞在時間の上界は $W = L / \lambda = 64 / 103,026 = 0.621\text{ ms}$ である（クローズドループの Phase 1 `ceiling` では `-c 50` で `p50 = 0.22 ms`、Phase 2.1 `sweep` でも `VU 50` で `p50 = 0.24 ms`）。
   - それにもかかわらず `openloop` の報告 `p50` が `0.841 ms`（平均 `0.895 ms`）だった。`openloop_hist.csv` を 100 µs 刻みで見ると 0.2〜1.4 ms に平らな台地があり、幅 1 ms の一様遅延をワイヤ遅延に畳み込んだ形と整合する。`bench/loadgen/src/openloop.rs` は `tokio::time::sleep_until(scheduled)` を直接呼んでおり、Tokio のタイマーホイールは 1 ms 粒度なので、各発射が最大 1 ms（一様なら平均約 0.5 ms）遅れてその分が schedule-latency に加算される——というのが最有力の仮説である（もう一つの候補である 1 接続あたり 1,610 req/s の接続単位キューイングは幾何的な裾を作るはずで、台地の形とは合わない）。
   - また `bench/k6/weighted-mix.js` では `rt_static` のみ `p(99.9)` を集計し、`rt_auth` / `rt_write` / `rt_large` の `p99.9` を `mix.csv` に出力していなかった。

## Decision

1. **`ConnGuards` の `Arc` 共有と Upgrade トンネルタスクへの寿命束縛（`crates/server/src/{listener,dispatch,proxy}.rs`）**:
   - `listener.rs` に `pub(crate) struct ConnGuards { _permit: OwnedSemaphorePermit, _ip_guard: PerIpConnGuard }` を定義し、TCP accept 時に `Arc::new(ConnGuards { _permit: permit, _ip_guard: ip_guard })` として生成する。
   - `serve_conn` の HTTP/1.1 分岐のリクエストクロージャが `conn_guards.clone()` を `dispatch::handle` → `proxy::proxy_core_with_conn_guards` へ渡す。HTTP/2 は Upgrade 経路を持たない（[[000048]] — h2/h3 は extended CONNECT）ため、h2 分岐のストリームには `None` を渡し、ストリームごとの `Arc` clone/drop と 1 本のキャッシュラインの取り合いを避ける。ガード本体は `serve_conn` のフレームが接続終了まで保持する。
   - `101 Switching Protocols` が成立して `upgrade_switch` がバックグラウンドの双方向トンネルタスクを `tokio::spawn` する際、既存の `_permit`（circuit breaker）や `_pick`（LB）と並べて `let _conn_guards = conn_guards;` をタスク内へ move する。
   - これにより、通常の HTTP/1.1 リクエスト・レスポンスでは従来どおり接続終了時に `Arc<ConnGuards>` の最後の参照が消えてスロットが解放される一方、101 昇格した WebSocket トンネルではトンネルタスクが EOF・エラー・idle timeout・graceful drain のいずれかで終了するまで `MAX_CONNECTIONS` と `MAX_CONNECTIONS_PER_IP`（256）の双方が確実に保持される。
   - `bench/perf/run-perf.sh` の `phase_ws` では、(a) フェーズ冒頭で既存の共有 `bench-server` を停止してクリーンな `bench-server` を新規起動し、(b) `10.1 handshake` や `10.3 echo` より先に `10.2 tunnel footprint` を実行してバースト後のヒープ干渉を排除し、(c) 単一 IP 上限 256 の範囲内である `--conns 250` を指定し、(d) `bytes_per_tunnel` の算出分母に要求数ではなく実保持数 `held` を用い、`held` が 0 ならフェーズを失敗させる。

2. **`fastpath_inst` における初回ウォームアップと返り値化による teardown 除染（`crates/control/benches/fastpath_inst.rs`）**:
   - `group(algo: &str, hash: &str) -> Arc<UpstreamGroup>` ヘルパー内で `let _ = g.pick(Some(HashInput::Ip(IpAddr::V4(Ipv4Addr::new(203, 0, 113, 7)))));` を 1 回実行してスレッドローカル RNG や `arc_swap` の遅延初期化を完了させたうえで、`lb_pick` と `lb_pick_maglev` のシグネチャを `-> Arc<UpstreamGroup>` に変更し、`black_box(g.pick(...))` の後に `g` を呼び出し元（Gungraun ハーネス）へ返す。
   - [[000113]] の `wasm_inst.rs` と同じ規律により、`Arc<UpstreamGroup>` の `Drop` は callgrind の計測区間外で実行される。除染後の実測命令数は以下のとおり約 1 桁減少し、アルゴリズム間の真の計算量差が可視化された:
     - `lb_pick_rr`: `2,114` → **`225` instructions**
     - `lb_pick_p2c`: `2,377` → **`340` instructions**
     - `lb_pick_maglev`: `2,277` → **`282` instructions**

3. **gate の数理整合化 — 離散補充式・95 % t 区間・paired 短窓 round・プール・CPU-µs/req・二層整合（`bench/perf/*`）**:
   - `enforce()` の期待許可レート計算を `apply_bucket` の離散 1 秒ティック意味論に合わせ、`refill_ticks = max(0, band["window_s"] - 1)`、`expected_rate = (band["capacity"] + refill_ticks * band["refill_per_s"]) / band["window_s"]` に修正する。
   - $W = 10\text{ s}$・`capacity = 2,000`・`refill = 1,000/s` における期待レートは `1,100.0 req/s` となり、実測 `1,099.9 req/s` との比 `enforce_allowed_ratio` は `0.9999` となる。帯域 `[0.90, 1.10]` は変更しない（中心が 0.9166 から 1.0 へ移ることで、上下とも約 10 % の退行余地が戻る）。
   - `ci_half` を、round ごとの paired 差分 $d_1..d_n$ の平均に対する両側 95 % Student-t 半幅 $t_{0.975,n-1}\cdot s/\sqrt{n}$ に改める（$df \le 30$ は表、それ以上は Cornish-Fisher 展開。$n = 1$ は `inf` で必ず INCONCLUSIVE）。CSV 列名 `ci_half` は維持し、末尾に `n` 列を追加する。
   - 半幅の倍率 $t/\sqrt{n}$ は $n=2$ で 8.99、$n=3$ で 2.48、$n=8$ で 0.84 なので、gate tier の ladder と rate-limit tax を **8 round × 短窓**（`GATE_D_LADDER=4 s`、`GATE_D_RL=3 s` + warm-up 1 s）に再設計し、偶数 round で腕の順序を反転して順序効果を相殺する。他 phase の窓（`D_WASM` / `D_RL`）は gate tier でも変えない。計測窓の合計はおよそ 265 s → 300 s。
   - INCONCLUSIVE 後の再実行は置き換えではなく **プール** とする: `GATE_POOL_FROM=<RUN_DIR>[:...]` を指定すると `pooled_from.txt` が書かれ、`gate_verdict.py` は前回 run の round 生データを（推移的に）合わせて 1 つの推定にする。計測 binary・実行時に読む WASM フィルタ component・gate パラメータ（`gate_params.txt`）の SHA-256（`build_id.txt`）が一致しない run とのプールは exit 64 で拒否する。プール元は計測前に検証し、`run-perf.sh` の終了コードも 64 のまま伝える（性能 FAIL の 1 と区別するため）。
   - 生成器に依存しない加法的な rate-limit コストとして、固定レート 20k/s（k6 constant-arrival-rate、VU < 256）で `/baseline` と `/ratelimit` を交互に流し、各腕の前後で `/proc/<pid>/task/*/schedstat` を採取してプロキシ CPU-µs/req を求める（`proc_cpu.py`、スレッド終了時は `/proc/<pid>/stat` の utime+stime にフォールバック）。`ratelimit_cpu_us_per_req` は較正が済むまで info 行とし、`gate_tolerances.toml` に帯を足した時点で判定対象になる。
   - `ratelimit_tax_us` の帯の下端を 0.9 → 0.5 に移す（2026-10-25）。最初の 8 round run 3 本の 95 % 区間の下端は最小 0.709 で、2 本が速い側でのみ保留になった。下端を下げて許すのはコストが安い方向だけで、遅い側の上端 2.4（blocking-pool への退行は ~4.6 µs）は変えない。「フィルタが制限をしなくなった」は `enforce_allowed_ratio` が検出するので、この下端が担う必要はない。帯がその 3 run を見て決めた事後設定であることは明記し、独立した holdout run（`20261025T061734Z`、n = 8、プールなし）で単独 PASS を確認した。
   - 命令数と wall-clock の自己整合チェック `ipc_check.py` を置く: gungraun の Ir（スレッド別ファイルを合算）と Criterion の平均 ns から暗黙 IPC = Ir / (ns × GHz) を求め、5 を超えたら非ゼロ終了する。CI は Criterion を回さないので任意手順とする。

4. **`openloop` のサブミリ秒 2 段ペーシングと `weighted-mix` の全クラス `p99.9` 出力（`bench/loadgen/src/openloop.rs` / `bench/k6/weighted-mix.js`）**:
   - `openloop.rs` の到着待機ループにおいて、`scheduled` まで `2 ms` 超の余裕がある場合は `tokio::time::sleep_until(scheduled - Duration::from_millis(1)).await` で 1 ms 手前までスリープし、残りのサブミリ秒区間を `while Instant::now() < scheduled { tokio::task::yield_now().await; }` で協調スピンする。Tokio タイマーホイールの 1 ms 量子化を発射時刻から外しつつ、同一ランタイム上の他タスク（レスポンス受信や hyper の接続ドライバ）の進行を妨げない。再計測（2026-10-25）で p50 は `0.050 ms` となり、Little の法則の上界 0.621 ms を大きく下回った（§ Verification）。
   - `bench/k6/weighted-mix.js` の `handleSummary` と `bench/perf/run-perf.sh` の CSV ヘッダに `auth_p99_9`・`write_p99_9`・`large_p99_9` を追加し、4 トラフィッククラスすべての `p50 / p99 / p99.9` を揃える。

検討した代替案:

- **WebSocket トンネルは `MAX_CONNECTIONS_PER_IP` の対象外とし、ベンチマークスクリプト側だけ修正する** — 却下。
  101 昇格後に `PerIpConnGuard` と `OwnedSemaphorePermit` が外れる挙動は、攻撃者が単一 IP から軽量な WebSocket ハンドシェイクを繰り返すだけで per-IP 上限 256 もグローバル上限 10,000 も無制限に突破できることを意味し、[[000027]] と [[000092]] の inbound admission control を根底から無効化する。コード側で `Arc<ConnGuards>` をトンネルタスクへ move して fail-closed に塞ぐのが唯一の正しい修正である。
- **`openloop.rs` で `std::hint::spin_loop()` によるビジースピンを使う** — 却下。
  `openloop` の各ワーカーは同一 Tokio タスク／スレッド上でレスポンス受信タスク（`tokio::spawn`）と多重化されているため、スレッドをブロッキングスピンさせると受信側の poll が遅延して逆方向の計測歪みを生む。`tokio::task::yield_now().await` による協調スピンであればランタイムの他タスクを回しながらマイクロ秒オーダーの精度で発射できる。
- **`ci_half` の半範囲は据え置き、意味をコメントで明記するだけにする** — 却下。
  名前と中身の食い違いは解消するが、gate が 95 % の確からしさで帯の内側にあると主張できないことは変わらない。保存済みの生 round を t 区間で再判定すると `ratelimit_tax_us` は当時の帯に対して全 run で INCONCLUSIVE になり、判定力の不足は実データで確認できる。
- **gungraun ベンチを 1 回呼び出しから K 回ループに変え、固定費を償却する** — 却下。
  CI の `ir=5%` ソフトリミットは main で保存した baseline との比較なので、K 倍化した最初の PR が必ず上限を踏む。現行の「setup で 1 回温め、1 回呼び、fixture を返して drop を区間外へ出す」形で固定費は既に区間外にあり、`ir=5%` は `on_request` pooled（30,448 命令）で約 1.5k 命令とホットパス 1 回分より十分小さい。
- **ratelimit tax を dispatch floor と同じ oha で測り直して加法性を回復する** — 採らない。
  `/ratelimit` は 1,000 キーに散らしたヘッダを要し、oha の固定ヘッダでは bucket の参照パターンが変わる。生成器の天井と無関係な CPU-µs/req を別に持つほうが、閉ループ差分の生成器依存そのものを避けられる。

具体化する Tenet:
- `CLAUDE.md` コア原則「fail-closed」「deny-by-default capability」「ベンチ駆動の設計判断（不純物のないベースライン維持）」

## Consequences

### Pros
- HTTP/1.1 Upgrade（WebSocket）トンネルが `MAX_CONNECTIONS`（10,000）・`MAX_CONNECTIONS_PER_IP`（256）・circuit breaker permit・LB `Pick`・request admission permit・`tunnels_active` gauge の資源会計に漏れなく乗り、drain でも閉じるようになり、101 昇格を利用した接続上限バイパス（CWE-770）が構造的に封じられる（`tests/upgrade.rs` の E2E テストで 256 本保持中の 257 本目拒否と、1 本閉鎖後にスロットが再利用できることを自動検証）。
- `fastpath_inst` の LB pick 命令数が teardown 除染により `225〜340 instructions` の純粋な per-pick コストを反映するようになり、CI の命令数ソフトリミット（`--callgrind-limits=ir=5%`）が許す変動が約 106 命令（旧 2,114 命令基準）から約 11〜17 命令へ縮み、感度が約 6〜9 倍向上する。
- `gate_verdict.py` の `enforce_allowed_ratio` が `apply_bucket` の離散 1 秒補充モデルと一致し（`0.9999`）、従来から変わらない帯域 `[0.90, 1.10]` の中心に乗るので、上下どちらの退行も検知できるようになる。
- gate の `ci_half` が名前どおりの 95 % 区間になり、PASS の主張に統計的な裏付けが付く。8 round の paired 設計で $t/\sqrt{n}$ は 3 round 比で約 1/3 になる（窓を短くした分 round あたりの分散は増えうるが、実測の `dispatch_floor_us` 区間は n = 3 の ±0.08〜0.26 から n = 8 の ±0.05〜0.12 に縮んだ）。再実行のプールで「通るまで回す」選択バイアスが構造的に除かれる。
- rate-limit コストを生成器に依存しない CPU-µs/req でも追えるようになり、`ipc_check.py` で命令数層への fixture 混入を機械的に検出できる。
- `openloop` 負荷生成器から 1 ms タイマー量子化の発射遅延が取り除かれた。2026-10-25 の再計測（同一ホスト、103,026 req/s）で p50 は `0.84 → 0.050 ms`、平均は `0.895 → 0.132 ms` に下がり、0.2〜1.4 ms の台地が消えた（最初の 100 µs ビンに 89.6 %）。

### Cons / Tradeoffs
- 単一クライアント IP（または単一 IPv6 `/64`）から同時に張れる WebSocket トンネル数も、通常の HTTP 接続と合算で `MAX_CONNECTIONS_PER_IP = 256` に制限される。[[000092]] の再検討条件と同様、大規模 NAT 配下で単一送信元 IP から 256 本を超える同時 WebSocket 接続が必要な環境では、将来的なマニフェスト設定化の対象となる。
- `openloop` の最終 1 ms 区間で `yield_now()` を回すため、loadgen の生成器コア（`GEN_CPUS=12-23`）はペーシング中ほぼ常時ビジーになる。プロキシとは別プロセス・別コアだが、パッケージの電力・熱の予算は P コアの Turbo と共有なので、生成器の消費電力増がプロキシ側のクロックを下げる交絡はありうる（governor は `powersave` で非固定）。影響の上限は、同じ build で旧ペーシングと新ペーシングの openloop を並べ、プロキシ側の CPU-µs/req（`proc_cpu.py`）と閉ループ ceiling が動かないことで確認する。
- gate の計測窓の合計がおよそ 265 s から 300 s へ約 15 % 伸びる。また旧方式の帯は half-range 基準で設定されたままなので、`ratelimit_tax_us` の下端を除き、n = 8 の実測が数本たまるまで帯の再較正は保留する。
- graceful shutdown の `acquire_many(MAX_CONNECTIONS)` は、接続ガードを持つようになったトンネルの終了も待つ。確立済みトンネルは `splice` が drain フラグで閉じ、確立前（両側の `OnUpgrade` 待ち）も `tunnel::run` が drain を監視して抜けるので drain は止まらない。ただしトンネルタスクは `conns` の `JoinSet` 外で spawn されるため、drain 期限での `abort_all()` の対象にはならない。
