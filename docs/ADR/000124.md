# ホスト同期実行・借用契約射影・ゼロコピー高速経路・観測遅延生成の 4 軸でプロキシデータプレーンを最適化する

## Status
accepted

## Date
2026-11-14

## Affected Components
- `plecto/crates/host/src/engine.rs` — `wasmtime = "50.0.1"` 上で非同期 WASI 機能（`outbound-http` / `outbound-tcp` / `fat-guest`）をリンクしないビルドでは `Config::concurrency_support(false)` を明示し、`Store` ごとの並行タスク管理構造体初期化を省略
- `plecto/crates/host/src/host.rs` / `runtime.rs` / `state.rs` — コンポーネントが `wasi_base` やアウトバウンド runtime を借りない場合 `needs_async_store = false` として `InstancePre::instantiate` / `TypedFunc::call` の同期直接呼び出しを選択。`host-clock` / `host-ratelimit` / 未知外部インポートがない場合 `needs_wall_clock = false` としてリクエスト毎の `SystemTime::now()` を抑止。0.2 / 0.3 契約では `ValidatedV02` / `ValidatedV03` がインスタンス初期化時に `Func::typed::<(HttpRequestV02V03Ref<'_>,), ...>` を一度だけ検証し、呼出毎の `String` / `Vec<Header>` 複製を廃して借用 Lowering を実施
- `plecto/crates/host/src/pool.rs` — `PoolInner` に `waiters: usize` を追加し、`idle.push` / リサイクル / discard 時の `available.notify_one()` を実際の待機スレッドが存在する場合に限定
- `plecto/crates/host/src/observe.rs` / `filter.rs` — `RequestTrace::to_traceparent_bytes(&self) -> [u8; 55]` でスタック上の W3C `traceparent` 生成を追加。`TelemetrySink::needs_full_span` と `record_outcome` を追加し、`NoopSink` および `MetricsSink` が有効な場合は `FilterSpan` 構築・`SpanId` 採番・`SystemTime::now()`・ホストログ回収（`capture_logs`）を遅延・抑止
- `plecto/crates/control/src/route.rs` / `snapshot.rs` / `lib.rs` / `chain.rs` / `upstream/instance.rs` — `normalize_path` の単一パス走査（ドットセグメント無しの通常経路は `Cow::Borrowed` 返却）、`HeaderLookup` トレイトによる `&http::HeaderMap` 直接マッチ（静的 hop-by-hop および `Connection` 動的指定ヘッダ除外を `headers_to_vec` と同一意味で維持）、`compile_route_order` / `select_ordered` による設定コンパイル時ソートと早期終了、`UpstreamInstance::uri_authority` の事前パース、`LoadedFilter::*_for_chain` によるログ抑止呼出を追加
- `plecto/crates/server/src/proxy.rs` / `headers.rs` / `forward.rs` / `metrics.rs` / `compression.rs` — 無フィルタ経路での `ConfigSnapshot::match_route_parts`（`MatchedRoute<'a>` 借用ルーティング）＋ `AttemptHeaders::Direct`（`copy_headers_direct`）＋ `stream_response_direct` による契約射影（`HttpRequest` / `HttpResponse` / `Vec<Header>`）の完全バイパス、`ServerMetrics::with_counters`・`compression::apply`・`Attribution<'a>`・`request_authority_str` による借用化、`set_forwarded` の `[u8; 48]` スタックバッファ IP 書式化、ならびに `has_valid_port_syntax` の ASCII 数字限定（RFC 3986 §3.2.3）修正
- `bench/perf/gate_tolerances.toml` — pooled 較正計測（`n = 24`）に基づき `dispatch_floor_us` / `apikey_cost_us` / `ratelimit_tax_us` の下限（`lo`）のみを再設定（上限 `hi` は据え置き）

## Context

[[000021]] で M3 Stage 1（host async 化）を導入して以降、すべての WASI 非利用・同期 WASM フィルタを含め、`engine.rs`・`runtime.rs` は一律に `InstancePre::instantiate_async` と `TypedFunc::call_async` を Wasmtime のファイバー上で `block_on_with_deadline` 駆動し、さらに [[000119]] で inline 実行経路を導入した後も、1 リクエストあたり以下のホスト側固定費と契約変換費が残存していた（[[000119]] の Consequences で未解明 CPU として先送りされていた領域）:

1. **Wasmtime 実行形態と契約変換コスト**:
   - WASI 非依存・非同期インポートを持たないゼロ WASI フィルタに対しても、ファイバー確保・コンテキストスイッチおよび `Config::concurrency_support`（Wasmtime `50.0.1` では並行 `Store` データ構造を初期化する）相当のオーバーヘッドが毎リクエスト発生していた。
   - 0.2 / 0.3 契約では実行前のリクエスト毎アダプタ（`request_to_v02` / `request_to_v03`）が全ヘッダ・文字列をヒープ複製し、さらに不要なフィルタでも `SystemTime::now()` を毎回取得していた。
   - プール返却時は `waiters == 0` の無競合時でも毎回 `Condvar::notify_one()` のシステムコール／ロック検査を踏み、ログ・メトリクス用途のみの `MetricsSink` / `NoopSink` でもフック毎に `FilterSpan` 構築と `SystemTime::now()`、空ログ用 `Vec` 回収を行っていた。
2. **プロキシ経路のルーティング・ヘッダ処理・契約射影コスト**:
   - `proxy_core_inner` はルートにフィルタが 0 個の経路であっても、`to_http_request` による `HttpRequest` / `Vec<Header>` 構築と応答側 `HttpResponse` 変換をルーティング前に行っていた。
   - `route::normalize_path` がセグメント分割前に複数パスで走査・確保を行い、`route::select` はリクエスト毎に全ルートを走査して `max_by_key` で順位付けしていた。
   - フォワード時はアップストリームの `pick.address()` から毎回 `Uri::from_str`（文字列結合 `format!` + Authority 再パース）を行い、`set_forwarded`・`traceparent` 生成もヒープ文字列を都度確保していた。
3. **実測と上流仕様に基づく検証基盤**:
   - Criterion（`plecto-host --bench wasm`, `plecto-control --bench fastpath`）、Valgrind Cachegrind ベースの決定論的命令数計測（`gungraun`: `wasm_inst`, `fastpath_inst`）、CPU アフィニティ固定（`PROXY_CPUS=0-11`, `GEN_CPUS=12-23`）+ ナノ秒解像度 `/proc/<pid>/schedstat` 付き 3 ラウンド交互 A/B（`bench-server`）、および `just gate`（`n=8×3` pooled 較正 + 独立 holdout）の多層計測により、推測ではなく命令数・CPU 消費（µs/req）・スループット・テール遅延・不変条件を直接裏打ちした。
   - また、Wasmtime 50.0.1 公式 API ドキュメント（[Config::concurrency_support](https://docs.rs/wasmtime/50.0.1/wasmtime/struct.Config.html#method.concurrency_support), [component::TypedFunc](https://docs.rs/wasmtime/50.0.1/wasmtime/component/struct.TypedFunc.html)）、[RFC 9110 §7.6.1](https://www.rfc-editor.org/rfc/rfc9110#section-7.6.1)、[RFC 9112 §3.2](https://www.rfc-editor.org/rfc/rfc9112#section-3.2)、[RFC 3986 §3.2.3](https://www.rfc-editor.org/rfc/rfc3986#section-3.2.3)、[W3C Trace Context](https://www.w3.org/TR/trace-context/) に照らし、セキュリティ境界とプロトコル厳格性を一切緩めない範囲を見定めた。

## Decision

Plecto のセキュリティ不変条件（deny-by-default capability・hop-by-hop / `Connection` 動的除外・トラバーサル拒否・fail-closed・ゼロコピーボディ境界・契約バイト等価）を一切緩和せず、**初期化時分類とリクエスト時ゼロアロケーション** を徹底する 4 軸の最適化を採用する。

### 1. ホスト拡張面（`plecto-host`）の同期直接呼出と借用 Lowering・選択的初期化
- **同期エンジン／ストア切替（[[000021]]・[[000119]] の補完）**:
  - `engine::build_engine` において、非同期 WASI 機能（`outbound-http` / `outbound-tcp` / `fat-guest`）がいずれもコンパイル有効でない構成では `config.concurrency_support(false)` を設定する。
  - `Host::load` がコンポーネントのインポートと貸与 capability スライスを検査し、`needs_async_store = lent.wasi_base || needs_rt` を事前決定する。`needs_async_store == false` のフィルタ（ゼロ WASI フィルタ）は `InstancePre::instantiate` および `TypedFunc::call` を呼び出しスレッド上で直接同期実行し、`drive_call`（ファイバー生成と Tokio `block_on` ポーリング）を完全にバイパスする。`needs_async_store == true` のフィルタ（`wasi = "minimal"`・outbound HTTP/TCP・streaming）は従来どおり `instantiate_async` / `call_async` を維持する（[[000021]] の機能後方互換を保持）。
- **初期化時型検証済み借用パラメータ Lowering（`HttpRequestV02V03Ref<'a>`）**:
  - `ValidatedV02`・`ValidatedV03` を導入し、インスタンス生成時（コールドパス）に `Func::typed::<(HttpRequestV02V03Ref<'_>,), ...>`（および v0.3 の `on-response` 用 `(HttpRequestV02V03Ref<'_>, &HttpResponse)`）を一度だけ検証して保持する。
  - Component Model ABI 上でレコードレイアウトが `types_v02::HttpRequest` / `types_v03::HttpRequest` と同一である借用ラッパー `HttpRequestV02V03Ref<'a>` により、v0.2 / v0.3 呼出時の `String`・`Vec<Header>` 全量クローンを撤廃し、ヘッダバイト検証・不変条件を保ったままゼロクローンで Lowering する。
  - 同様の理由で `func_*` 毎の型再チェックではなく、`unsafe { TypedFunc::new_unchecked(...) }` を「直前の `ValidatedV02::new` / `ValidatedV03::new` で同一 `Store` 向けに `Func::typed` 検証済みである」という明確な安全不変条件の下に限定して適用する（`unsafe_op_in_unsafe_fn = "deny"` 遵守）。
- **条件付き壁時計と待機者限定 Condvar 通知**:
  - コンポーネントが `host-clock`・`host-ratelimit` または未知の外部インポートを持たない場合 `needs_wall_clock = false` とし、`HostState::new` / `begin_request` での `SystemTime::now()` 呼び出しを省略する。
  - `PoolInner` に `waiters: usize` を保持し、`TrustedPool` への返却・リサイクル・破棄時、`g.waiters > 0` のときに限り `available.notify_one()` を呼ぶ。

### 2. 可観測性（`plecto-host/observe`）の遅延生成とスタック書式化（[[000009]] の補完）
- `TelemetrySink` トレイトにデフォルト実装付きの `needs_full_span(&self) -> bool` と `record_outcome(&self, outcome, duration, span_builder: &mut dyn FnMut() -> FilterSpan)` を導入する（既存の外部 `TelemetrySink` 実装との後方互換を維持）。
- `NoopSink` およびカウンタ集計専用の `MetricsSink` は `needs_full_span() -> false` を返し、`execute_hook` は `full_span == false` のとき `SystemTime::now()`・`SpanId` 採番・`FilterSpan`（`Vec<KeyValue>` / `Vec<Event>`）構築を完全にスキップし、`LoadedFilter::*_for_chain` 経由の呼び出しでも `capture_logs = false` としてホストログ収集を省略する。`FanOutSink` は子シンクの `any_needs_full_span` に応じて、必要なときのみ `span_builder()` を最大 1 回だけ評価して全 `needs_full_span` シンクへ共有する（[[000009]] の OTel データモデル・W3C 相関・`InMemorySink` / `OtlpBuffer` の出力契約は無変更）。
- `RequestTrace::to_traceparent_bytes(&self) -> [u8; 55]` を追加し、`00-<32hex>-<16hex>-01/00` の固定 55 バイト（[W3C Trace Context](https://www.w3.org/TR/trace-context/)）をヒープ確保なしでフォワード要求へ書き込む。

### 3. 制御面・ルーティング・上流解決（`plecto-control`）の前処理移管と借用照合
- **単一パス `normalize_path`**:
  - リクエストパス文字列を先頭から `?` まで 1 パスで走査し、制御バイト・`\`・`%2e`/`%2f`/`%5c`（大文字小文字含む）を即座に拒否（`None`）しつつ、`.` / `..` セグメントの有無だけを検出する。ドットセグメントを含まない通常パスは `Cow::Borrowed(target)` を返し、ヒープ確保をゼロにする。
- **`HeaderMap` 直接 `HeaderLookup` と静的ルート順 `compile_route_order`**:
  - ルーティングのヘッダ一致を抽象化する `HeaderLookup` トレイトを `[Header]` と `&http::HeaderMap` の双方に実装する。`HeaderMap` 実装でも静的 hop-by-hop ヘッダ（`is_hop_by_hop_lower`）および `Connection` ヘッダで動的に指定されたヘッダ名を除外し（[RFC 9110 §7.6.1](https://www.rfc-editor.org/rfc/rfc9110#section-7.6.1) / CWE-436）、契約射影後の `headers_to_vec` と同一の一致結果を維持する。
  - 設定コンパイル時に Gateway-API 特異性順（`host` > `path_prefix.len()` > `method` > `headers.len()` > `query.len()` > 宣言順）へインデックス配列 `route_order: Box<[usize]>` を事前ソートし、`select_ordered` で先頭一致時に即座に打ち切る（最良探索と完全同値）。
- **上流 `Authority` 事前パース**:
  - `UpstreamInstance::new` 時に `address.parse::<http::uri::Authority>()` を事前計算し、`forward_with_retry` のリトライループ内での `format!`＋文字列再パースを排除する。

### 4. プロキシデータプレーン（`plecto-server`）の無フィルタゼロコピー経路とプロトコル厳格化
- **無フィルタ経路での契約射影バイパス（[[000119]] の補完）**:
  - `proxy_core_inner` は `norm_path` と借用 authority（`request_authority_str`）を用いて `snapshot.match_route_parts`（借用 `&HeaderMap` 照合）でルートを決定し、**マッチしたルートがフィルタを持つ（`route.has_filters()`）場合にのみ** `to_http_request_with` による `HttpRequest` / `Vec<Header>` 構築およびチェーンディスパッチ（応答側の `HttpResponse` 変換と `respond_through_chain` 含む）を実行する。
  - 無フィルタ経路では `AttemptHeaders::Direct(&parts.headers)` → `copy_headers_direct` および `stream_response_direct` を通り、静的 hop-by-hop ヘッダ + `Connection` 動的指定ヘッダ除外を `http::HeaderName` / `HeaderValue` の参照カウント共有クローンのみで完遂する（`close` / `keep-alive` トークンの不要な小文字化・`HashSet` 挿入も省略）。
- **周辺ホットパス確保削減と厳格性の明確化**:
  - `set_forwarded` は IPv6 最大長 45 バイトを収容する `[u8; 48]` スタックバッファへ書式化し `HeaderValue::from_bytes` へ直接渡す。`MatchedRoute<'a>`（`RouteInfo` クローン回避）・`Attribution<'a>`（ルート名 `&str` 借用）・`compression::apply`（`Option<&CompressionConfig>` 借用）・`ServerMetrics::with_counters`（`Arc<RouteCounters>` クローン回避）により、リクエスト毎の参照カウント増減と不要コピーを排除する。
  - 入口 authority 正規化（`normalize_ingress_authority`, [RFC 9112 §3.2](https://www.rfc-editor.org/rfc/rfc9112#section-3.2)）のフォールバック検証において、`has_valid_port_syntax` を Rust 標準の `u16::from_str` 任せ（`+80` 等の先頭 `+` を許容してしまう）から `!port.is_empty() && port.bytes().all(|b| b.is_ascii_digit()) && port.parse::<u16>().is_ok()` へ厳格化し、[RFC 3986 §3.2.3](https://www.rfc-editor.org/rfc/rfc3986#section-3.2.3)（`port = *DIGIT`）準拠へ揃えた。なお非 IPv6 ホスト部のパーセント文字（`ex%2d.example`）は `http::uri::Authority::from_str` 自体が拒否するためフォールバック試験でも fail-closed のまま扱う。

### 却下・保留した代替案
- **Wasmtime pooling allocator を全フィルタ（untrusted 含む）へ拡大**: untrusted フィルタはリクエスト単位の隔離・ゼロ初期化・メモリ上限独立性（[[000006]]・[[000012]]）が原則であるため不採用。ゼロ WASI の純同期呼出化によって untrusted 自体の呼出時間も `-51.33%`（`35.30 µs -> 17.18 µs`）改善した。
- **`unsafe` な契約バイト列の線形メモリ直接マップ**: Wasm guest の未検証バイト列を `headers` バリデーション無しで信用することは [[000021]]・[[000119]] のフェイルクローズ原則に反するため不採用。`HttpRequestV02V03Ref<'a>` による安全な Rust 側借用 Lowering + 返却値の従来どおりの `request_decision_from_*` 検証を採用した。
- **アクセスログ／フック毎トレースのサンプリング率強制的引下げ**: [[000009]]・[[000099]] が定める観測契約を変更することになるため不採用。`MetricsSink` / `NoopSink` 側の `needs_full_span = false` 最適化のみを行い、サンプリングされた要求および `InMemorySink` / `OtlpBuffer` の出力内容は 1 ビットも変えていない。
- **ゲート許容帯の上限（`hi`）緩和**: 性能向上に伴って高速側下限（`lo`）のみを割り込む現象が見られたため、`hi`（`2.1` / `1.7` / `2.4`）は一切緩めず `lo` のみ再較正した。

## Consequences

### Pros
- **WASIp2 / Component 呼出の命令数と時間半減**: ゼロ WASI フィルタに対する `on_request` 時間は pooled で `-49.25%`（`1,915.68 ns -> 972.25 ns`）、untrusted（毎回インスタンス生成）で `-51.33%`（`35.30 µs -> 17.18 µs`）、Valgrind 命令数はそれぞれ `-31.31%`・`-26.89%`、LL キャッシュミス（ヒープ操作由来）も `-51%〜-61%` 削減された。
- **実トラフィック相当での高スループットと低 CPU 消費**: 全プロキシ経路で CPU 消費が `15.90%〜17.08%` 削減され、フィルタ有りの `trusted` / `ratelimit` ではスループットが `+21.19%` / `+18.20%` 向上し p99 遅延も低下した。
- **設定規模に強い制御面**: `find_route` はルート数 16 で `-50.50%`、64 で `-33.41%`、通常パスの `normalize_path` は `-47.55%〜-57.36%` に短縮された。
- **セキュリティと観測性の維持**: hop-by-hop・`Connection` 指定ヘッダの除外、パス正規化・authority 検証（RFC 3986 §3.2.3 準拠強化）、サンプリング済みスパンやログ出力契約、および 10 本すべての性能ゲート不変条件（`just gate` exit 0）が無欠損で保たれた。

### Cons / Tradeoffs
- **`ValidatedV02` / `ValidatedV03` 内の `unsafe` 境界**: `TypedFunc::new_unchecked` を用いているため、`ValidatedV02::new` / `ValidatedV03::new` と呼出シグネチャ（`HttpRequestV02V03Ref<'_>` 等）の対応を将来の契約版で崩してはならないという保守不変条件が加わる（`wasmtime` の安全契約としてユニットテスト＋統合テストで担保）。
- **飽和ループバック下での無フィルタ経路 p99 変動**: 12 コア上限の飽和負荷（`bench-server` `baseline` / `noop-pooled`）では 1 リクエストの CPU 時間が下がりスループットが上がった反面、瞬間的なバッチ起床に伴う p99 遅延が `0.53 ms -> 0.96 ms`（`noop-pooled` では `0.59 ms -> 0.73 ms`）へ変動する挙動が見られた。非飽和の通常・テール計測（`just gate`）では `+0.0089 ms` 未満であり問題ないが、極限飽和時のスケジューリングジッタは引き続き観察対象とする。
- **再見直し条件**:
  1. WASI 0.3 / Component Model async（[[000123]]）を既定パスへ切り替える際は、`needs_async_store == false` のゼロ WASI 同期最適化を 0.4 以降の async 世界で維持する境界を再定義する必要がある。
  2. `outbound-http` / `outbound-tcp` / `fat-guest` のいずれかを既定有効化するリリースプロファイルへ移行する場合、`engine.rs` の `concurrency_support(false)` ビルド分岐をストア単位設定（または非同期ビルド前提の評価）へ見直す。
  3. 今後 Wasmtime のアップグレードにより `HttpRequestV02V03Ref` と `wit-bindgen` 生成型レイアウトが乖離した場合や、フィルタ実装の最適化により `ratelimit_tax_us` 等がさらに負側へ振れる場合は `gate_tolerances.toml` を再較正する。
